# Комнаты

Комнаты — голосовые разговоры до пяти участников, общий экран YouTube или аудиозаписей и эфемерный чат. Страницы `/rooms` и `/room/<uuid>` существуют отдельно для компьютера и телефона, используют общие скрипты. В OpenVK комнат нет: список следует его списку групп, блоки — профилю, чат — беседе. Записи разговоров, камера, показ экрана, жалобы и отдельные слушательские роли не входят в эту версию.

## Жизнь и доступ

`room` (gRPC 7059, метрики 9059, CN `room`) владеет PostgreSQL с таблицами `rooms`, `room_bans` и outbox. Временная комната закрывается через `ROOM_EMPTY_TTL` (5 минут) после ухода последнего участника. Постоянная сохраняет адрес: максимум три личных или пять на сообщество. Создавать комнаты сообщества могут его руководители. Владелец меняет название, вид, доступ и управление экраном, закрывает комнату, выключает чужой микрофон и выгоняет участника. Бан временной комнаты действует до её закрытия, постоянной — 24 часа.

Доступ: `everyone`, `friends` (взаимная подписка на хозяина), `link` (не попадает ни в один список), `club` (участники сообщества). Гость читает только публичную карточку, без чата и медиа. Чёрный список хозяина скрывает комнату. Заблокированная или удалённая страница войти не может. Между участниками чат фильтруется сервером в обоих направлениях; `join.mutedIds` запрещает браузеру подписываться на их аудио. Пользователь также может локально отключить звук другого участника.

Для отношений `room` вызывает новые внутренние `user.GetRoomAccess` и `club.GetRoomAccess`. Они всегда требуют проверенный mTLS CN `room`, в том числе при разработке. `PurgeUser`, `PurgeClub` доступны только CN `user`, `club`; оба вызываются через outbox окончательного удаления. `CurrentRooms` и `AuthorizeMedia` — только CN `gateway`. Эти RPC не входят в публичные методы.

## Присутствие и состояние

Redis хранит sorted set участников (`room:members:<id>`, score — последний heartbeat), время входа, индекс `room:current:<user>`, живые комнаты, момент опустения, экран и последние 50 сообщений чата. У всех ключей TTL `ROOM_STATE_TTL` (24 часа). Heartbeat каждые 20 секунд, уход без него через 45 секунд; sweep каждые 10 секунд под Redis SET NX с TTL. Возобновившийся heartbeat проверяется повторно атомарно, чтобы sweep не выгнал ожившего участника. В `inmem` то же время и TTL через Clock.

Lua атомарно проверяет вместимость целевой комнаты до выхода из прежней; один пользователь находится только в одной комнате. Пределы — `ROOM_MAX_MEMBERS=5` и `ROOM_MAX_LIVE=20`. Метаданные, квоты, входы и закрытия сериализованы транзакцией PostgreSQL с advisory lock; бан и команда удаления медиа записываются в outbox в одной транзакции. Команда LiveKit исполняется сразу и повторяется relay при сбое. Отложенное обычное удаление не отключает новую разрешённую сессию в той же комнате.

События `room_join`, `room_leave`, `room_chat`, `room_playback`, `room_update`, `room_closed`, `room_kick` идут через pkg/pubsub Redis и `room.Subscribe`, затем через существующий `/api/v1/events`. Переполнение потока требует повторного join для полного снимка; join идемпотентен. Выход страницы отправляется sendBeacon: access-токен только в JSON-теле, никогда в URL.

## Голос

Закреплённый LiveKit `v1.13.11` принимает сигнал через same-origin `/rtc` (WebSocket), медиа — UDP 7882, запасной TCP 7881. HTTP 7880 и административный Twirp API наружу не опубликованы. LiveKit API key/secret создаёт deploy/deploy.sh на сервере и хранит в `.env`. Браузеру достаётся HS256 JWT на 10 минут: одна комната, одна личность, только microphone audio; без камеры, данных и административных прав.

На self-hosted LiveKit RemoveParticipant не отзывает старый JWT. Поэтому Caddy направляет `/rtc` через gateway, который перед каждым сигнальным подключением вызывает `room.AuthorizeMedia`: проверка подписи и срока медиа-токена, актуального членства, бана и доступа. После исключения, переключения комнаты или закрытия старый токен больше не даёт войти в сигнал. Само исключение вызывает RemoveParticipant, закрытие — DeleteRoom. Caddy не пишет `/rtc` в access log: SDK передаёт медиа-токен в query. Gateway логирует только path.

Звук шифруется DTLS-SRTP до сервера; сквозного шифрования комнаты нет. Это объяснено в справке на странице. Участники видят IP сервера, а не друг друга. Личные звонки продолжают использовать прежнее сквозное шифрование и TURN. Комната и звонок взаимно исключаются клиентом.

`room-voice.js` лениво загружает закреплённый ES-модуль livekit-client; версия, хеш и CSP-проверка — docs/web.md и scripts/rooms-probe/README.md. CSP не ослаблена. В ожидании разрешения микрофона и автозапуска звука чат, экран и heartbeat уже работают. При потере транспорта SDK переподключается; после окончательного разрыва клиент получает новый `/token` с повторной проверкой членства.

## Общий экран

Состояние: kind (`youtube` или `audio`), mediaId, playing, position в секундах, серверный updatedAt, монотонная version и очередь максимум 50. `SetPlayback` проверяет участника и режим управления (`owner` или `everyone`), затем делает CAS в Redis. Старая версия даёт HTTP 409 с актуальным playback. Смена вида хозяином очищает несовместимый экран и очередь, повышая version; хозяину для настройки не нужно вступать в комнату. Позиция рассчитывается относительно серверного времени; отклонение более двух секунд исправляется. URL YouTube превращается в проверенный 11-символьный ID; аудиозаписи выбираются существующим picker и воспроизводятся существующим player.js. Ошибка недоступного трека показывается участникам, бесконечного автоматического пропуска нет.

`room-sync.js` содержит чистую математику, `room-screen.js` — встроенный экземпляр player.js. Экран остаётся во внешнем документе: фрейм сообщает только прямоугольник для размещения. Управление идёт через сервер, встроенные элементы YouTube не перехватывают экран.

## Комнаты на сайте

Меню показывает число видимых комнат с друзьями. Над лентой — до трёх живых комнат; пустой блок скрыт. Под статусом человека — ссылка на текущую доступную комнату. Gateway получает CurrentRooms пакетом для страниц списков людей. В сообществе комнаты выглядят как блок обсуждений справа, на телефоне — как строка в меню группы. Список доступен на `/rooms?club=<id>`. В пустом блоке руководитель открывает форму создания ссылкой с `create=1`. Пустой список предлагает создать комнату и показывает постоянные комнаты друзей.

Приглашения — `notification.KIND_ROOM_INVITE`, outbox и уникальность actor/recipient/room. Название разрешается в gateway из актуальной комнаты; закрытие отзывает приглашения. Push не содержит текст чата или название комнаты.

`room-runtime.js` — один экземпляр во внешнем документе. shell.js принимает несколько причин сохранения оболочки (плеер или комната). Страницы открываются во фрейме, сверху остаются название, число участников, микрофон, «Вернуться», «Выйти». Фреймы получают снимки без медиатокена. Отдельный localStorage-флаг различает вкладки и аккаунты; вторая комната прекращает прежнюю. На телефоне экран прилипает к верху, участники идут полосой, свои кнопки — снизу.

## Запуск и проверки

`make dev-rooms` добавляет room к обычному dev, включает mTLS для всех сервисов и локальный LiveKit с тестовыми ключами. `make dev` остаётся без Docker и комнат. `make stack` включает room-postgres, room и LiveKit; прод использует образы GHCR, закрытые порты БД и публичные только 7881/TCP, 7882/UDP. На уже установленном сервере перед первым запуском надо открыть эти два порта ufw (bootstrap делает это для новой машины).

Тесты: доменные границы и доступ, use cases с Clock, bufconn RPC/Subscribe, PostgreSQL и Redis через make check-integration, маршруты и сигнальный прокси gateway, математика синхронизации, полные проверки сайта. Smoke создаёт комнату, входит двумя людьми, отправляет чат, проверяет CAS и реальный `/rtc/validate` (200 для участника, 403 для его сохранённого медиатокена после выхода), выходит и закрывает комнату. CI задаёт временным комнатам TTL 3 секунды и sweep 1 секунду для проверки автоматического закрытия.

Метрики: room_live по kind, room_members, room_joins_total, room_join_failures_total по ограниченным причинам, room_session_seconds, room_playback_changes_total. Prometheus собирает и LiveKit. В Grafana — строка «Комнаты», алерты на недоступность, ошибки входа >20%, потери >5% и выходящий трафик. Начальный сетевой бюджет алерта 10 Мбит/с (порог 8); его надо соотнести с реальным каналом провайдера перед увеличением вместимости.

Владелец разрешил выпуск 2026-11-10 и взял физическую проверку голоса на проде на себя: Chrome, Firefox и Safari на iPhone в разных сетях, включая сеть без UDP. Локальный встроенный браузер не заменяет проверку телефона. iOS может остановить звук при сворачивании вкладки.


## Проверено 2026-11-10

`make check-integration` прошёл с PostgreSQL, Redis и проверкой protobuf; после заключительных изменений прошли `make -C room check`, 270 тестов сайта и повторный полный smoke на окончательных образах. Конфигурации compose (включая production) и Caddy 2.10.2 проверены. Во встроенном браузере проверены создание, вход, чат, YouTube, смена вида, мобильная страница 390×844, навигация через оболочку и возврат без выхода из комнаты. После перезапуска LiveKit клиент вернулся в подключённое состояние. Физические микрофоны и iPhone этим не проверены.

До выпуска сервер проверен по SSH только на чтение: 1968 МБ RAM, около 756 МБ available, одно ядро; LiveKit с начальным пределом требует наблюдения за памятью и нагрузкой. Скорость канала и месячная квота трафика провайдера не подтверждены; порог алерта пока использует описанный выше начальный бюджет.
