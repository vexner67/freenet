# AGENTS.md — правила разработки бэкенда Freenet

Freenet — социальная сеть наподобие Twitter. Бэкенд: набор Go-микросервисов в монорепозитории (`go.work`). Снаружи доступен только `gateway` (REST/JSON, контракт — `gateway/api/openapi.yaml`); внутренние сервисы общаются по gRPC поверх mTLS.

Этот файл — источник правил для людей и AI-агентов. Перед изменением кода прочитай его целиком. Новый агент, продолжающий работу, — начни с §10: там текущее состояние, договорённости с владельцем проекта и что делать дальше. Если правило конфликтует с существующим кодом — прав правило, код нужно привести к нему (но не рефакторь чужой код «заодно», см. раздел «Рабочий процесс»).

---

## 1. Стек и структура репозитория

- Язык: Go (версия — из `go.work`). Транспорт: gRPC + protobuf. БД: PostgreSQL (`pgx/v5`, `pgxpool`), Redis (`go-redis/v9`) для эфемерных данных (коды, счётчики лимитов) и живых событий между репликами (pub/sub).
- Конфиг: `caarlos0/env` + `godotenv`. Логи: стандартный `log/slog`. Миграции: `goose`. JWT: `golang-jwt/jwt/v5` (RS256).
- Модуль каждого сервиса: `github.com/vexner67/freenet/<service>`, общие модули: `github.com/vexner67/freenet/pkg/<name>`.

```
freenet/
├── go.work                  # workspace: все сервисы и pkg/*
├── compose.yaml             # postgres на каждый сервис, redis; сервисы и Prometheus — в профиле app
├── monitoring/             # наблюдаемость стека: prometheus.yml (что собирать), alerts.yml (+ alerts_test.yml),
│                            # alertmanager.yml (кого оповещать), grafana/ (источники данных и дашборд)
├── Dockerfile               # образ любого сервиса: --build-arg SERVICE=<имя>
├── Makefile                 # dev, check, stack, smoke, certs, docker compose up/ps/down
├── .github/workflows/ci.yml # CI: make check-integration, make stack + make smoke; на main — образы в GHCR и деплой
├── deploy/                  # прод: compose.prod.yaml (поверх compose.yaml), Caddyfile, bootstrap.sh (сервер), deploy.sh
├── scripts/
│   ├── dev.sh               # весь бэкенд локально (make dev)
│   ├── check.sh             # проверки всех модулей, как в CI (make check)
│   ├── check-proto.sh       # сгенерированный protobuf-код соответствует .proto (make check-proto)
│   ├── smoke.sh             # сквозная проверка запущенного стека (make smoke)
│   └── gen-certs.sh         # dev CA, mTLS-сертификаты и JWT-ключи → certs/ (в .gitignore)
├── pkg/                     # ОБЩИЕ модули (каждый — отдельный go.mod)
│   ├── errs/                #   errs.Wrap
│   ├── logger/              #   slog-логгер из конфига
│   ├── hmac/                #   HMAC-хешер
│   ├── envconfig/           #   загрузка конфига: необязательный .env + env + Validate()
│   ├── pgpool/              #   пул PostgreSQL, goose-миграции при старте, транзакции в контексте (TxManager, Conn)
│   ├── pubsub/              #   события подписчикам по ключу (пользователю): в процессе (Hub) и между репликами (Redis)
│   ├── outbox/              #   надёжная доставка другому сервису: запись в транзакции изменения, relay с повторами
│   ├── reqid/               #   ID запроса: контекст, X-Request-ID, gRPC-метаданные, request_id в логах
│   ├── metrics/             #   реестр Prometheus и отдельный порт /metrics
│   ├── ratelimit/           #   счётчики событий в фиксированных окнах: в памяти или в Redis
│   ├── grpcserver/          #   gRPC-сервер: health и Probe, reflection, request ID, метрики, graceful stop, ErrorInterceptor
│   ├── mtls/                #   mTLS между сервисами, идентичность вызывающего, RestrictMethods
│   └── jwtauth/             #   формат JWT, проверка токенов, gRPC-интерсептор аутентификации
├── web/                     # сайт в стиле old web: HTML + CSS + JS-модули без сборки
├── gateway/                 # публичный REST/JSON API (BFF) и раздача web/, единственная точка входа снаружи
├── auth/                    # сервис аутентификации (коды по email, JWT, сессии)
├── user/                    # сервис пользователей (профиль, приватность, подписки, поиск)
├── post/                    # сервис записей: стена, лайки, комментарии
├── media/                   # сервис фото: аватарки и фото записей — проверка, обрезка, хранение, выдача
├── notification/            # уведомления («Мои Ответы»): лайки, комментарии, подписки
├── message/                 # личные сообщения («Мои Сообщения»): диалоги, прочитанное
└── club/                    # сообщества («Мои Группы»): группы, участники, руководство
```

Поток запроса: браузер → `gateway` (страницы из `web/` и HTTP/JSON API на одном origin) → `auth`/`user`/`post`/`media`/`notification`/`message`/`club` (gRPC + mTLS); `auth` → `user`, `post`, `user` и `club` → `notification`, `post` и `message` → `media` (фото опубликованных и удалённых записей, комментариев и сообщений), `post` → `club` (кто модерирует стену группы и кому сообщать о предложенных записях), `user` → `post`/`media`/`message`/`club` (очистка удалённых страниц) (gRPC + mTLS, внутренние RPC). Порты по умолчанию: `auth` 7051, `user` 7052, `post` 7053, `media` 7054, `notification` 7055, `message` 7056, `club` 7057, `gateway` 8080; метрики — на «девятке» с теми же последними цифрами (`METRICS_PORT`: 9051–9057, у `gateway` 9080). Порты сервисов — только ниже 32768: выше начинаются диапазоны, из которых ОС раздаёт порты исходящим соединениям (macOS — 49152–65535, Linux — 32768–60999), и любой процесс может случайно занять такой порт — сервис тогда не стартует с `address already in use` (так было с привычными для gRPC 50051–50056).

Структура одного сервиса (эталон — `user/` и `auth/`):

```
<service>/
├── api/<service>/v1/        # .proto + сгенерированный код (*.pb.go, *_grpc.pb.go)
├── cmd/<service>/main.go    # только точка входа
├── internal/
│   ├── <domain>/            # доменный слой: сущности, value objects, доменные ошибки
│   ├── service/             # прикладной слой (use cases) + DTO + порты (интерфейсы)
│   ├── grpc/                # транспорт: хендлеры + mapper.go (proto <-> домен)
│   ├── postgres/            # реализации репозиториев на PostgreSQL
│   ├── redis/               # реализации на Redis
│   ├── inmem/               # in-memory реализации (dev/тесты)
│   ├── config/              # конфигурация из окружения
│   └── app/                 # composition root: сборка зависимостей, Run/Close
├── migrations/              # goose SQL-миграции + embed.go (встраиваются в бинарник)
├── .env.example
└── Makefile                 # run build test fmt lint tidy proto check migrate-*
```

Новый сервис создаётся копированием этой структуры, добавляется в `go.work` и `compose.yaml` (своя БД на сервис и сам сервис в профиле `app`), в `scripts/dev.sh`, получает сертификат в `scripts/gen-certs.sh`, порт метрик и цель в `monitoring/prometheus.yml` (и в список `services` `scripts/smoke.sh`) и строится на `pkg/grpcserver`, `pkg/envconfig`, `pkg/mtls`.

Docker: один `Dockerfile` на все сервисы (контекст — корень репозитория из-за `go.work` и `pkg/*`): статический бинарник (`CGO_ENABLED=0`, `-trimpath`; Go собирает на платформе сборщика под целевую — `--platform linux/amd64` на Mac с arm64 не эмулирует компилятор) в distroless `static:nonroot`, модули и кеш сборки — в cache mount BuildKit; у `gateway` своя цель `--target gateway` с сайтом в `/web`. `make stack` поднимает весь сайт в Docker на тех же базах, что `make dev-persistent`, с mTLS между сервисами и JWT-ключами из `certs/` (`make certs`), `HASH_SECRET` — в корневом `.env`. Контейнеры работают от имени пользователя, запустившего `make stack` (`FREENET_UID`/`FREENET_GID`): так они читают ключи с правами 600 и пишут фото в `.data/media`. `make smoke` (`scripts/smoke.sh`) регистрирует пользователя и проходит через все сервисы (код входа — из `docker compose logs auth`), затем проверяет наблюдаемость: все контейнеры здоровы, ID запроса из ответа gateway — в строке лога `auth`, Prometheus собирает метрики всех сервисов, видит все базы и Redis через экспортёры, правила алертов загружены и работают, Alertmanager готов, в Grafana есть дашборд и его источник данных отвечает. В образе нет оболочки и curl, поэтому healthcheck — сам бинарник: `HEALTHCHECK` в `Dockerfile` запускает `/service -healthcheck`, который берёт тот же конфиг и спрашивает работающий сервис — gRPC health `Check` по mTLS (`grpcserver.Probe`; сертификат сервиса годится и как клиентский, в нём есть `localhost`) или `GET /healthz` у `gateway`. Поэтому в `compose.yaml` сервисы ждут тех, кого вызывают, `service_healthy`, а `make stack` (`up --wait`) возвращается, когда весь сайт готов.

CI (GitHub Actions, `.github/workflows/ci.yml`) делает то же, что локальные команды: `make check-integration` (gofmt, vet, golangci-lint, `go test -race` во всех модулях `go.work` с интеграционными тестами на временных Postgres и Redis, тесты сайта, конфиги наблюдаемости и `make check-proto`) и `make stack` + `make smoke`. `make check-proto` (`scripts/check-proto.sh`) генерирует protobuf-код каждого сервиса заново во временный каталог, с флагами `make proto`, и сравнивает с закоммиченными `*.pb.go` — изменённый без `make proto` `.proto`, правка кода руками и лишний или пропавший сгенерированный файл роняют проверку; генераторы пишут свои версии в код, поэтому скрипт требует ровно те, которыми код сгенерирован (protoc 34.1, protoc-gen-go v1.36.12, protoc-gen-go-grpc 1.6.2), и говорит, как их поставить. Версии инструментов — Go из `go.work`, golangci-lint и goose — закреплены в workflow и `scripts/check.sh`, генераторов protobuf — в workflow (архив protoc — с контрольной суммой) и `scripts/check-proto.sh`; меняя их, меняй в обоих местах, а после смены генераторов — `make proto` во всех сервисах.

Деплой. Пуш в `main`, прошедший проверки, сразу уходит на сервер: задание `images` собирает образы всех сервисов (у `gateway` — с сайтом) и кладёт их в GHCR (`ghcr.io/vexner67/freenet-<сервис>:<коммит>` и `:latest`, кеш сборки — в кеше GitHub Actions), задание `deploy` (по одному, в порядке пушей — запуски на `main` не отменяют друг друга) копирует `compose.yaml`, `deploy/` и `monitoring/` в `/opt/freenet` на сервере по SSH (пользователь `freenet`, ключ — секрет `DEPLOY_SSH_KEY`, ключ сервера — `DEPLOY_KNOWN_HOSTS`, адрес — `DEPLOY_HOST`) и запускает `deploy/deploy.sh <коммит>`: он записывает коммит в `FREENET_TAG`, тянет образы (токен GHCR — `GITHUB_TOKEN` задания, через stdin, только на этот запуск), проверяет `deploy/Caddyfile` с `.env` сервера (Caddy, который не может его прочитать, уронил бы сайт — так деплой падает раньше, чем что-то перезапустится), делает `docker compose up --wait` (миграции сервисы применяют при старте), перезапускает Prometheus, если его `prometheus.yml` или `alerts.yml` изменились (файл, смонтированный в контейнер, меняется там только при перезапуске — иначе новые правила до сервера не дошли бы), и чистит образы старше трёх дней; в конце CI проверяет `SITE_URL/healthz` (переменная репозитория). Откат — тот же `deploy.sh` с прежним коммитом. На сервере `.env` задаёт `COMPOSE_FILE=compose.yaml:deploy/compose.prod.yaml` и `COMPOSE_PROFILES=app`, так что там просто `docker compose ps|logs|...`. `deploy/compose.prod.yaml` поверх `compose.yaml`: образы из GHCR вместо сборки, наружу опубликован только Caddy (80/443 и 443/udp) — Docker пишет свои правила iptables в обход ufw, поэтому базы, Redis и gateway не публикуются вовсе (`!reset`), а Prometheus, Alertmanager и Grafana — только на 127.0.0.1 (смотреть через `ssh -L 3001:localhost:3001`). Caddy (`deploy/Caddyfile`) — TLS и прокси на gateway: `SITE_ADDRESS` — домен (сертификат Let's Encrypt Caddy получает и продлевает сам) или `:80`, пока домена нет, а `REDIRECT_ADDRESS` (`www.<домен>`) постоянно перенаправляет на него — у сайта один адрес, и вход действует, откуда бы ни пришли; каждому запросу Caddy даёт свой `X-Request-ID`, gateway ему верит (`TRUST_FORWARDED_FOR=true`). Коды входа, пока нет SMTP, — в `docker compose logs auth` (`MAILER=console`) или, с `MAILER=telegram`, в том же чате Telegram, что алерты: `auth/internal/telegram` шлёт боту `sendMessage` «Код входа Freenet для <почта>: <код>» с `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` из `.env` сервера (без них сервис с таким `MAILER` не стартует; токен в ошибки и логи не попадает), а владелец передаёт код человеку сам; для писем — `MAILER=smtp` и `SMTP_*`. Сервер готовит один раз `deploy/bootstrap.sh` (Ubuntu 24.04, от root, повторный запуск безопасен): вход по SSH только по ключу (`PasswordAuthentication no`, root — только по ключу), fail2ban, ufw (22 с ограничением частоты — не больше 6 соединений за 30 с с одного адреса, поэтому для работы с сервером удобно одно переиспользуемое соединение `ControlMaster`; 80, 443), автоматические обновления безопасности, swap на маленькой машине, Docker из его репозитория с ротацией логов, пользователь `freenet` для деплоя, `/opt/freenet/.env` со случайными паролями баз и секретами (и пустыми `TELEGRAM_*` для алертов) и `certs/` (`scripts/gen-certs.sh`) — секреты живут только на сервере.

`gateway` может собирать ответ из нескольких сервисов (стена = профиль из `user` + записи из `post` + профили авторов; лента = подписки из `user` → записи этих авторов из `post` → профили авторов и владельцев стен одним `GetProfiles`), но правил предметной области не придумывает. Исключение — проверка «писать на стену и подписываться можно после заполнения профиля»: без никнейма у человека нет адреса и имени в списках.

Подписки живут в `user`: это связь между пользователями, и только там внешний ключ гарантирует, что подписываются на существующего человека. «Общие друзья» openvk — общие подписки: кого читают и владелец страницы, и вошедший зритель (`ListFollowing` с `common`, зритель — из токена; gateway — `?common=true`, как другие подписки — по `friends_read`); на сайте — блок «Общие подписки» («N общих подписок», «Все», первые шесть) на чужой странице и вкладка «Общие» у страницы подписок.

Фото: `media` хранит файлы, `user` — только `avatar_id` текущего фото. Загрузку собирает gateway: `media.UploadAvatar` → `user.SetAvatar` → `media.DeleteAvatars` с сохранением нового (старое удаляется лишь после того, как профиль указывает на новое). Путь к фото содержит ID пользователя, поэтому чужой `avatar_id` в своём профиле даёт лишь битую картинку. URL фото меняется с каждым новым фото — ответы кешируются навсегда (`immutable`). Изображения из загрузки всегда перекодируются (EXIF с геолокацией не сохраняется); размеры проверяются по заголовку до распаковки (защита от «пиксельных бомб»). Телефон хранит снимок так, как его видела матрица, и лишь помечает в EXIF, как его повернуть (`Orientation`) — `imaging.Picture` читает эту метку из JPEG (свой разбор APP1 на несколько десятков строк, каждое смещение проверяется) и отдаёт картинку стоящей прямо: масштабируются исходные пиксели, а поворачивается уже маленький результат, иначе поворот 50-мегапиксельной загрузки стоил бы сотни мегабайт.

Фото в записях: до 10 на запись, запись может состоять из одних фото (`post.Content` — текст, фото или оба, но не пусто; то же правило — `CHECK` в БД). Фото загружается в `media` до публикации (`POST /api/v1/me/photos`), запись хранит только ID. `post` не знает, чьи это фото, поэтому перед `CreatePost` gateway спрашивает у `media` `ListOwnPhotos` и отказывает при чужом/несуществующем ID; путь к файлу содержит ID автора, так что даже без проверки чужое фото дало бы лишь битую картинку. Загрузка ждёт своей записи в `<MEDIA_DIR>/uploads`: опубликованную запись `post` в той же транзакции записывает в outbox (поток `media`, `mediaclient`) — внутренний `PublishPhotos` (только для mTLS-идентичностей `post`, `message` и `gateway` — фон страницы человека) переносит фото в `<MEDIA_DIR>/photos` одним `rename`; удалённую — `DeletePublishedPhotos` с автором записи, кто бы её ни удалил (автор, владелец стены, очистка страницы). Так же устроены фото комментариев (`post`) и сообщений (`message`, свой outbox и своя копия `mediaclient` — сервисы не делят код, кроме `pkg/*`): до 10, текст, фото или оба, но не пусто (`CHECK` в БД), gateway проверяет их у `media` перед `CreateComment`/`SendMessage`. Комментарий уносит свои фото, удаляясь сам, с записью (`DeleteByPost` сначала берёт запись `FOR UPDATE`: комментарий, написанный в это время, ждёт и падает, а не исчезает каскадом незамеченным с фото) и при очистке страницы; сообщения удаляются только очисткой — она стирает и фото собеседников из диалогов стёртого. Сайт показывает фото комментария и сообщения той же сеткой, что у записи, только меньше; в списке диалогов и в «Ответах» вместо пустого текста — «Фотография», как во ВКонтакте. Фото, которое за `UNPUBLISHED_PHOTO_TTL` (по умолчанию сутки) не попало в запись, `media` убирает сам (раз в `PHOTO_CLEANUP_INTERVAL`, возраст — из UUIDv7 фото); такой ID gateway уже не примет (`photo not found`). Убирает — не удаляет, а откладывает в `<MEDIA_DIR>/retired` (`PhotoStore.Retire`): для владельца фото больше нет (`Load`, `Existing`, `Copy` его не находят), но запись могла быть опубликована, а весть об этом — опоздать (outbox её сервиса стоял), поэтому `PublishPhotos` ищет фото и среди отложенных и возвращает его одним `rename`. Совсем отложенное фото удаляется через `RETIRED_PHOTO_TTL` после загрузки (по умолчанию 30 дней, не короче `UNPUBLISHED_PHOTO_TTL` — иначе сервис не стартует; `DeleteRetired`), а удалённые запись и страница забирают и отложенные фото. Публикация и удаление идут одним потоком — по порядку. Без `MEDIA_SERVICE_ADDR` у `post` фото записей считаются неопубликованными и удаляются — предупреждение при старте. В отличие от аватарки фото не обрезается: оно уменьшается целиком с сохранением пропорций (до 1280 и 640 по длинной стороне) и никогда не увеличивается. Чтение загрузки (сначала заголовок — защита от «пиксельных бомб») и запись JPEG без метаданных — общий пакет `media/internal/imaging`.

Записи на чужой стене: у записи есть автор (`author_id`) и стена (`wall_id`, ID владельца); на своей стене они совпадают. Стена (`ListPosts`, «N записей») — по `wall_id`, лента — по `author_id` и по `wall_id`: в ленте видно, что человек написал и у себя, и у других, и что другие написали на его стене (как в openvk, где лента — стены подписок) и на стене читателя. Кто может писать на стену, решает её владелец — настройка приватности `wall_write` в `user` («Кто может писать у меня на стене», как в openvk): `everyone`, `following` (те, на кого владелец подписан; по умолчанию — так незнакомцы не пишут на новую стену) и `only_me`. Друзей у нас нет: «Друзья» openvk — это подписки владельца. Правило — `user.CanPostOnWall` в домене `user`, там же подписки; `post` пользователей не знает, поэтому перед `CreatePost` с `wall_id` gateway спрашивает `user.CanPostOnWall` (как с фото у `media`) и отказывает `403 you cannot post on this wall`. Запись удаляет её автор или владелец стены; комментарий — его автор, автор записи или владелец стены. Владельцу стены о чужой записи приходит уведомление `wall_post`. Сайт показывает форму, если первая страница стены пришла с `canPost`; в ленте у записи на чужой стене — «написал на стене Петра Петрова» (имя в родительном падеже склоняет `genitiveName` из `labels.js`), на странице записи — «Владелец » Стена » Запись», как в openvk. Стена — как в openvk: над записями «Стена», «N записей» и «Все» — ссылка на стену отдельной страницей (`/wall/<никнейм>`, у группы `/club/<адрес>/wall`; никнейм `wall` зарезервирован) с вкладками «Все записи», «Записи Анны» (у группы — «Записи сообщества») и «Чужие записи»: `ListPosts` с `filter` (`post.WallFilter`; своя запись — автора-владельца на своей стене или «От имени сообщества» на стене группы, `Post.ByWallOwner`; gateway — `?type=owner|others`), `total` считает вкладку; закреплённая запись первой — только во «Всех записях», на других вкладках она на своём месте, форма — тоже только там.

Репосты («Поделиться», как в openvk): репост — обычная запись на стене того, кто делится, с `repost_of` (ID записи, которой поделились) и необязательным комментарием — словами и фото (до 10, как у записи: gateway проверяет их у `media`, `post` публикует и кладёт в «Фотографии со стены»; правка репоста меняет и их); `post.Content` — текст, фото, репост или их сочетание, но не пусто (то же правило — `CHECK` в БД). Отдельный RPC `RepostPost`, всегда на свою стену; лимит частоты — тот же `RATE_LIMIT_POSTS`, счётчик свой. Счётчик `repost_count` меняется тем же SQL-запросом, что вставляет или удаляет репост (CTE); репост записи, которой уже нет, не создаётся (`NotFound`). Внешнего ключа нет: репост переживает исходную запись и показывает «Запись удалена.». Репост без своих слов не делится сам — делятся его исходной записью (`post.Shared`), чтобы не плодить пустые вложенные цепочки; репост со своим комментарием делится сам, а сайт показывает в нём ссылку «Открыть запись» вместо второго уровня вложенности. Автору исходной записи приходит уведомление `repost`, его `post_id` — сам репост, поэтому удалённый репост забирает уведомление через `ForgetPost`, а удалённая исходная запись — уведомления о своих репостах (`forgetReposts`: `Retract` на каждый из последних 1000, в транзакции удаления). «Кто поделился» — публичный `ListReposts`: записи-репосты, новые первыми (keyset по ID, частичный индекс по `repost_of`), без архивных, `total` — счётчик; gateway — `GET /posts/{id}/reposts` страницей записей с авторами (группа — у репоста от её имени); на сайте над «Поделиться» — та же подсказка, что над сердечком: «Поделились N человек», шесть фото и окно со всеми, каждый ведёт к своему репосту (`likers.js` со списком `sharers` из `posts.js`). Вложенные записи gateway подтягивает одним `GetPosts`, а профили всех людей страницы — `GetProfiles` пачками по 100. Окно «Поделиться» openvk: «на стену», «в группу» (группы, которыми человек управляет, с «От имени сообщества» и «Подписью автора»; права проверяет gateway, как у записи на стене группы, и передаёт `RepostPost` стену, `from_wall` и `signed`; автор исходной записи слышит о репосте от имени группы) и «в переписку» — сообщение с вложенной записью (`message.Content.post`, колонка `post_id`; сообщение — текст, фото или запись, `CHECK` в БД; gateway проверяет, что запись есть, и показывает её в диалоге, отправке и живых событиях как вложение репоста, удалённую — «Запись удалена.», а в списке диалогов вместо текста — «Запись»). Так же «в переписку» уходит фото альбома: `message.Content.sharedPhoto` (колонка `shared_photo_id` без внешнего ключа, `NewPhotoShare`; только со словами — с фото, записью и пересланными `ErrSharedPhotoAlone` → `InvalidArgument`; пересылка несёт его дальше), gateway (`albumPhoto` в теле отправки) пускает только фото, которое отправитель видит (`photo not found`), и показывает его, как в записи (`sharedPhoto`, удалённое — «Фотография удалена.»), а список диалогов пишет «Фотография». «Понравилось N людям» (openvk): публичные `ListPostLikers`, `ListCommentLikers` и `ListAlbumPhotoLikers` — кто лайкнул, новые первыми, keyset по (`created_at`, `user_id`) с индексами, `total` — счётчик; gateway — `GET /posts|comments|album-photos/{id}/likes` списком людей; на сайте над сердечком с лайками через 400 мс появляется подсказка с числом и шестью фото, а её заголовок открывает окно со всеми и «Показать ещё» (`likers.js`).

Опросы (openvk «Новый опрос») живут в `post` рядом с записью: запись задаёт не больше одного опроса, и опрос известен по ID своей записи (`post.Poll`, таблицы `polls` с ключом `post_id` и `ON DELETE CASCADE`, `poll_options` — до 10 вариантов (`post.MaxPollOptions`, как `polls.max-opts` openvk) с местом от 0 и счётчиком `vote_count`, `poll_votes`). Тема и вариант — одна строка до 128 символов (`post.PollLine`); опрос бывает анонимным, с множественным выбором, с запретом отменять голос (`locked`) и со сроком — от 1 до 31 дня, 0 — бессрочно (`PollDraft.Days`, `ends_at`). Опрос — тоже содержимое: запись с ним может не иметь ни текста, ни фото (`post.NewPolled`, колонка `posts.polled`, `CHECK` в БД), а правка меняет слова и фото и опрос не трогает (текст может стать пустым). Задаётся опрос только новой записью — `CreatePost.poll` на своей и чужой стене и на стене группы; у репоста, предложенной записи и записи о новом фото его нет. Запись и опрос сохраняются в одной транзакции. Сами опросы читаются отдельно от записей: запись говорит `polled`, а публичный `GetPolls` (до 100 записей, `service.MaxPollBatch`) отдаёт опросы тех из них, что видны зрителю (опрос архивной записи — только тем, кто ведёт архив), с выбором зрителя, если пришёл токен. Голос — `VotePoll` (места вариантов: одно, а при множественном выборе — несколько, `Poll.Choice`), один раз: второй — `ErrPollVoted`, сначала голос надо забрать (`RetractPollVote`; не голосовал — `ErrPollNotVoted`, запрещено — `ErrPollLocked`), по окончании срока — `ErrPollEnded`; всё это `FailedPrecondition`/409, неверный выбор — `InvalidArgument`. Голос и его отмена идут в транзакции, которая сначала берёт строку опроса `FOR UPDATE` — голоса одного опроса идут по очереди, — а счётчики вариантов и `voter_count` (сколько человек, а не голосов) меняет тот же SQL-запрос, что вставляет или удаляет голоса. Голосовать может тот, кому видна запись (`PollService.checkSeen`, как лайк), чёрный список не мешает; лимит частоты — как у лайков, счётчики свои; о голосах никого не уведомляют. «Список проголосовавших» — публичный `ListPollVoters` по варианту, новые первыми, keyset по (`created_at`, `user_id`), `total` — счётчик варианта; у анонимного опроса — `ErrPollAnonymous` (409). Очистка страницы забирает её голоса со счётчиками (`PollRepository.DeleteByUser`). Gateway: `poll` в теле `POST /users/{nickname}/posts` и `/clubs/{ref}/posts` (правка с ним — 400), запись и вложенная запись репоста отдают `poll` (тема, варианты с голосами, `voters`, `anonymous`, `multiple`, `locked`, `endsAt`, `ended`, `voted` — места, выбранные зрителем) — опросы страницы gateway берёт одним `GetPolls` (стена, лента, страница записи, репосты, запись в сообщении); `PUT`/`DELETE /posts/{id}/poll/vote` отвечают опросом, `GET /posts/{id}/poll/voters?option=` — людьми, как лайкнувшие. На сайте (`poll.js`) — блок openvk под словами записи: тема, варианты (радио — щелчок голосует сразу; галочки и «Проголосовать!» при множественном выборе; гостю — неактивные), а проголосовавшему и после срока — результаты полосами с числом голосов и процентом от проголосовавших (выбранное — жирным, название ведёт к списку проголосовавших) и «Отменить голос»; под ними «В опросе проголосовало N человек.» и курсивом «Публичное голосование • много вариантов • нельзя переголосовать • до …». В форме записи (стена, группа, лента) — «Прикрепить опрос»: окно «Новый опрос» с «Темой опроса», вариантами («Добавить вариант ответа...», Backspace в пустом удаляет, Enter/Tab в последнем добавляет), галочками «Анонимный опрос», «Множественный выбор», «Запретить отменять свой голос», «Голосование истекает через: N дней» и кнопкой «Прикрепить», после которой под полем стоит «Опрос: тема ×».

Редактирование и закрепление записей — как в openvk. Свою запись автор правит неделю после публикации (`post.Edited`: только автор и до `EditableUntil`, иначе `ErrCannotEdit` → 403 и `ErrEditExpired` → `FailedPrecondition`/409): `EditPost` заменяет текст и фото целиком, как при публикации (gateway так же проверяет фото у `media`), репост меняет только свои слова и остаётся репостом той же записи. Запись не изменяется на месте — `Edited` возвращает новую, потому что читатели (`inmem`) держат указатели. Фото, которые правка добавила, `post` публикует, а убранные удаляет — в той же транзакции через outbox `media`. Запись хранит `edited_at`, сайт пишет после даты «(ред.)», а правит запись на месте (`postedit.js`): текст и фото уступают место форме с «Сохранить»/«Отмена». Лимит частоты — `RATE_LIMIT_POST_EDITS`. Закрепляет запись владелец стены, чья бы она ни была (`CanBePinnedBy`); на стене закреплена одна запись — таблица `pinned_posts` с ключом по стене, так что закрепить другую — один `INSERT ... ON CONFLICT` без гонки, а удалённая запись уносит закрепление каскадом. `ListPosts` отдаёт закреплённую первой на первой странице, сверх `limit`, и пропускает её дальше; запись показывает «, закреплено» после даты. Ссылки «Редактировать», «Удалить», «Закрепить»/«Открепить» — в подвале записи, в порядке openvk. «Архив записей» openvk: владелец стены (администраторы группы — `post` спрашивает `club.CanModerateWall`, правило `Post.OnWallOf`) убирает запись в архив и возвращает её (`ArchivePost`/`UnarchivePost`, колонка `archived`; архивация тем же SQL-запросом снимает закрепление). Архивную запись видят только они: стена, вкладки, счётчик «N записей» и лента её пропускают (`WallFilter.Matches`, `AND NOT archived`), `GetPost` другим отвечает «не найдено», `GetPosts` (вложенные записи репостов, уведомления) её не отдаёт, комментировать её может только владелец; читается она вкладкой «Архив записей» (`WallFilter` `archive`, чужим — `ErrCannotArchive` → 403), а лайкнуть её и поделиться ею (и репостом, который её несёт) другие не могут — «не найдено», как у `GetPost` (`PostService.seen`; лайк, поставленный раньше, снять можно). Архив читается по годам, как в openvk: `ListPosts` с `year` (`post.WallYear`, год записи в UTC, 0 — все; с годом закреплённая запись стоит на своём месте), годы стены — все, что есть у её записей, архивных и нет, новые первыми (`ListWallYears`, только тем, кто ведёт архив), а «Архивировать все записи за 2025», «Разархивировать все записи за 2025» и «Архивировать все записи целиком» — `ArchiveWall` (стена, год или 0, куда): один SQL-запрос переносит записи и снимает закрепление, отвечает, сколько перенёс. «Поиск» по стене — `ListPosts` с `query` (`post.WallQuery`, до 100 символов: подстрока текста без учёта регистра, `ILIKE` с экранированными `%` и `_`; закреплённая запись в поиске стоит на своём месте, `total` считает найденное). Владелец стены может закрыть комментарии записи (`CloseComments`/`OpenComments`, колонка `comments_closed`): новые не принимаются ни от кого (`ErrCommentsClosed` → `FailedPrecondition`/409), написанные остаются. Лимит всех четырёх — как у правок. Gateway: `PUT`/`DELETE /posts/{id}/archive` и `/posts/{id}/closed-comments`, стена — `?type=archive`, `?q=` и `?year=`, первая страница архива несёт `years`; `PUT`/`DELETE /users/{nickname}/posts/archive` и `/clubs/{ref}/posts/archive` с необязательным `?year=` — весь год или вся стена, ответ — `changed`; запись отдаёт `archived` и `commentsClosed`. На сайте — «Архивировать»/«Разархивировать» и «Закрыть комментарии»/«Открыть комментарии» в подвале записи у владельца стены, «, в архиве» и «, комментарии закрыты» после даты, вкладки «Архив записей» (с плашкой openvk «Это архив записей» и его полосой под ней: «Все годы», годы стены — дальше шестого под «Ещё», — `?type=archive&year=`, и справа меню «Действия» с тремя действиями и окном подтверждения, после которого открывается архив этого года; раскладка годов — `archiveYears` в `labels.js`) и «Поиск» (`?type=search&q=`, обычная GET-форма; найденное в тексте записей подсвечено — `found` у `postNode` и `textNode`, те же `foundParts`, что в сообщениях) на странице стены, а на странице записи вместо формы — «Комментарии к этой записи закрыты.».

Сообщества («группы» openvk) — сервис `club`: группа (`club.Club`: название до 64 символов, описание, необязательный адрес, «Сайт» — ссылка http/https, `https://` дописывается, если схему не указали, как в openvk, — стена `open`/`suggest`/`closed` («Открытая», «Предложка», «Закрытая» openvk) и «Список админов» `creator`/`all`/`none`), её участники (`club_members`, счётчик `member_count` меняется тем же SQL-запросом, что добавляет или убирает участника) и роли: создатель — владелец (`owner`, один на группу — частичный уникальный индекс; выйти не может), им назначенные администраторы (`admin`) и участники (`member`). Правила — в домене: правят группу и пишут «От имени сообщества» администраторы и владелец (`Role.Manages`), назначает их только владелец (`CheckAppoint`), он же передаёт группу одному из администраторов и сам остаётся администратором (`TransferClub`, «Назначить владельцем» openvk, `CheckTransfer`; роли меняются в одной транзакции — сначала владелец становится администратором, потом администратор владельцем, иначе частичный уникальный индекс увидел бы двух владельцев; второй одновременный перенос ждёт строку владельца и не находит его), на открытой стене пишет любой (как «Открытая» в openvk, даже не участник), на остальных — только администраторы и только от имени группы (`CanPostOnWall`; gateway сам ставит `from_wall`, как openvk), а на «Предложке» остальные предлагают записи (`CanSuggest`, ответ `suggest` у `CanPostOnWall`). Предложенные записи («Предложка» openvk) живут в `post` отдельной таблицей `suggestions` (`post.Suggestion`: текст, фото или оба, не репост), поэтому стена, лента и счётчик их не видят: видят только автор («Предложенные вами записи», `ListSuggestions` с `mine`) и администраторы («Предложенные записи», `post` спрашивает `club.CanModerateWall`). Фото публикуются в `media` сразу при предложении — запись может ждать дольше, чем `media` хранит неопубликованные. «Опубликовать запись» (`PublishSuggestion`, администратор правит текст и ставит «Подпись автора») в одной транзакции удаляет предложение (уже опубликованное или отклонённое — `NotFound`, дважды не опубликуется) и создаёт новую запись от имени группы с новым ID и датой — она встаёт наверх стены; это запись группы (`post.suggested`): автор её не правит и не удаляет, как «Вы не можете удалить ваш принятый пост» openvk, `mine` ему не говорят. Автору приходит уведомление `post_accepted` от имени группы (актор — ID группы; «Сообщество Кошки опубликовало вашу предложенную запись»). Администраторам о каждом новом предложении приходит `suggested_post` от имени группы («В сообществе Кошки новые записи в предложке» openvk, ссылка — на «Предложенные записи»): кому, `post` спрашивает у внутреннего `club.ListWallModerators` (владелец и администраторы, до 100), а `post_id` уведомления — ID предложения, поэтому gateway не ищет его среди записей; опубликованное, отклонённое, удалённое автором и стёртое с его страницей предложение забирает эти уведомления (`ForgetPost` с ID предложения). «Отклонить» и удаление своего предложения (`DeleteSuggestion`) уносят его фото. Очистка страницы удаляет и её предложения. Страница группы — `/club/<адрес>`, без адреса — `/club/<id>`, как `/club123` openvk; адрес — как никнейм (латиница, цифры, `_`, буква первой, поэтому ID с адресом не спутать), уникален без учёта регистра (индекс по `lower(address)`). Общего пространства адресов с никнеймами нет: уникальность пришлось бы держать в двух базах. Стена группы живёт в `post`: `wall_id` — ID группы, `post` не знает, чья это стена. Запись «От имени сообщества» хранит `from_wall`: автор (`author_id`) правит её неделю, как свою, но читателям gateway показывает автором группу (`author.club`), а `post` говорит только самому автору `mine`; такие записи не уведомляют автора (`post.Notified` — никто), не попадают в ленту по автору (только по стене) и не проверяют чёрный список автора при комментарии — иначе отказ выдал бы, кто писал. Так же администраторы комментируют записи на стене группы «От имени сообщества» (галочка под формой комментария, как в openvk): комментарий хранит `from_wall` (`Comment.ForWall`), gateway проверяет право у `club.CanPostOnWall` с `from_club` и показывает автором группу (фото остаются под автором), `post` говорит автору `mine`; уведомления о таком комментарии приходят от группы (актор — ID группы, «Сообщество Кошки оставило комментарий»), а ответы на него и его лайки никого не уведомляют (`Comment.Notified` — никто). Кто может писать, gateway спрашивает у `club.CanPostOnWall` (как у `user` для стен людей) и передаёт в `CreatePost` `club_wall` (владельца стены не уведомлять) и `from_wall`; удалять и закреплять чужие записи и комментарии на стене группы `post` разрешает сам, если запрос не прошёл его собственные правила, спросив внутренний `club.CanModerateWall` (`clubclient`, только для mTLS-идентичности `post`; для стены человека — «нет»). Лента («Мои Новости») — записи подписок и читателя и все записи на их стенах и на стенах групп, где состоит читатель (`ListMyClubIDs`, до 1000 последних; `ListFeed` с `author_ids` — до 1001 — и `wall_ids` — до 2001: люди и группы). Записи тех, кто у читателя в чёрном списке, лента не показывает, на чьей бы стене они ни были, и «Все новости» тоже: gateway берёт у `user` `ListBlockedIDs` (с токеном, до 1000 новейших) и передаёт `ListFeed` в `hidden_author_ids` (`FeedSources.Hidden`, `AND NOT (author_id = ANY(...) AND NOT from_wall)`); запись «От имени сообщества» остаётся — иначе пропажа выдала бы, кто писал. Над лентой, на обеих вкладках, — форма новой записи, как в openvk: запись идёт на свою стену и встаёт первой (`initForm` в `feed.js`; без заполненной анкеты формы нет). «Все новости» openvk (`/feed/all`, вкладки «Мои новости» и «Все новости» над лентой) — записи всех, на кого бы читатель ни был подписан: `ListFeed` с `everyone` (gateway — `GET /feed?type=all`, без подписок и групп) отдаёт записи всех стен, как openvk по умолчанию (без «Показывать посты на чужих стенах» — только то, что стены говорят сами, см. «Настройки ленты»), без архивных и, если читатель так настроил, без NSFW; читается вниз по первичному ключу. В ленте запись несёт те же ссылки, что на стене (`feed.js`): «Редактировать» и «Удалить» у своей, «Удалить», «Закрепить», «Архивировать» и «Закрыть комментарии» у записей своей стены и стен групп, которыми читатель управляет (gateway спрашивает у `club` роли читателя в группах страницы одним `ListMyRoles` — до 100 групп, только те, где он состоит, — и помечает такие записи `moderated`); удалённая и убранная в архив запись уступает место строке «Запись удалена.»/«Запись перенесена в архив.». Авторов и стены страницы gateway ищет сначала среди людей (`GetProfiles`), остальные ID — среди групп (`GetClubs`, пачками по 100). Фото группы хранит `media` под ID группы и отдаёт как аватарку (`/media/avatars/<club>/...`): загрузку собирает gateway — проверяет у `club`, что вызывающий администратор, вызывает внутренние `media.UploadClubAvatar`/`DeleteClubAvatars` (только для mTLS-идентичности `gateway`, токен идёт с ними — по нему лимит), затем `club.SetClubAvatar` (правило — `Club.WithAvatar`), и лишь потом удаляет старое фото, как у людей. «Фон страницы» группы (openvk) — два фото по бокам страницы: левое и правое (`club.Club.backdrop`, колонки `backdrop_left`/`backdrop_right`, каждая сторона меняется своим `UPDATE`, чтобы два администратора не затёрли друг друга, `Club.WithBackdrop`); файлы — фото группы в `media` под её ID (внутренние `UploadClubPhoto` — сразу опубликованное, — и `DeleteClubPhotos` с оставляемыми ID, только для mTLS-идентичности `gateway`, лимит — как у аватарок), раздаются как фото записей (`/media/photos/<club>/...`). Gateway (`PUT /clubs/{ref}/backdrop/{left|right}`, `DELETE /clubs/{ref}/backdrop` — обе стороны, как «Удалить фон» openvk) загружает картинку, ставит её стороной у `club` и удаляет фото группы, которые она больше не показывает. Сайт рисует фон, как openvk: неподвижный слой за страницей, картинки по высоте экрана слева и справа, белая колонка с мягкими краями посередине (`showBackdrop` в `club.js`, картинки — через CSSOM, CSP запрещает только `style=""`); настройки — вкладка «Фон» со схемой страницы и «Обзор» на каждой стороне. Фото человека и группы загружается окном openvk «Загрузка новой фотографии» (`avatar.js`): квадрат выбирают и картинку поворачивают на canvas в браузере, и на сервер уходит уже вырезанный квадрат (до 800×800), как в openvk, — `media` ничего об обрезке не знает. С «Опубликовать запись на стене» (`?onWall=true`) gateway сначала загружает ту же картинку как фото записи (отказ `media` ничего не меняет), а после смены фото создаёт запись `avatar_update` (`post.NewAvatarUpdate`: одно фото и ничего больше — `CHECK` в БД; на своей стене — запись человека, «обновил(а) фотографию на своей странице», на стене группы — от её имени, «обновило фотографию группы»; не редактируется — `EditableUntil` равен дате записи); без заполненной анкеты записи нет, а отказ в записи (лимит частоты) приходит ошибкой, хотя фото уже сменилось. Поиск групп (`SearchClubs`, `/search?section=groups`) — как поиск людей: каждое слово `LIKE '%слово%'` по названию и адресу с триграммным индексом. Руководители группы дают друг другу должность и скрывают друг друга, как в openvk («Изменить комментарий» и «Скрыт: Да/Нет»): у членства есть `title` (до 36 символов в одну строку, `club.Title`) и `hidden` — только у владельца и администраторов (`CHECK` в БД), вместе это `club.Seat`. Меняют их владелец и администраторы друг другу, владельцу тоже (`CheckDescribe`, `DescribeMember`, `PATCH /clubs/{ref}/admins/{nickname}` — оба поля сразу; не руководителю — `ErrNotManager` → `FailedPrecondition`/409), снятый администратор теряет и то и другое тем же `UPDATE`. Скрытого руководителя видят руководителем только другие руководители (`Seat.Shown`): остальным он обычный участник без должности, его нет во вкладке «Руководство» и в счётчике администраторов (`ListMembers` публичный, но смотрит на токен), а скрытого владельца `GetClub` им не называет (`owner_id` пуст); стену он модерирует по-прежнему (`ListWallModerators` — все). Должность владельца — `owner_title`. О назначении администратором человек узнаёт уведомлением `club_admin` от имени группы («Вас назначили руководителем сообщества Кошки»; в openvk — «… назначил вас руководителем сообщества …»): `club` записывает его в свой outbox (поток `notification`, `notifyclient`, `TxManager`) в одной транзакции со сменой роли, а снятие забирает уведомление (`Retract`); без `NOTIFICATION_SERVICE_ADDR` у `club` назначение никого не уведомляет. От назначения администратором человек получает то же, что в openvk: группа появляется во вкладке «Управляемые» «Моих Групп» (`ListMyClubs` с `managed`), её можно «Добавить в левое меню» (`PinClub`, флаг `pinned` у членства, не больше `club.MaxPinned` = 10 — проверка тем же `UPDATE`; показываются только группы, которыми человек ещё управляет), и он правит группу, ставит фото, пишет от её имени и следит за стеной. Запись «От имени сообщества» может нести «Подпись автора» (`signed`, только вместе с `from_wall` — `CHECK` в БД): тогда gateway отдаёт автора в `signer`, и сайт пишет под текстом «Автор: Иван Иванов» со ссылкой, как openvk; на закрытой стене и «Предложке» администраторы, как в openvk, пишут только от имени группы (gateway ставит `from_wall` сам). Чьи группы видно: блок «Группы» на странице человека и его список (`/groups?u=<никнейм>`) отдаёт `club.ListUserClubs` (публичный, только группы — без ролей и меню; вошедшему gateway добавляет к каждой его `role` тем же `ListMyRoles`, и в чужом списке у группы стоит «Вступить в группу» или «Выйти из группы», у встречи — «Я приду» и «Я не приду»), а можно ли их видеть, gateway спрашивает у `user.GetAccess` — настройка `clubs_read` («Кому видно мои группы» openvk: `everyone` по умолчанию, как там, `users`, `following`, `only_me`, правило — `User.ClubsVisibleTo`, см. «Приватность страницы»). Сами группы показывают участников при любой настройке, как в openvk. Лимиты частоты: создание групп, правка настроек и фото, передача группы, вступление; предложение и публикация записи — `RATE_LIMIT_POSTS`, у каждого свой счётчик. При очистке страницы `club` (поток `club` outbox `user`) убирает человека из всех групп; группа, которой он владел, достаётся тому, кто в ней дольше всех: из администраторов, а без них — из всех участников (`MemberRepository.DeleteByUser`: в одной транзакции уходят членства и наследник становится владельцем — он «придёт точно» на встречу, как любой владелец); без владельца остаётся только группа, в которой больше никого нет. На сайте — «Мои Группы» (`/groups`: вкладки «Группы» и «Управляемые» (`?act=managed`), серая полоса с «Поиском по группам» и «Создать группу» → `/groups/create`, «Вы состоите в N группах», группы списком openvk — фото, «Название», «Размер», описание и справа «Просмотр группы», «Добавить в левое меню»/«Удалить из левого меню», «Выйти из группы»; общий `clubs.js`), закреплённые группы — в левом меню под чертой (приходят с `GET /me` полем `pinnedClubs`: gateway спрашивает их у `club` одновременно с `user.GetMe`, а сбой `club` меню не ломает — поля просто нет; `showPinnedClubs` перечитывает их после «Добавить в левое меню»), страница группы (`club.js`, раскладка openvk, зеркальная странице человека: слева «Информация» с «Сайтом», «Участники» и стена с «От имени сообщества» и «Подпись автора» для администраторов, справа фото с «Загрузить фотографию» для них, «Вступить в группу»/«Выйти из группы», «Редактировать группу», «Тип группы» и, как велит «Список админов», «Создатель», «Администраторы» (сколько, «Все» и первые пять, владелец первым) или ничего), настройки (`/club/<адрес>/edit`: название, описание, адрес страницы, сайт, стена, список админов) и участники (`/club/<адрес>/members`, вкладка «Руководство», у владельца «Назначить администратором»/«Снять полномочия администратора» и у администраторов «Назначить владельцем» с окном openvk «Передача прав владельца»), над стеной — ссылка openvk «N предложенных записей» администраторам и «N предложенных вами записей» автору, форма «Предложить новость» на «Предложке» (после неё — свои предложенные записи, как в openvk), страница предложенных записей (`club-suggested.js`: «Опубликовать запись» с окном «Публикация предложенной записи» и «Отклонить» у администраторов, «Удалить» у автора); на странице человека — блок «Группы» openvk (сколько, «Все», названия через «•»); вместо аватарки — камера, как в openvk. Запись группы подписана «Кошки опубликовали» (openvk «post_writes_g»), запись участника на её стене — «Пётр написал в Кошки» (openvk «в $1»). На вкладке «Руководство» у руководителей — «Изменить комментарий» (окно openvk «Изменить комментарий к администратору») и «Скрыт: Да/Нет», под ролью — «Комментарий: …», а на странице группы должность стоит под именем создателя и администраторов.

Встречи («Встречи» openvk) — те же группы другого вида: `club.Club.kind` = `event` с расписанием (`club.Schedule`: начало обязательно, окончание — позже начала или никакого; колонки `kind`, `starts_at`, `ends_at`, правило — `CHECK` в БД). Всё, что умеет группа, умеет и встреча, по тем же RPC и адресам: стена, руководство, обсуждения, альбомы, фон, лента. Создаёт её `CreateEvent` («Создать встречу», `POST /events`; лимит — как у групп, счётчик свой), даты правятся вместе с настройками (`UpdateClub` с `starts_at`/`ends_at`: встреча не может остаться без начала, группе они не нужны). Участник встречи придёт точно («Я приду») или возможно («Возможно приду»): `maybe` у членства (`JoinClub` с `maybe`, `PUT …/membership?maybe=true`), и только пока встреча не началась — начавшуюся openvk считает прошедшей (`Club.JoinsAsMaybe`); вступивший меняет ответ, вступая снова с другим (тот же `JoinClub`: один SQL-запрос меняет `maybe` и счётчик, новую строку от изменённой отличает `xmax`; владелец всегда придёт точно) — на странице встречи участнику вторая кнопка предлагает другой ответ («Я приду» тому, кто «возможно», и наоборот). Сколько «возможно», считает `maybe_count` в строке группы тем же SQL-запросом, что добавляет или убирает участника; «Точно придут» — остальные. `ListMembers` с `going` (`?going=sure|maybe`) отдаёт один из списков, `total` считает его. Списки человека различают вид: `ListMyClubs` и `ListUserClubs` с `kind` — «Мои Группы» и блок «Группы» показывают только группы, «Мои Встречи» (`GET /me/events`) — только встречи; меню, лента и поиск вида не различают. Списки встреч различают и время (`club.Period`, `period` у `ListMyClubs` и `ListUserClubs`; gateway — `?time=upcoming|past`): встреча прошла, когда закончилась или, не имея окончания, началась (`Schedule.Over`), остальные — предстоящие; `total` считает выбранные. Напоминание openvk «В ближайшее время состоится событие …»: раз в `EVENT_REMINDER_INTERVAL` (5 минут) `club` (`service.ReminderService`) берёт встречи, которые начнутся в ближайшие `EVENT_REMINDER_AHEAD` (сутки) и о которых ещё не напоминали (`clubs.reminded_at`, `FOR UPDATE SKIP LOCKED` — реплики не мешают друг другу, частичный индекс по `starts_at`), и в той же транзакции, что ставит отметку, записывает в outbox уведомление `event_reminder` от имени встречи каждому её участнику, точному и «возможно» (до `service.MaxReminded` = 1000 последних); перенесённая встреча (`UpdateClub` с другим началом сбрасывает отметку тем же `UPDATE`) напоминает о себе снова — прежнее напоминание забирается (`Retract`) перед новым, так что оно одно и снова непрочитанное. Без `NOTIFICATION_SERVICE_ADDR` напоминаний нет. В «Ответах» — «В ближайшее время состоится событие Название.» со ссылкой на встречу. Встречи человека видны другим так же, как его группы (`GET /users/{nickname}/events`, по `clubs_read` — в openvk у обоих блоков одна настройка). На сайте — «Мои Встречи» в левом меню (`/events`, та же страница, что «Мои Группы»: вкладки «Встречи» — предстоящие, — «Прошедшие» (`?act=past`) и «Управляемые», «Создать встречу», «Вы участвуете в N встречах», в строке встречи — «Начало» и «Окончание»), «Создать встречу» (`/events/create`: название, описание, «Начало» — дата и время, «Указать дату окончания»), а страница встречи — страница группы с «Началом» и «Окончанием» в «Информации», блоками «Точно придут» и «Возможно придут», кнопками «Я приду» и «Возможно приду» («Добавить в список», когда началась; участнику — «Я не приду»), «Типом встречи» и «Организатором», который показан всегда; у страницы участников — вкладки «Точно придут», «Возможно придут» и «Руководство», в настройках — те же поля дат. На странице человека — блок «Встречи» openvk под «Группами» («N встреч», «Все», названия через «•»; предстоящие), «Все» ведёт на его встречи (`/events?u=<никнейм>`, вкладки «Встречи» и «Прошедшие»).

Обсуждения групп («Обсуждения» openvk) живут в `post` рядом с комментариями: темы (`post.Topic`, таблица `topics`: заголовок до 127 символов в одну строку, как обрезает openvk, автор и `from_wall` — тема от имени группы, «Закрыть тему», «Закрепить тему» и «Комментировать могут только администраторы» — `restricted`, только у темы группы, `CHECK` в БД) и сообщения в них (`post.TopicMessage`, `topic_messages`: текст, фото или оба, как комментарий, тоже `from_wall`). Тема считает сообщения и помнит время последнего (`message_count`, `updated_at`) тем же SQL-запросом, что добавляет или удаляет сообщение; список группы (`ListTopics`, публичный) — закреплённые первыми, затем по последнему сообщению, keyset-курсор по (`pinned`, `updated_at`, `id`), `q` ищет по заголовку без учёта регистра, к каждой теме — последнее сообщение («ответил» openvk); сообщения темы — от старых к новым. Кто может начать тему, решает группа: «Все могут создавать темы» (`club.Club.open_topics`, по умолчанию только администраторы — `Club.CanStartTopic`, ответ `can_start_topic` в `ClubView`) и, как с записями, проверяет gateway, он же пускает «От имени сообщества» только администраторов; остальное `post` решает сам, спросив `club.CanModerateWall`: переименовать и закрыть тему могут её автор и администраторы, закрепить и ограничить — только администраторы (`Topic.Changed`), в закрытую тему не пишет никто, в ограниченную — только администраторы (`Topic.CheckWrite`), сообщение удаляют его автор и администраторы, тему — её автор и администраторы, вместе с сообщениями и их фото (тема блокируется `FOR UPDATE`, чтобы сообщение, написанное в это время, не пропало каскадом незамеченным). Лимиты частоты — те же, что у записей (тема) и комментариев (сообщение), счётчики свои; очистка страницы удаляет её сообщения и темы (с чужими сообщениями и их фото). В openvk сообщение темы — комментарий, поэтому у него то же сердечко и те же уведомления. Сердечки — `topic_message_likes` и счётчик `like_count` тем же SQL-запросом, как у комментариев (`LikeTopicMessage`/`UnlikeTopicMessage`, лимит — как у лайков; `ListTopicMessages` говорит вошедшему `liked`; `PUT`/`DELETE /topic-messages/{id}/like`; кто поставил — публичный `ListTopicMessageLikers`, `GET /topic-messages/{id}/likes`, та же подсказка «Понравилось N людям», что у комментариев; очистка страницы забирает её сердечки со счётчиками); о сердечке слышит автор сообщения — уведомление `topic_message_like` (`TopicMessage.Notified`: не о своём и не о сердечке на сообщении «От имени сообщества»; `post_id` — тема, `comment_id` — сообщение; снятое сердечко забирает его `Retract`, удалённые сообщение и тема — как прочие). О новом сообщении слышит тот, кто начал тему (`Topic.Hears`, openvk «оставил комментарий под вашей темой»): уведомление `topic_message` от автора сообщения или, если оно «От имени сообщества», от группы; своё сообщение и сообщение в теме, начатой от имени группы, не уведомляют никого — иначе уведомление выдало бы, кто её начал. `post_id` уведомления — ID темы, `comment_id` — сообщения, поэтому удалённое сообщение забирает своё уведомление (`ForgetComment`), а удалённая тема — все (`ForgetPost`); gateway для такого уведомления ищет не запись и комментарий, а тему (`topic` с заголовком, по запросу на тему) и цитирует сообщение (`comment` — его текст; сообщения страницы — одним публичным `GetTopicMessages`, как `GetComments`). На сайте — блок «Обсуждения» на странице группы («N тем», «Все», три последние темы с «Обновлено …» или «Создать») над стеной или в правой колонке, как велит «Отображать список тем над стеной» (`topics_above_wall`), список тем с поиском, «N результатов» и «Создать тему», «Новая тема» (заголовок, текст с фото, «От имени сообщества»), тема (серый блок с заголовком, автором и «Создано …», «В теме N сообщений», сообщения — `commentNode` с сердечком (`topicHearts`) — и форма; «Ответить» подставляет имя, как openvk) и «Редактирование темы» с «Удалить тему».

Фотоальбомы («Альбомы» openvk) живут в `post` рядом с темами: альбом (`post.Album`, таблица `albums`: название до 36 символов в одну строку — openvk считает байты, мы символы, — описание до 255, `owner_id` — человек или группа, как `wall_id` записи) и его фото (`post.AlbumPhoto`, `album_photos`: ключ — ID фото в `media`, так что фото лежит не больше чем в одном альбоме; кто загрузил — `author_id`, под ним `media` хранит файл; описание до 255, как в openvk). Альбом считает фото и помнит время последнего изменения («Обновлено») тем же SQL-запросом, что добавляет или удаляет фото; фото — от старых к новым по ID (UUIDv7 загрузки в `media`), обложка — первое (`Covers`, как openvk показывает альбом без своей обложки), альбомы — новые первыми. Свой альбом создаёт сам человек, альбом группы — её администраторы; переименовывают, удаляют (с фото) и добавляют фото владелец альбома или администраторы группы (`Album.CanBeChangedBy`, `post` спрашивает `club.CanModerateWall`); описание фото меняет только загрузивший, удаляет фото он или тот, кто может менять альбом (крестик на фото openvk). Фото загружается в `media`, как фото записи (`POST /me/photos`), а «Завершить загрузку» (`AddAlbumPhotos`, до 10 за раз — «Вы можете загружать до 10 фотографий за один раз» openvk) добавляет их с описаниями: gateway проверяет у `media`, что фото свои, `post` публикует их через outbox `media` в той же транзакции; удалённые альбом или фото уносят файлы (`DeletePublishedPhotos` по загрузившим, по 10 за вызов — больше `media` не берёт; альбом блокируется `FOR UPDATE`, как тема). Лимиты частоты — создание альбома и добавление фото считаются как записи, правки альбома и описания — как правки записей, счётчики свои. Альбомы удалённой страницы gateway скрывает, как её стену; фото удалённых страниц в альбоме группы пропускаются, но посчитаны; очистка страницы удаляет её альбомы и её фото в чужих альбомах (файлы `media` стирает сама). На сайте — «Мои Фотографии» в левом меню, как в openvk (`/albums`; чужие — `/albums?u=<никнейм>`, группы — `/club/<адрес>/albums`: «У Вас N альбомов» или «N альбомов» с «Создать альбом» и альбомы списком openvk — обложка, название, описание, «N фотографий», «Обновлено», «Создано»), «Создание альбома» (`/albums/create`, для группы `?club=<адрес>`), альбом (`/album/<id>`: «Анна » Альбомы » Лето», «N фотографий | Загрузить фотографию | Редактировать альбом», фото в сером блоке с крестиком, щелчок открывает просмотр поверх страницы), «Редактировать альбом» и «Добавить фотографии» вкладками (`/album/<id>/edit` с «Вы также можете удалить альбом», `/album/<id>/upload` с белым блоком «Ограничения» openvk; фото загружаются по одному, чтобы альбом сохранил порядок выбора), фотография (`/photo/<id>`: фото, описание и «Дата загрузки», справа загрузивший, «Редактировать» — окно «Изменить фотографию», — «Удалить» и «Открыть оригинал») и блок «Альбомы» на странице человека (между подписками и группами, как у openvk друзья и группы; первые 10) и группы (в правой колонке после руководства, три; администраторам пустой — «Загрузить»). «Фотографии со страницы» openvk — альбом, который ведёт сайт (`post.Album.kind` = `avatars`, один на владельца — частичный уникальный индекс; «получить или создать» опирается на него): каждое новое фото человека и группы gateway загружает в `media` ещё раз, отдельным фото, и кладёт туда (`AddAvatarPhoto`, право — как у альбомов группы, лимит — как у записей); переименовать, удалить и пополнить такой альбом вручную нельзя (`Album.CheckManual`, `FailedPrecondition`/409), удалять из него фото можно. На сайте у него нет «Загрузить фотографию» и «Редактировать альбом», а фото на странице человека ведёт в него. «Фотографии со стены» openvk — второй такой альбом (`kind` = `wall`, свой частичный уникальный индекс; общий конструктор `post.NewSystemAlbum`): фото записи, которую человек написал на своей стене (`Post.InWallAlbum`: не чужая стена, не запись группы и не запись о новом фото страницы), `post` кладёт туда при публикации и при правке, добавившей фото, — копиями под новыми ID (UUIDv7, порядок записи сохраняется), в той же транзакции: строки альбома и запись `copy_photos` в outbox `media` после `publish_photos` (внутренний `media.CopyPhotos`, для mTLS-идентичностей `post` и `message` — так же копируются фото пересылаемых сообщений: жёсткие ссылки на файлы опубликованного фото, идемпотентно, исчезнувшее фото — не ошибка). Копия живёт сама: удалённая запись оставляет фото в альбоме, а удалённое из альбома фото остаётся в записи, как в openvk. Альбом находится или создаётся до транзакции записи (`AlbumService.WallAlbum`): отказ уникального индекса внутри неё оборвал бы её. «Обложка альбома» — фото, выбранное показывать альбом вместо первого (`albums.cover_photo_id` с `ON DELETE SET NULL`, `Album.CheckCover` — только фото самого альбома; `SetAlbumCover`, `PUT /albums/{id}/cover`), а перенос фото — в другой альбом того же владельца, который ведут люди (`Album.CheckMove`; из системного альбома можно, в него — `FailedPrecondition`/409; `MoveAlbumPhoto`, `PUT /album-photos/{id}/album`): один SQL-запрос переносит фото, пересчитывает оба альбома, датирует их и снимает фото с обложки покинутого. И то и другое — тем, кто может менять альбом; лимит — как у правок. На странице фото для них — «Сделать обложкой альбома» и «Перенести в альбом» (окно с выбором альбома). Фото альбома лайкают, комментируют и которым делятся, как записью: лайки (`album_photo_likes`, счётчик `like_count` тем же SQL-запросом, лимит — как у лайков), комментарии — только текст (`post.PhotoComment`, `photo_comments`, счётчик `comment_count`; удаляют автор, загрузивший фото и те, кто может менять альбом; лимит — как у комментариев; gateway проверяет чёрный список с загрузившим), с ответами и сердечками, как у комментариев записи: `reply_to` — комментарий того же фото (`post.NewPhotoReply`, чужой — `ErrReplyOtherPhoto` → `InvalidArgument`; удалённый оставляет ответы — `ON DELETE SET NULL`), `photo_comment_likes` и счётчик `like_count` тем же SQL-запросом (`LikePhotoComment`/`UnlikePhotoComment`, лимит — как у лайков; `ListPhotoCommentLikers`; `PUT`/`DELETE /photo-comments/{id}/like`, `GET /photo-comments/{id}/likes`; о них никого не уведомляют), «Поделиться» — запись с фото (`post.Content.sharedPhoto`, колонка `shared_photo_id` без внешнего ключа: удалённое фото оставляет запись, `RepostPost` с `photo_id`); всё это gateway разрешает только тому, кому видно фото, а очистка страницы забирает её лайки и комментарии фото со счётчиками. О лайке и комментарии слышит загрузивший фото (не о своих): уведомления `photo_like` и `photo_comment` («оставил комментарий под вашей фотографией» openvk) `post` пишет в outbox в транзакции лайка и комментария, их `post_id` — ID фото, `comment_id` — комментария; снятый лайк забирает своё (`Retract`), удалённый комментарий — своё (`ForgetComment`), удалённые фото и альбом — все (`ForgetPost` по фото). Gateway для таких уведомлений читает не запись, а фото (`photo` с адресами картинки, по запросу на фото), а для `topic_message_like` — тему; комментарий фото он цитирует, как сообщение темы (`GetPhotoComments` пачкой). На странице фото — сердечко после «Даты загрузки», «Комментарии (N)» с формой (у комментария — «Ответить», «в ответ» и сердечко, `photoCommentHearts`) и «Поделиться», в просмотре альбома — описание, сердечко, «Поделиться» и ссылка на комментарии.

Заметки («Заметки» openvk) живут в `post` рядом с альбомами: заметка (`post.Note`, таблица `notes`: название до 256 символов в одну строку, как `varchar(256)` openvk, и текст от 1 до 60 000 символов — простой, как у записи; автор — только человек, у групп заметок нет и в openvk) и комментарии под ней (`post.NoteComment`, `note_comments` с `ON DELETE CASCADE`: только текст). Заметки человека — новые первыми, keyset по ID (UUIDv7), комментарии — от старых к новым; счётчик `comment_count` меняется тем же SQL-запросом, что добавляет или удаляет комментарий. Правит и удаляет заметку только автор и когда угодно — срока, как у записи, нет (`Note.Edited`, `CanBeChangedBy`, чужому — `ErrCannotChangeNote` → 403), заметка хранит `edited_at`; комментарий удаляет его автор или автор заметки (`NoteComment.CanBeDeletedBy`). О комментарии слышит автор заметки, не о своём: уведомление `note_comment` («оставил комментарий под вашей заметкой» openvk) `post` пишет в outbox в транзакции комментария, его `post_id` — ID заметки, `comment_id` — комментария; удалённый комментарий забирает своё (`ForgetComment`), удалённая заметка — все (`ForgetPost` по заметке). Кому видны заметки, решает их автор — настройка `notes_read` в `user` («Кому видно мои заметки» openvk, те же четыре варианта, по умолчанию все, см. «Приватность страницы»); `post` пользователей не знает, поэтому проверяет gateway, спросив `user.GetAccess` (`access.notes`): список отвечает 403 `this user's notes are hidden`, а сама заметка, её комментарии и текст комментария — «не найдено», как и заметка удалённой или скрытой страницы (`visibleNote`). Перед комментарием gateway требует заполненную анкету и проверяет чёрный список с автором заметки (`you cannot comment on this note`), как у фото. Список несёт начало текста (`text_limit`, `textCut`), заметка целиком — `GetNote`, комментарий целиком — `GetNoteComment`. Лимиты частоты: заметка — как запись, правка — как правка записи, комментарий — как комментарий, счётчики свои. Очистка страницы удаляет её заметки с комментариями и её комментарии под чужими заметками со счётчиками (`NoteRepository.DeleteByUser`). Gateway: `GET /users/{nickname}/notes`, `POST /me/notes`, `GET`/`PATCH`/`DELETE /notes/{id}`, `GET`/`POST /notes/{id}/comments`, `DELETE /note-comments/{id}`, `GET /note-comments/{id}/text`; уведомление `note_comment` несёт `note` (ID и название, заметку gateway читает отдельным запросом) и цитату комментария (`GetNoteComments` пачкой). На сайте — «Мои Заметки» в левом меню после сообщений, как в openvk (`/notes`; чужие — `/notes?u=<никнейм>`: «Найдено N заметок | Добавить запись» и заметки списком openvk — фото автора, название, «Анна сегодня в 12:00 (ред. …)», начало текста с «Показать больше» и внизу «Комментарии (N)» или «Нет комментариев», «Удалить», «Редактировать»; владельцу без заметок — «Добро пожаловать» openvk), заметка (`/note/<id>`: «Анна » Заметки » Название», заметка целиком и «Комментарии (N)» с формой), «Добавить запись» и «Редактировать заметку» (`/notes/create`, `/note/<id>/edit`: «Название», «Содержание», «Сохранить») и блок «Заметки» на странице человека под «Встречами» («N заметок», «Все», четыре последних названия с датами).

«Закладки» openvk (`/fave`, «Понравившиеся записи») — то, что человек лайкнул: записи, комментарии под записями и фото альбомов, новые лайки первыми, только ему самому. Отдельного хранилища нет — это таблицы лайков, прочитанные со стороны лайкнувшего (`service.FaveRepository`: `LikedBy` и `CountLikedBy` у хранилищ лайков записей, комментариев и фото; keyset по (`created_at`, ID лайкнутого), индексы `*_faves_idx` по (`user_id`, `created_at`, ID) — они же находят лайки стираемой страницы вместо прежних индексов по `user_id`). `service.FaveService` читает страницу лайков, затем сами записи, комментарии или фото одним запросом (`GetMany`) и расставляет их в порядке лайков; фото несут владельца своего альбома (`owner_ids`) — кому видно фото, решает он. Запись в архиве и комментарии под ней не показываются и не считаются (`JOIN posts ... NOT archived`), `total` — сколько лайкнуто. RPC `ListLikedPosts`, `ListLikedComments`, `ListLikedAlbumPhotos` — только с токеном, курсор — «<микросекунды>_<ID>», как у лайкнувших. «Написанные мной записи» openvk (у него — поиск записей `from_me`) — `ListOwnPosts`: записи вызывающего на своей и чужих стенах, новые первыми (`posts_author_id_idx`, правило — `Post.ListedFor`: не предложенные и опубликованные группой и не убранные в архив на чужой стене — своё на своей стене в архиве остаётся), `total` считает их. Gateway (`rest.Faves`, `backend.Faves`): `GET /me/faves/posts|comments|photos` и `GET /me/posts` — записи показаны, как на стене (`withPeople`), комментарий несёт `postId` (запись gateway берёт `GetPosts` пачкой: без неё, без её автора или владельца стены комментарий пропущен, а комментарий «От имени сообщества» показывает группу), фото — как в альбоме, без тех, чей загрузивший удалил страницу или чей владелец альбома скрыл фотографии от зрителя (`albumOwner`, каждый владелец — один раз); пропущенное посчитано. На сайте (`fave.html`, `fave.js`) — «Понравившиеся записи» с вкладками «Записи», «Комментарии» (`?section=comments`) и «Фотографии» (`?section=photos`), «N закладок» и подсказками openvk «Здесь будут отображаться понравившиеся Вам записи.»; запись — как в ленте, комментарий ведёт к своей записи, фото — на свою страницу; «Написанные мной записи» — `/fave/own` с «N записей». Ведут туда ссылки openvk под «Основным» «Моих Настроек»: «Понравившиеся записи • Написанные мной записи»; пункта в левом меню нет — в openvk он закомментирован.

«Настройки ленты» openvk — окно с двумя вкладками над лентой. «Игнорируемые источники» — стены, которые читатель убрал из своих новостей: человек или группа, не больше 50 (`user.MaxIgnoredSources`, как `ignoredSourcesLimit` openvk). Они живут в `user` рядом с чёрным списком (таблица `feed_ignores`: источник — ID без внешнего ключа, группы знает только `club`; строки уходят каскадом со своим владельцем; `IgnoreSource`, `UnignoreSources` — до 10 за раз, как `newsfeed.deleteBan`, — и `ListIgnoredSources`, новые первыми, все идемпотентны; себя нельзя — `ErrIgnoreSelf` → `InvalidArgument`, 51-й — `ErrTooManyIgnored` → `FailedPrecondition`/409). Предел проверяет тот же SQL-запрос, что добавляет источник, под блокировкой строки пользователя — два одновременных не займут последнее место оба. Есть ли такой человек или группа, проверяет gateway (`PUT`/`DELETE /me/feed/ignored/users/{nickname}` и `/me/feed/ignored/clubs/{ref}`, `DELETE /me/feed/ignored?id=…` — до 10, `GET /me/feed/ignored` — люди и группы списком авторов; источник, которого больше нет, gateway при чтении списка сам перестаёт игнорировать, иначе он занимал бы место навсегда), а страницы человека и группы говорят вошедшему `ignoredByMe`. Лента их пропускает: `ListFeed` с `ignored_wall_ids` (до 50, `FeedSources.Ignored`, `AND NOT (wall_id = ANY(...))` — в «Моих новостях» и во «Всех новостях», кто бы там ни писал), а игнорируемого человека gateway убирает и из авторов — за ним не ходят и на чужие стены. Остальные настройки приходят с запросом и на сервере не хранятся: `GET /feed?ignored=true` — «Показывать игнорируемые источники», `?alien=false` — снятая галочка «Показывать посты на чужих стенах» (`ListFeed.own_only`, `FeedSources.OwnOnly`: только `Post.ByWallOwner` — человек на своей стене и группа от своего имени), `?limit=` — «Количество записей на странице». Лимита частоты у игнорирования нет: оно ничего не создаёт для других. На сайте (`feedsettings.js`) — ссылка «Настройки ленты» справа от вкладок ленты и окно openvk: «Основное» («Количество записей на странице» — 1, 5, 10, 20, 30, 40, 50, — «Показывать игнорируемые источники», «Показывать посты на чужих стенах», «Применить») и «Игнорируемые источники» (фото, имя и галочка у каждого, «Не игнорировать» — не больше 10 за раз; «Игнорируемых источников нет.»). Число записей и чужие стены хранит браузер (`localStorage`, `freenet.feed`; у openvk — cookie), игнорируемые показываются, пока это сказано в адресе (`/feed?ignored=1`). На странице человека под «Добавить в чёрный список» — «Игнорировать пользователя»/«Не игнорировать пользователя», на странице группы — «Игнорировать группу».

Лайки и комментарии живут в `post` рядом с записями: внешние ключи `ON DELETE CASCADE` удаляют их вместе с записью. Счётчики (`like_count`, `comment_count`) хранятся в строке записи и меняются **тем же SQL-запросом** (CTE), что вставляет или удаляет лайк/комментарий, — счётчик не расходится с данными даже при одновременных лайках, а стена читается без подсчёта. Лайк идемпотентен (первичный ключ `(post_id, user_id)`). «Нравится ли мне» — поле `liked` у записи: публичные методы заполняют его, если пришёл токен. Комментарий удаляет его автор, автор записи или владелец стены. In-memory реализация (`inmem.Store`) ведёт себя так же: репозитории записей, лайков и комментариев работают над общим состоянием. У комментария — свои лайки (`comment_likes`, счётчик `like_count` тем же SQL-запросом, `LikeComment`/`UnlikeComment`, тот же лимит частоты, что у лайков записей) и ответы, как в openvk: «Ответить» подставляет в поле имя автора («Катя, ») и отправляет `reply_to` — комментарий той же записи (`post.NewReply` отказывает в чужом: иначе ответ обошёл бы проверку чёрного списка по записи из URL); удалённый комментарий оставляет ответы, которые больше ни на что не отвечают (`ON DELETE SET NULL`). Сайт показывает у ответа ссылку «в ответ» на тот комментарий, сердечко — справа в подвале, как у записи (общий `likeButton`). Лента ответов плоская, по времени: веток нет и в openvk.

Обращения и упоминания (openvk): текст называет человека двумя способами — `[никнейм|Имя]`, как пишет «Ответить» (в openvk — `[id1|Имя]`), и `@никнейм` в начале текста или после пробела. Разбирает текст gateway (`model.MentionedNicknames`: первые 10 разных никнеймов, без учёта регистра; `@ann_` называет `ann` — никнейм не кончается на «_»), у `user` спрашивает, кого из них автор вправе назвать (`ResolveMentions`, с токеном; правило — `User.CanBeMentionedBy`: не себя, не того, с кем есть чёрный список в любую сторону, и не удалённую страницу; неизвестные никнеймы пропускаются), и передаёт ID в `post` полем `mentioned_ids` (`CreatePost`, `EditPost`, `RepostPost`, `CreateComment`, `CreatePhotoComment`, `CreateTopic`, `CreateTopicMessage`; `post.Mentions`, больше 10 — `InvalidArgument`). `post` уведомляет названных в той же транзакции, через outbox: `post_mention` (запись; слова репоста — тоже запись, `post_id` — сам репост), `comment_mention` (запись и комментарий), `topic_mention` (тема и сообщение — в `post_id` и `comment_id`, как у `topic_message`), `photo_mention` (фото альбома и комментарий под ним, как у `photo_comment`); кто и так слышит о тексте (владелец стены, автор записи, автор комментария, на который ответили, начавший тему, автор записи, которой поделились, загрузивший фото), второго уведомления не получает (`Mentions.Heard`), а текст «От имени сообщества» упоминает от имени группы (`speaker`). Правка записи уведомляет названных в новом тексте: кто был назван раньше, уведомление уже имеет. Одно упоминание — одно уведомление (частичные уникальные индексы по получателю и записи или комментарию — поэтому повторная правка не дублирует); удалённые запись, комментарий, тема, сообщение, фото и комментарий к нему забирают его обычными `ForgetPost`/`ForgetComment`. Сайт рисует оба вида ссылками на страницу (`mentionParts` в `labels.js` — тот же шаблон, что в gateway; `mentionNodes`/`textNode` в `layout.js`: `[ann|Анна]` — «Анна», `@ann` — «@ann»), но только когда такая страница есть: текст говорит `@слово` о чём угодно, поэтому никнеймы страницы сайт спрашивает разом (`nicknames.js`: каждый один раз за загрузку страницы, пачками по 50; публичный `GET /api/v1/nicknames?nickname=…` — до 100, `user.FindNicknames` по уникальному индексу `lower(nickname)`, удалённые страницы тоже «есть»), и ссылка на никого снова становится простым текстом (без ответа сервера ссылки остаются); «Ответить» в комментариях и темах подставляет `[никнейм|Имя], ` (группе — просто имя, `replyMention`), в «Ответах» — «Анна упомянула вас в записи / в комментарии под записью / в комментарии под фотографией / в обсуждении «Тема»», а цитаты показывают упоминание именем (`plainMentions`).

Уведомления — сервис `notification`. О событиях сообщают их владельцы: `post` (лайк, комментарий, запись на чужой стене, репост, ответ на комментарий — `comment_reply`, лайк комментария — `comment_like`, упоминания — `post_mention`, `comment_mention`, `topic_mention`, `photo_mention`, сердечко сообщения темы — `topic_message_like`, лайк и комментарий фото альбома — `photo_like`, `photo_comment`, комментарий под заметкой — `note_comment`, опубликованная предложенная запись — `post_accepted`, новая предложенная — `suggested_post` администраторам группы), `user` (подписка) и `club` (назначение администратором — `club_admin`, напоминание о встрече — `event_reminder`) вызывают внутренние `Notify`/`Retract` по mTLS; отмена действия (лайк снят, отписка, блокировка) забирает уведомление `Retract`, удалённая запись — все свои `ForgetPost`, удалённый комментарий — все свои `ForgetComment` (о нём, об ответе, которым он был, и о его лайках). Ответ слышит автор комментария, на который ответили, а автор записи — о новом комментарии, если это не он же. Доставка надёжная, через outbox (`pkg/outbox`): `service.Notifier` не звонит, а записывает запрос (proto `NotifyRequest`/`RetractRequest`/`ForgetPostRequest`) в таблицу `outbox` своей БД **в той же транзакции**, что и лайк (`service.TxManager`), — уведомление записано тогда и только тогда, когда записано действие. Таблица делится на потоки (`stream`, по одному на получателя: у `user` это `notification`, `post`, `media`, `message`, `club`, у `post` — `notification` и `media`, у `message` — `media`, у `club` — `notification`) — у каждого свой порядок и свой relay, так что недоступный получатель задерживает только своё. Relay того же процесса доставляет записи потока по одной в порядке записи (`id` — identity из БД, не часы реплик) и повторяет с нарастающей паузой (1 с … 5 мин), пока `notification` недоступен: неудачная запись задерживает следующие, поэтому «снял лайк» не обгонит «поставил». Ошибки, которые повтор не исправит (`InvalidArgument`, `NotFound` и т. п. — `notifyclient.Deliverer`), запись отбрасывают с `ERROR` в логе. Доставляет один relay на поток — тот, кто держит advisory lock потока на своём соединении; новые записи будят его `LISTEN/NOTIFY` (NOTIFY приходит только после коммита), раз в 5 с он смотрит и сам. Доставка «хотя бы раз»: `Notify`/`Retract`/`ForgetPost` идемпотентны. Записи несут `request_id` запроса, а relay доставляет с ним — в логах доставка видна рядом с лайком. Метрики — `outbox_messages_total{result}` и `outbox_lag_seconds` (возраст самой старой недоставленной) с меткой `stream`. В `STORAGE=inmem` outbox в памяти (`outbox.Memory`) и без транзакций. Без `NOTIFICATION_SERVICE_ADDR` сервисы работают без уведомлений (предупреждение при старте). «Сам себе» уведомление не отправляется — это решает сервис-источник, домен `notification` такое отвергает. Один лайк/комментарий/подписка/запись на стене/репост — одно уведомление (частичные уникальные индексы), повтор не дублирует. Прочитанное — одна отметка на пользователя: `read_up_to`, ID самого нового прочитанного (UUIDv7 растут со временем); новее — «Непрочитанное», остальное — «Архив», как в openvk. Отметка только движется вперёд и принимает лишь собственное уведомление пользователя, иначе выдуманный ID «из будущего» спрятал бы все будущие уведомления. Ленту уведомлений собирает gateway: авторы из `user`, даты и тексты записей и тексты комментариев из `post` (`GetPosts`/`GetComments` пачкой); уведомления об исчезнувшем пропускаются, а `newestId` страницы отдаётся всегда, чтобы пропущенное не висело непрочитанным.

Личные сообщения — сервис `message`. Сообщение — строка `messages` с парой (`user_lo`, `user_hi`) = (меньший, больший) ID собеседников: история диалога — один диапазон индекса в обе стороны. Диалог — по строке `dialogs` на каждого участника: последнее сообщение, последнее входящее и отметка «прочитано до» (ID самого нового прочитанного входящего). Отправка — один SQL-запрос: сообщение и обе строки диалога; строки диалога пишутся в порядке `user_id`, иначе двое, пишущие друг другу одновременно, захватывают их в разном порядке и ловят взаимную блокировку (была найдена тестом). «Прочитано» вычисляется по отметкам обеих сторон (`message.ReadMarks`): видно и что не прочитал я, и что не прочитал собеседник. Отметка двигается только вперёд и только на сообщение собеседника пользователю. Своё сообщение отправитель забирает у обоих в течение суток (`Message.TakenBack`, как «Удалить для всех» во ВКонтакте; позже — `ErrDeleteExpired` → `FailedPrecondition`/409, чужое — `ErrCannotDelete` → 403, сообщение из чужого диалога и уже забранное — `NotFound`): строка остаётся на своём месте в диалоге пустой, с `deleted_at` («Сообщение удалено» — собеседник видит, что здесь что-то было; пустым сообщение может быть только такое, `CHECK` в БД), фото уходят (outbox `media`), а обе стороны слышат событие `edit` с тем, чем оно стало. Забранное сообщение остаётся последним в диалоге и непрочитанным, пока его не прочтут, и по-прежнему даёт право ответить; его нельзя править, пересылать и найти поиском, а убрать — только каждому у себя (`HideMessage`). Совсем сообщение удаляет `MessageRepository.Delete` (его скрыли оба, очистка страницы) — один SQL-запрос: удаляет сообщение и возвращает каждую строку диалога к последнему оставшемуся сообщению, только если удалённое было её последним (сообщение, отправленное в это время, уже сдвинуло строку — её не трогаем); строки блокируются в том же порядке `user_id`, что при отправке. Удалено всё — строка остаётся с нулевым `last_message_id` (и отметкой «прочитано») и выпадает из списка диалогов. Как во ВКонтакте, сообщение можно ещё и удалить только у себя и отредактировать. «Удалить у себя» (`HideMessage`, `DELETE /messages/{id}?for=me`) — любое сообщение своего диалога, своё или собеседника: флаги `hidden_from_sender`/`hidden_from_recipient` в строке сообщения (`Message.HiddenFrom`, `VisibleTo`), собеседник его сохраняет и ничего не узнаёт; тот же SQL-запрос возвращает сторону удалившего к последнему сообщению, которое у него осталось (и удаление совсем возвращает каждую сторону только к видимому ей). История, поиск, отметка «прочитано», правка и «удалить для всех» скрытое сообщение не находят; когда его скрыли оба, оно удаляется совсем, с фото. Несколько сообщений удаляются одним запросом — `DeleteMessages` (`ids` — от 1 до `message.MaxBatch` = 100, названное дважды считается раз, `message.Batch`; `for_everyone` — забрать у обоих, иначе — у себя; `DELETE /messages?id=…&id=…[&for=me]`): `MessageService.DeleteMany` сначала читает и проверяет все сообщения, затем меняет их в одной транзакции — все или ни одного, если хоть одно удалить нельзя, — и лишь потом рассылает события; `DeleteMessage` и `HideMessage` — он же с одним сообщением. Правка (`EditMessage`, `PATCH /messages/{id}`) — слова и фото своего сообщения в течение суток (`message.Revision`, `Message.Edited`, `editable_until`; фото заменяются целиком, только когда правка их называет, — `replace_photos`, в JSON поле `photos`, без него они остаются; gateway проверяет названные фото у `media`, как при отправке, а `message` в транзакции правки публикует добавленные и удаляет убранные через outbox `media`; вложенная запись и пересланные остаются, без них и без фото текст не может стать пустым; сообщению с фото альбома свои фото не положены; `ErrCannotEdit` → 403, `ErrEditExpired` → 409), `edited_at` и «(ред.)» на сайте, лимит — как у отправки, свой счётчик; обе стороны, у кого сообщение ещё есть, получают живое событие `edit`. Поиск (`SearchMessages`, `GET /messages/search?q=&peer=`) — подстрока текста без учёта регистра (`message.Query`, до 100 символов, `ILIKE` с экранированием) по всем своим диалогам или по одному, новые первыми, keyset по ID; индексы по отправителю и получателю. Ищет он и в пересланных: сообщение находится и по словам тех, что оно несёт (`Query.Matches`; в SQL — `EXISTS` по `jsonb_array_elements(forwarded)`), их тексты режутся вокруг найденного, как свой, а gateway отдаёт найденное сообщение с пересланными (`showAttached`). Пересылка («Переслать» ВКонтакте): сообщение несёт в себе другие — `message.Forwarded` (кто написал, когда, текст, фото, вложенная запись), колонка `forwarded` (`jsonb`, массив до 20 — `message.MaxForwarded`, `CHECK`); это копии: исходное сообщение может измениться или исчезнуть, а читатель — не быть стороной того диалога. `SendMessage` с `forward_ids` (`service.Draft`) берёт сообщения, которые отправитель видит в своих диалогах (чужое, скрытое у себя и забранное — `ErrForwardNotFound` → `InvalidArgument` «forwarded message not found»), от старых к новым, одно — один раз; пересланное сообщение, которое само что-то несло, разворачивается (`Message.Carried`: его слова, затем то, что оно несло) — вложенности нет. Фото пересланного получают новые ID и копируются в `media` под тем же владельцем (`CopyPhotos` — теперь и для mTLS-идентичности `message`, запись `copy_photos` в outbox в транзакции отправки), поэтому переживают исходное сообщение; забранное или стёртое пересылающее сообщение уносит свои копии (`dropPhotos`). Сообщение — текст, фото, запись, пересланные или их сочетание; правка меняет слова и фото. Gateway (`forward` в теле отправки) отдаёт у сообщения `forwardedCount` и `forwarded` с авторами (одним `GetProfiles` на страницу) и вложенными записями (`showAttached`); пересланное от стёртой или удалённой страницы не показывается. Диалог открывается и вокруг сообщения: `ListMessages` с `around` (`Around`: около половины `limit` до и после, `NotFound`, если сообщения в этом диалоге у вызывающего нет; gateway — `?around=`), дальше — `cursor` назад и `after` вперёд. Сайт показывает под датой сообщения при наведении «Редактировать» (текст возвращается в поле ввода с пометкой «Редактирование сообщения ×», а фото — под него миниатюрами с крестиком, как прикреплённые: их можно убрать и добавить «Прикрепить фотографию»; «Сохранить», Esc отменяет), «Переслать» и «Удалить» — окно с галочкой «Удалить для всех», пока все удаляемые сообщения свои и моложе суток; щелчок по сообщению выделяет его, над диалогом появляется полоса «Выбрано N сообщений | Переслать | Удалить | Отмена» (удаление — одним запросом; если одно из сообщений уже исчезло, остальные удаляются по одному). «Переслать» открывает окно «Пересылка сообщений»: что пересылается, «Кому» (поле поиска человека по имени или никнейму и список: этот диалог и последние или найденные люди) и «Ваш комментарий»; пересланные показаны под словами сообщения с чертой слева — имя, дата, текст, фото, запись. Забранное сообщение — серое «Сообщение удалено» с одной ссылкой «Удалить», в списке диалогов — тем же текстом (`messagePreview` в `labels.js`; пересланные без слов — «N пересланных сообщений»). Поиск — форма над списком диалогов («Мои Сообщения», `/im?q=`, вкладка «Поиск»: найденные сообщения строками, как диалоги, с отрывком вокруг найденного — `SearchMessages` режет текст там, где он говорит запрос (`Text.ExcerptAround`), — подсвеченными словами (`foundParts`, `foundSnippet` в `labels.js`; сообщение, найденное по пересланному, показывает его текст с пометкой «Пересланное сообщение:» — `foundText`) и ссылкой на само сообщение — `/im/<никнейм>?msg=<id>&q=<запрос>`: диалог открывается вокруг него, оно подсвечено, раскрыто целиком и в середине списка, слова запроса в нём и в пересланных им выделены, более новые догружаются, когда список долистан до конца, а до тех пор живые сообщения ждут своей очереди) и «Поиск по переписке» в заголовке диалога (`/im?peer=<никнейм>`). `message` не знает пользователей: получателя по никнейму находит и проверяет gateway, он же требует заполненную анкету отправителя и спрашивает право писать (см. ниже).

Беседы («беседы» openvk и ВКонтакте — чаты нескольких человек) живут в `message` рядом с диалогами, своими таблицами: беседа (`message.Chat`, `chats`: название до 64 символов в одну строку, может быть пустым, и создатель — `owner_id`), её участники (`chat_members`: состояние `active`, `left` — покинул сам, `kicked` — исключён; как строка `dialogs`, участник хранит последнее сообщение, которое ему показано, последнее чужое и отметку «прочитано до») и сообщения (`message.ChatMessage`, `chat_messages`: текст, фото (до 10) или оба — либо действие). Создаёт беседу человек с хотя бы двумя другими («В беседе должно быть как минимум два других пользователя», `MinChatInvited`), в ней не больше 50 человек (`MaxChatMembers`, `ErrChatFull`). Пишет, добавляет людей и переименовывает беседу любой её участник; исключает только создатель (`Chat.CheckKick`, не себя); покинувший возвращается сам (`ReturnToChat`), и другие его не добавят (`ErrMemberLeft`), исключённый — только когда его добавят снова (`message.Admit`, `ErrKicked`). Кто не в беседе, сохраняет её такой, какой она была, когда он ушёл: его строка не двигается дальше последнего показанного сообщения (`Member.Bound`, `Sees`), писать и читать новое он не может. Всё, что происходит в беседе, — тоже её сообщения (`Action`: `create`, `title` — их текст — название, `invite` и `kick` — с `target_id`, `leave`, `return`), записанные в той же транзакции, что и само изменение; транзакция сначала берёт строку беседы `FOR UPDATE` отдельным запросом (`ChatRepository.Lock`) — участники и предел в 50 читаются уже после блокировки. Своё сообщение автор правит (только текст) и забирает у всех в течение суток — оно остаётся на месте пустым («Сообщение удалено»), фото уходят через outbox `media`, как в диалоге. Список бесед человека — keyset по ID последнего показанного ему сообщения, тем же курсором, что `ListDialogs`: UUIDv7 растут со временем в обеих таблицах, поэтому gateway читает по странице диалогов и бесед и сливает их в один список «Моих Сообщений» (`conversations` в `rest/messages.go`; строка — `peer` с `lastMessage` или `chat`), а `CountUnreadDialogs` считает и беседы с непрочитанным. Кого можно добавить, решает добавляемый — настройка приватности `chats_invite` в `user` («Кто может добавлять меня в чаты» openvk: `everyone`, `following` — те, на кого он подписан, по умолчанию, чтобы незнакомец не втянул страницу в беседу, — и `nobody`; клиент, не знающий настройки, её не присылает; правило — `User.CanBeInvitedBy`: не себя, не через чёрный список и не удалённую страницу). `message` пользователей не знает, поэтому перед `CreateChat` и `AddChatMembers` gateway спрашивает `user.ResolveInvites` (никнеймы, до 49 → ID и «можно ли»): неизвестный никнейм — 404 `user not found`, запрет — 403 `you cannot add this user to a chat`; создателю нужна заполненная анкета, фото сообщения gateway проверяет у `media`, как в диалоге. Лимиты частоты: создание, переименование и добавление — `RATE_LIMIT_CHATS`, сообщение и его правка — как у личных сообщений. Очистка страницы (`ChatRepository.DeleteByUser`) убирает человека из всех бесед с его сообщениями и действиями о нём, возвращает строки остальных к оставшимся сообщениям и передаёт его беседы тому, кто в них дольше всех. Gateway: `POST /chats` (название и никнеймы), `GET`/`PATCH /chats/{id}` (беседа с участниками; название), `POST /chats/{id}/members`, `DELETE /chats/{id}/members/{nickname}`, `PUT`/`DELETE /chats/{id}/membership` (вернуться и покинуть) — все отвечают беседой, какой она стала, — `GET`/`POST /chats/{id}/messages` (`?cursor=`, `?after=`), `POST /chats/{id}/read`, `GET`/`PATCH`/`DELETE /chat-messages/{id}`. На сайте — «Новая беседа» справа в заголовке «Моих Сообщений» (`chats.js`: окно с «Введите название беседы» и людьми с галочками — подписчики человека или найденные по имени; без названия беседа называется именами — «Анна, Пётр, Иван», `defaultChatTitle`), беседы в общем списке диалогов (название, «Пётр: иду» или «Анна создала беседу «Поход»» — `chatPreview`) и страница беседы (`/im/chat/<id>`, `chat.js`): «N участников | Добавить участников | Обновить название | Покинуть чат», сообщения с именами, между ними серые строки действий («Анна пригласила Петра Петрова», «исключил … из беседы» — имя в винительном падеже склоняет `accusativeName`), «Редактировать» и «Удалить» у своих сообщений, «О чате» — участники с пометкой «создатель» и «Исключить из беседы» у создателя; покинувшему — «Вы покинули беседу. Вернуться в чат», исключённому — «Вас исключили из беседы.»; в «Приватности» настроек — «Кто может добавлять меня в чаты».

Анкета («Редактировать страницу» openvk) — в `user`: кроме имени, никнейма, статуса и «взглядов», это «Родной город» (`user.Place`, до 64 символов в строку), «Местоимения» (пол `male`/`female` и `neutral` — «они/их» openvk, о таких людях сайт говорит во множественном числе: «написали», «обновили фотографию»), «Семейное положение» с восемью вариантами openvk (`engaged`, `civil_union`, `complicated` добавились) и человеком, которого оно называет (`Profile.Partner`, колонка `relationship_partner_id` с `ON DELETE SET NULL`: стёртый партнёр оставляет положение «ни с кем»; задаётся никнеймом, `partner not found` — если никого; только у положений, которые `TakesPartner`, — не у «не женат» и «в активном поиске»; себя нельзя), «Показывать только день и месяц» дня рождения (`HideBirthYear`: публичный профиль отдаёт дату с годом 2000 и `birth_year_hidden`, gateway — `--MM-DD`), «Контактная информация» (`user.Contacts`: почта для показа — не та, что для входа, — Telegram без «@» (ссылки t.me и «@» принимаются), «Личный сайт» с `https://`, если схему не указали, город, адрес), «Личная информация» (`user.Interests`: интересы, любимые музыка, фильмы, ТВ-шоу, книги, цитаты, игры и «О себе», до 1000 символов каждое, как в openvk) и «Дополнительно» (`user.ExtraField`: до 7 полей с названием до 50 символов, текстом и местом — «В „контактах“» или «В „интересах“»; колонка `extra_fields`, `jsonb`, с `CHECK` на массив до 7). «Дата регистрации» — время UUIDv7 пользователя (`user.RegisteredAt`), отдельной колонки нет. Контакты, интересы и дополнительные поля — не специальные категории ПДн и видны тем, кому видна основная информация (`info_read`, см. «Приватность страницы»); семейное положение с партнёром и день рождения закрыты, пока владелец их не откроет. Части анкеты меняются отдельно, вкладками openvk: `UpdateProfile` («Основное»), `UpdateContacts`, `UpdateInterests`, `UpdateExtraFields`. Поиск людей (`SearchUsers`) понимает фильтры, на которые ведут ссылки страницы: `hometown` и `city` (совпадение без учёта регистра), `film`, `show`, `book` (подстрока поля без учёта регистра); с фильтром слова запроса не нужны. На сайте страница человека — как в openvk: под именем таблица «Местоимения», «Семейное положение» («замужем за Петром Петровым» — предлог openvk и ссылка), «Дата регистрации», «Родной город» (ссылка на поиск), «Полит. взгляды», «Мировоззрение», «Дата рождения»; ниже блок «Информация» с «Контактной информацией» и «Личной информацией» («[ Редактировать ]» владельцу, «Информация отсутствует.»), почта — `mailto:`, Telegram и сайт — ссылки, город и каждое из любимых фильмов, ТВ-шоу и книг через запятую — ссылки на поиск. «Редактировать страницу» (`/edit`, `?act=contacts|interests|additional|avatar`) — вкладки «Основное», «Контакты», «Интересы», «Дополнительно» (поля с «×» и «Добавить») «Аватар» (окно «Загрузка новой фотографии») и «Фон» (`?act=backdrop`, «Фон страницы» — см. ниже), с «Изменения сохранены» после сохранения. Статус владелец правит прямо на странице, как в openvk: щелчок по статусу (или по «[ изменить статус ]») открывает поле с «Сохранить» (`UpdateStatus`, `PUT /me/status` — только статус). «Заполненность страницы» openvk (`User.Completeness`, без рейтинга openvk): интересы, почта и город из контактов — по 20%, Telegram и статус — по 15%, 10% — всегда; профиль отдаёт процент (`completeness`, на удалённой и скрытой странице — нет), владельцу `GetMe` — ещё и недостающее (`unfilled`); сайт показывает серую шкалу (золотую при 100%) вошедшим и владельцу — подсказки openvk «Интересы (+20%)», «Email (+20%)», «Telegram (+15%)», «Статус (+15%)».

Приватность страницы («Приватность» настроек openvk) — в `user`: кто видит (`user.Audience`: `everyone` — «Всем желающим», `users` — «Пользователям Freenet», то есть вошедшим, `following` — тем, на кого подписан владелец, как «Друзьям» openvk, `only_me`) саму страницу (`page_read`, «Кому в интернете видно мою страницу»: только `everyone` или `users`), её основную информацию (`info_read`, «Кому видно основную информацию моей страницы»: всё, кроме имени, фото, статуса и местоимений — по ним сайт склоняет слова), фотоальбомы (`photos_read`), подписки в обе стороны (`friends_read`, «Кому видно моих друзей»), группы (`clubs_read`) и заметки (`notes_read`, «Кому видно мои заметки»; клиент, не знающий настройки, её не присылает — `user` берёт «всем»); по умолчанию — всем, как в openvk. Правило — `User.AccessFor` (`user.Access`: страница, информация, фото, подписки, группы, заметки): владелец видит всё, у удалённой страницы — ничего, кроме неё самой, чёрный список ничего не скрывает (он закрывает контакт, а не данные). `GetProfile` отдаёт страницу такой, какой её видит вызывающий (`PermissionService.ProfileFor`, `PublicProfileFor`): скрытая — только имя и фото с `page_hidden`, скрытая информация — пустые поля с `info_hidden`; списки людей (`GetProfiles`, поиск) зрителя не знают и показывают информацию, только если она открыта всем, а фильтры поиска (`hometown`, `film` и т. д.) находят лишь таких людей. Остальное решает gateway, спросив `user.GetAccess` (публичный, с токеном или без): стена скрытой страницы, альбомы, подписки, группы и заметки отвечают 403 (`this page is hidden`, `this user's photos are hidden`, `this user's follows are hidden`, `this user's clubs are hidden`, `this user's notes are hidden`), альбом и фото скрытых альбомов — «не найдено», а профиль несёт `access` — какие блоки страницы показывать. На сайте — «Мои Настройки» (`/settings`, в меню после «Мои Ответы»): вкладки «Основное» («Адрес Вашей электронной почты», «Адрес Вашей страницы» с ID и никнеймом, «Вы также можете удалить свою страницу»), «Безопасность» (`?act=security`, см. «Сессии»), «Приватность» (`?act=privacy`: «Информация в профиле», «Контент в профиле», «Коммуникация», как в openvk, и наши галочки специальных категорий ПДн) «Чёрный список» (`/settings/blacklist`) и «Внешний вид» (`?act=interface`); скрытая страница показывает «Ошибка доступа» openvk, скрытые блоки пропадают. «Внешний вид» — вкладка openvk «Интерфейс»: как сайт выглядит самому человеку (`user.Interface`, колонки `avatar_style`, `main_page`, `hidden_menu` с `CHECK`; `UpdateInterface`, `PUT /me/interface`, вся форма сразу; `GetMe` отдаёт `interface`, чужому профилю его нет). «Отображение аватаров» — квадратные (как хранятся, по умолчанию) или круглые; «Стиль» — тема оформления (`theme`: `default`, `blue` — «Синий», `dark` — «Тёмный»; темы наши — у openvk это пакеты тем его установки): отдельный файл `web/static/themes/<тема>.css`, который `layout.js` подключает после `style.css`, а с галочкой «Применить стиль только для этого устройства» тема остаётся в `localStorage` браузера (`freenet.theme`) и на сервер не уходит; «Рейтинг» — показывать ли «Заполненность страницы» на страницах, которые человек читает (`hide_rating`; в openvk рейтинг — та же шкала); «NSFW-контент» — что делать с записями, которые автор пометил «Содержит NSFW-контент» (`nsfw`: `blur` — «Только замазывать», по умолчанию, `hide` — «Не показывать в ленте», `show`); «Вид постов» — «Старый» или «Микроблог» (`post_view`); «Часовой пояс» — часы, по которым сайт показывает и принимает даты (`timezone_offset`, минуты к востоку от UTC, от −720 до 840 с шагом 15, `NULL` — часы браузера; `user.Timezone`, в JSON — `timezone`: число или `null`; список поясов — openvk); «Главная страница» — куда сайт ведёт вошедшего с `/` и после входа: «Моя Страница» или «Мои Новости» (`homePath` в `layout.js`); «Левое меню» — какие из ссылок «Мои Фотографии», «Сообщения», «Заметки», «Группы», «Встречи», «Новости», «Ответы» показывать («Моя Страница» и «Мои Настройки» остаются всегда). Сервер только хранит и проверяет значения (кроме ленты, см. ниже), применяет их сайт: `applyInterface` в `layout.js` подключает тему, ставит классы `body` (`avatars-round` — CSS скругляет маленькие фото людей, `posts-microblog`, `nsfw-shown`, `rating-hidden`), передаёт часовой пояс в `labels.js` (`setTimezone`: `formatPostDate`, `formatDateTime`, поля дат встреч) и рисует меню без скрытых пунктов; после сохранения — сразу, без перезагрузки (вид постов — со следующей страницы). Настройки сайт держит и в `localStorage` (`freenet.interface`) и применяет при загрузке скрипта, до ответа `/me`; гостю и после выхода — вид по умолчанию. Клиент, не знающий новых настроек, их не присылает — `user` берёт значения по умолчанию. Пометка NSFW — в `post`: колонка `nsfw` у записи (`Post.Marked`), её ставят при публикации (`CreatePost.nsfw`, на своей и чужой стене и на стене группы) и меняют при правке (`EditPost.nsfw` — `optional`: правка, не назвавшая пометку, её сохраняет); репост не помечается — помечена запись, которой делятся. Стена и страница записи отдают помеченные записи всем, а лента пропускает их для читателя с `nsfw` = `hide` (`ListFeed.hide_nsfw`, `AND NOT (nsfw AND $5)`; gateway берёт настройку из `GetMe`, который лента и так читает). Сайт замазывает текст и фото помеченной записи (и вложенной в репост) плашкой openvk «Данный пост может содержать 18+ контент» и открывает их по щелчку — вошедшему, гостю нет; с «Показывать» не замазывает. Фото помеченной записи замазано и в «Фотографиях со стены»: копия в альбоме несёт пометку своей записи (`AlbumPhoto.Marked`, колонка `album_photos.nsfw`, ставится при копировании — `KeepWallPhotos`), gateway отдаёт `nsfw` у фото альбома, обложки и фото, которым поделились, а сайт размывает картинку (`adult` в `layout.js`: миниатюры, обложки альбомов, страница фото, просмотр) и на странице фото и в просмотре открывает её по щелчку (`revealAdult`), гостю — нет. «Микроблог» — раскладка `posts.js`: без серой полосы над записью и без «написал», дата внизу слева, «Поделиться» — стрелка со счётчиком рядом с сердечком, под каждой записью черта; «Редактировать», «Удалить», «Закрепить»/«Открепить» и «Архивировать» — значки справа от имени автора (карандаш, крест, кнопка, коробка; видны при наведении на запись, подпись — в `title`), как у openvk, а под записью стены и ленты — три её последних комментария, «Показать остальные комментарии (N)» (ссылка на страницу записи) и поле ответа (`postcomments.js`; без комментариев поле открывает «Комментировать»). Комментарии приходят со списком записей: `?comments=last` у стены человека, стены группы и ленты добавляет каждой записи `lastComments` — gateway одним запросом берёт у `post` `ListLastComments` (публичный: три новейших комментария каждой из ≤ 50 записей одним SQL-запросом с `LATERAL` по индексу (`post_id`, `id`), от старых к новым, с `liked` для вошедшего; архивные записи не отдают ничего) и ещё одним — их авторов; сайт просит их только в «Микроблоге». Значок сайта — «f» логотипа: `web/static/favicon.svg` (и PNG 32 и 180 px для браузеров без SVG), `/favicon.ico` gateway отдаёт тем же PNG.

Сессии («Безопасность» настроек openvk) — в `auth`: сессия помнит, когда ею пользовались в последний раз (`last_used_at` — вход и каждый refresh) и с какого устройства (`session.Device`: IP-адрес и `User-Agent`, одна строка до 255 символов; оба — со слов клиента). Их, как адрес для лимитов, называет gateway метаданными (`authv1.ClientIPMetadata`, `authv1.UserAgentMetadata`), и `auth` верит им только от mTLS-идентичности `gateway` — без mTLS (`make dev`) устройство пустое. Ротация refresh-токена тем же `UPDATE` пишет время и устройство (`Session.Rotated`). Свои сессии человек видит и завершает: `ListSessions` (те, чей refresh-токен ещё действует — `Session.LiveSince`, последняя использованная первой, до `service.MaxSessions` = 100; текущая — по `sessionId` access-токена, `current`), `EndSession` (только свою — чужая и уже завершённая отвечают `NotFound` «session not found») и `EndOtherSessions` (все, кроме текущей, отвечает, сколько). Поэтому `auth` теперь тоже проверяет access-токены (`jwtauth.UnaryServerInterceptor`, публичны четыре RPC входа — `grpc.PublicMethods`); токен удалённой страницы эти методы не пускают. Завершённая сессия не обновит токены, но её access-токен действует до истечения (≤ 15 мин), как после `Logout`. Gateway — `GET /me/sessions`, `DELETE /me/sessions` (все остальные, ответ — `ended`) и `DELETE /me/sessions/{id}`; `User-Agent` он передаёт печатными ASCII-символами, до 255. На сайте — вкладка «Безопасность» «Моих Настроек» (`?act=security`): блок «Сессии» — «Вы вошли на сайт с N устройств.», строки «Chrome, macOS — текущая сессия» (`deviceName` в `labels.js` угадывает браузер и систему по `User-Agent`, иначе «Неизвестное устройство») с IP-адресом, временем входа и последней активности и ссылкой «Завершить» у остальных, а под ними — текст и кнопка openvk «Сбросить все сессии», после которой — «Все остальные сессии сброшены».

Присутствие («Онлайн» и «был в сети» openvk) — в `user`: `last_seen_at` — время последнего визита (NULL — не заходил). Отмечает его gateway, пока у страницы открыт поток событий (`/api/v1/events`): при подключении, до `ready`, и раз в 2 минуты (`MarkOnline` с токеном вызывающего; сбой только логируется — события важнее); онлайн — кто заходил последние 5 минут (`user.OnlineFor`, как в openvk). Время только движется вперёд (`User.MarkSeen`, `UPDATE ... WHERE last_seen_at < $2`: запросы могут прийти не по порядку), а сохранение профиля (`Update`) его не пишет. Когда человек был в сети, говорит только `GetProfile` (`last_seen_at`; списки людей — нет), а кто онлайн сейчас — и списки (`User.ListedProfile`: подписчики и подписки, поиск, `GetProfiles` — отсюда и участники групп; зрителя список не знает, поэтому `online` говорит только страница, открытая всем, и не удалённая): отсутствие короче 29 дней видят все, как в openvk, дольше — только те, кого пускает «Кто видит мою неактивность» (`online_read`, те же четыре варианта, что у других настроек, по умолчанию все; правило — `User.lastSeenFor`), удалённая и скрытая страница не говорит ничего. «Друзья онлайн» openvk — подписки, которые сейчас онлайн: `ListFollowing` с `online` (gateway — `?online=true`, `total` считает их же; удалённые страницы не в счёт). На сайте — справа в заголовке страницы жирное «Онлайн» или «был(а) в сети сегодня в 12:00» (без него — никнейм), владельцу — «(это вы)» после имени, «Онлайн» и блок «Подписки онлайн» («N человек онлайн», «Все» и первые шесть) под подписками, а у страницы подписок — вкладка «Онлайн»; в списках людей (подписки, поиск, участники и руководство группы) у того, кто сейчас на сайте, после имени стоит «Онлайн».

«Фон страницы» человека (openvk) — как у групп: два фото по бокам страницы, `backdrop_left`/`backdrop_right` в `users` (`user.Backdrop`, публичны, как аватарка; у удалённой и скрытой страницы фона нет). Каждая сторона меняется своим `UPDATE`, который возвращает фото, что она показывала (`SetBackdrop` с `previous_photo_id`, строка блокируется подзапросом — два одновременных изменения стороны получают каждое своё прежнее фото), а `Update` профиля фон не пишет. Файлы — обычные фото человека в `media`: gateway (`PUT /me/backdrop/{left|right}`, `DELETE /me/backdrop`) загружает картинку `UploadPhoto`, сразу публикует её `PublishPhotos` (для mTLS-идентичности `gateway` — иначе через сутки она пропала бы как неопубликованная), ставит стороной и удаляет прежнее фото `DeletePublishedPhotos`; удалять «все фото, кроме оставляемых», как у групп, здесь нельзя — у человека это и фото записей. Сайт рисует фон страницы человека тем же `backdrop.js`, что у групп (там же форма «Обзор»/«Сохранить фон»/«Удалить фон»), а настраивает его на вкладке «Фон» «Редактировать страницу».

Приватность сообщений и чёрный список — в `user`, рядом с подписками. «Кто может писать мне сообщения» (`messages_write`, как в openvk): `everyone` (по умолчанию — как было до настройки), `following` (те, на кого подписан получатель) и `nobody`; тот, кому вы написали первыми, может ответить при любой настройке («Вам смогут ответить, если вы напишете первыми»). Писал ли получатель отправителю, знает только `message` (`HasMessagesFrom`, по строке `dialogs`): gateway берёт этот факт у `message` и передаёт в `user.CanMessage`, а решает правило домена `user.CanBeMessagedBy`. Чёрный список (`blocks`, «Чёрный список» openvk) действует в обе стороны: если один внёс другого, между ними нет сообщений (и ответов), записей на стене, подписок и комментариев к записям друг друга; блокировка удаляет подписки в обе стороны тем же SQL-запросом (CTE), их уведомления забираются. Правила («связи» `user.Ties`: подписан ли владелец, есть ли блокировка, писал ли первым) — в домене `user`, сбор связей — `service.PermissionService` (`CanPostOnWall`, `CanMessage`), подписка проверяет блокировку сама. Комментарии живут в `post`, который пользователей не знает, поэтому перед `CreateComment` gateway спрашивает `user.GetRelation` с автором записи и владельцем стены. Профиль для вошедшего отдаёт `blockedByMe`/`blockedMe`, и сайт показывает вместо него ограниченную страницу openvk («Анна ограничила доступ к своей странице», «… — в вашем чёрном списке»). Профиль и стена при этом остаются публичными (аноним видит их всё равно): чёрный список закрывает контакт, а не данные. Новые сообщения и отметки «прочитано» приходят на страницу сразу (см. «Живые события»); пока поток событий недоступен, страница диалога опрашивает раз в 5 секунд (`?after=`), только пока вкладка видна, и после переподключения один раз догоняет пропущенное; прочитанными отмечает только видимая вкладка.

Удаление страницы («Удаление страницы» openvk) — в `user`: `DeactivateAccount` с необязательной причиной (сайт предлагает причины openvk) скрывает страницу сразу, а восстановить её (`ReactivateAccount`) можно до `purge_at` — через `ACCOUNT_RETENTION` (по умолчанию 7 месяцев, как в openvk). Пока страница удалена, другие видят только имя и фото (`deactivated` в профиле): на неё нельзя подписаться, писать на её стену и ей, её нет в поиске, а написанное её владельцем gateway скрывает (записи, комментарии, уведомления — `authors` пропускает удалённых; в диалогах собеседник остаётся с пометкой). Правила — в домене (`User.Deactivate`/`Reactivate`, `PublicProfile`, `CanPostOnWall`, `CanBeMessagedBy`). Сам владелец удалённой страницы не может ничего, кроме как увидеть и восстановить её: `auth` при входе и при каждом refresh спрашивает `user` (`GetOrCreateByEmail`, внутренний `GetAccountState`) и ставит в access-токен `deactivated`; `jwtauth.UnaryServerInterceptor` во всех сервисах пускает такой токен только в методы `jwtauth.Access.Deactivated` (`GetMe`, `ReactivateAccount`), публичные видят его владельца анонимом, остальные отвечают `PermissionDenied` («your page is deleted»), потоков он не получает. После удаления и восстановления сайт сразу обновляет токены; уже выданный полный токен действует до истечения (≤ 15 мин), как после `Logout`. На сайте — ссылка «Вы также можете удалить свою страницу» под настройками (`deactivate.js`, окно openvk), у владельца удалённой страницы нет меню и в шапке только «выход», с любой страницы его переносит на свою, где «Ваша страница удалена… восстановить свою страницу до …»; другие видят «Страница удалена. Информация недоступна.». По истечении срока `user` каждые `ACCOUNT_PURGE_INTERVAL` (`service.PurgeService`) удаляет строки пользователей (подписки и блокировки — каскадом; `FOR UPDATE SKIP LOCKED`, реплики не мешают друг другу) и **в той же транзакции** записывает `purge_user` в outbox каждого сервиса, хранящего данные пользователей (`purgeclient`): их внутренний `PurgeUser` (только для mTLS-идентичности `user`, идемпотентный) стирает в `post` записи пользователя и записи на его стене с лайками и комментариями, его лайки и комментарии к чужим записям (счётчики — тем же SQL-запросом) и `ForgetPost` удалённых записей через свой outbox; в `media` — все аватарки и фото; в `message` — его диалоги с обеих сторон со всеми сообщениями (собеседнику остался бы диалог ни с кем); в `club` — его членство во всех группах; в `notification` — уведомления, которые он получил или вызвал, и отметку «прочитано» (через поток `notification`, чтобы старое уведомление о подписке не пришло после очистки). Сессии стёртого пользователя в `auth` кончаются при следующем refresh (`GetAccountState` → `NotFound`), почта освобождается — с ней можно зарегистрироваться заново, новым пользователем.

Живые события. Источники — сервисы, владеющие данными: `message` (новое сообщение — обоим участникам, сдвинутая отметка «прочитано» — обоим, отредактированное или забранное сообщение — обоим, удалённое у себя — удалившему; в беседе новое сообщение или действие и отредактированное или забранное — всем её участникам, отметка «прочитано» — прочитавшему: `chat_message`, `chat_edit`, `chat_read` у gateway) и `notification` (новое, отозванное, прочитанное). Каждый держит концентратор подписчиков (`pkg/pubsub`) и отдаёт события потоковым RPC `Subscribe` (server streaming): поток живёт не дольше access-токена — `jwtauth.StreamServerInterceptor` ставит дедлайн на его срок, и поток кончается `Unauthenticated`; отставший подписчик (буфер 64) отключается `ResourceExhausted` и догоняет из хранилища — события не теряются молча. При заданном `REDIS_ADDR` концентратор общий для реплик (`pubsub.Redis`): событие публикуется в канал Redis (`message:events`, `notification:events`, JSON — `internal/redis`), и каждая реплика раздаёт пришедшее своим подписчикам — поток получает события, опубликованные на любой реплике. Redis pub/sub ничего не хранит, поэтому реплика, потерявшая подписку на канал (переподключение, Redis недоступен), сбрасывает своих подписчиков и, пока не подписана снова, сразу закрывает новые потоки: страница получает 1013, догоняет обычными запросами (диалог — опросом) и подключается позже. go-redis не прерывает `Receive` по отмене контекста — `Run` закрывает подписку сам. Без `REDIS_ADDR` события остаются в реплике (`pubsub.Hub`, предупреждение при старте). `pkg/grpcserver` при остановке сначала отменяет все потоки, иначе `GracefulStop` ждал бы их до таймаута. `gateway` открывает на страницу один WebSocket `/api/v1/events` (`coder/websocket`): токен — первым сообщением, а не в URL (попал бы в логи); собирает оба потока, добавляет профили собеседников и пересчитывает счётчики у сервисов (события лишь говорят, когда), отдаёт JSON-события (`ready`, `counters`, `message`, `read`, `delete`, `notification`, контракт — `openapi.yaml`). Коды закрытия говорят странице, что делать: 4001 — обновить токен и подключиться заново, 1013 — подождать, 1001 — сервер останавливается. Таймаут запросов к потоку не применяется, дедлайны `http.Server` с перехваченного соединения снимаются, а при остановке gateway закрывает потоки сам (`Shutdown` их не ждёт). На сайте `events.js` (подключает `renderChrome`) держит соединение и переподключается с нарастающей паузой; счётчики меню, диалог, список диалогов (удалённое последнее сообщение — загрузкой первой страницы заново: что теперь последнее, знает только сервер) и вкладка «Непрочитанное» ответов обновляются без перезагрузки.

Наблюдаемость. **ID запроса** (`pkg/reqid`): `gateway` даёт каждому HTTP-запросу ID (или берёт `X-Request-ID` от своего прокси — только при `TRUST_FORWARDED_FOR=true` и только допустимого вида: до 64 символов из букв, цифр и `-_.:`, иначе ID подделал бы строки лога) и возвращает его в заголовке `X-Request-ID`. ID идёт в контексте и gRPC-метаданных `x-request-id` через все вызовы — gateway → сервис → сервис (клиенты собираются с `reqid.DialOptions()`; уведомления доставляет relay позже — ID хранится в записи outbox и идёт с доставкой), — и `pkg/logger` дописывает `request_id` в каждую строку, залогированную с этим контекстом. Сервер, к которому ID не пришёл, заводит свой. Поэтому логируем с контекстом (`InfoContext`, `ErrorContext`), когда он есть. Каждый gRPC-вызов пишется на уровне `debug` (`grpc call`: метод, код, время) — с `LOG_LEVEL=debug` весь путь запроса виден по одному `request_id`. **Метрики** Prometheus (`pkg/metrics`) — на отдельном порту `METRICS_PORT`, наружу не публикуется (без переменной не отдаются). `pkg/grpcserver` считает каждый вызов с кодом, который получил клиент (его интерсепторы стоят снаружи интерсепторов сервиса): `grpc_server_handled_total`, `grpc_server_handling_seconds` (только unary), `grpc_server_streams_open`; `gateway` — `http_requests_total` и `http_request_duration_seconds` по шаблону маршрута (`/api/v1/users/{nickname}`, никогда по самому пути — никнейм и ID в метке раздули бы её до бесконечности, поэтому middleware обёрнут прямо вокруг mux, который знает шаблон), `gateway_event_streams_open`; плюс метрики Go и процесса. `make stack` поднимает Prometheus (`monitoring/prometheus.yml`, http://localhost:9090), `make dev` даёт сервисам порты метрик сам. **Базы и Redis** наблюдаются экспортёрами в профиле `app` (`compose.yaml`): по `postgres-exporter` на каждую базу — у каждой свой пользователь и пароль (`<сервис>-postgres-exporter`, около 12 МБ памяти каждый) — и `redis-exporter`; Prometheus собирает их раз в 30 с заданиями `postgres` (метка `db` — чья база) и `redis`, порты наружу не публикуются. **Алерты** — правила Prometheus в `monitoring/alerts.yml`: сервис недоступен (`ServiceDown`), база или её экспортёр не отвечают (`PostgresDown`), занято больше 80% соединений базы (`PostgresConnectionsHigh`), не отвечает Redis (`RedisDown`), доля ошибок сервера выше 5% (`GRPCServerErrors` — коды `Internal`/`Unknown`/`DataLoss`, `HTTPServerErrors` — 5xx), 95-й перцентиль дольше 1 с у HTTP и 0,5 с у gRPC (`HTTPSlow`, `GRPCSlow`), поток outbox стоит дольше 5 минут (`OutboxLagging`) и часа (`OutboxStuck`, критично: через сутки `media` убирает фото как неопубликованные, и до доставки на их месте битые картинки, а через `RETIRED_PHOTO_TTL` удаляет их совсем), outbox отбросил запись (`OutboxDropped`). У каждого правила есть тест `promtool` в `monitoring/alerts_test.yml`; `make check-integration` гоняет их и проверяет конфиги `promtool`/`amtool` из тех же образов, что в `compose.yaml`. Новая метрика, о сбое которой надо знать, получает правило и тест. Prometheus отдаёт алерты Alertmanager (http://localhost:9093, `monitoring/alertmanager.yml`: группировка по сервису, `ServiceDown` глушит ошибки и задержки того же сервиса); локально оповещать некого — у получателя нет каналов, а на сервере `deploy/alertmanager.sh` при каждом деплое собирает из `monitoring/alertmanager.yml` файл `/opt/freenet/alertmanager.yml` (вне `monitoring/`, который деплой заменяет) с чатом Telegram, если в `.env` сервера заданы `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` (без них — никого; значения проверяются по формату до того, как попадут в YAML), деплой проверяет его `amtool`, как Caddyfile, и перезапускает Alertmanager, если файл изменился; токен живёт только на сервере, `make check-integration` проверяет сборку с выдуманным чатом. **Grafana** (http://localhost:3001, `GRAFANA_PORT`) открыта для просмотра без входа (`admin` — с `GRAFANA_ADMIN_PASSWORD`); источники данных (Prometheus, Alertmanager) и дашборд «Freenet» берутся из `monitoring/grafana` при старте, правка — только в git (`freenet.json`), не мышью в Grafana: доступность сервисов и алерты, gRPC (вызовы, доля ошибок, задержки, отказы по кодам, открытые потоки), HTTP gateway по маршрутам, outbox по потокам, память, CPU и горутины, базы и Redis (доступность, доля занятых соединений, размер баз, память Redis); переменная `service` выбирает сервисы. **Healthcheck** — `<service> -healthcheck` (см. Docker выше); gRPC health `Check` открыт без токена (`jwtauth`), он говорит только, работает ли сервис.

Защита от спама — ограничение частоты действий на пользователя: записи, репосты, правки записей, комментарии, лайки, голоса в опросах, заметки и комментарии к ним (`post`), сообщения, создание бесед и добавление в них (`message`), загрузка фото и аватарок (`media`), подписки (`user`), создание и правка групп и вступление в них (`club`). Это сквозная задача, поэтому она сделана gRPC-интерсептором `pkg/ratelimit.UnaryServerInterceptor`: он стоит **после** `jwtauth` и считает по ID пользователя из проверенного токена, ключ — метод + окно + пользователь. Правила — в конфиге сервиса (`RATE_LIMIT_*`, формат `5/1m,100/24h`: короткое окно против всплесков, длинное против медленного спама; неверный формат роняет старт), сопоставление метод → правило — в `app` (`rateLimits`). Счётчики — фиксированные окна в Redis при заданном `REDIS_ADDR` (общие для реплик; `make dev-persistent` берёт Redis из compose) или в памяти (на реплику, с предупреждением при старте). Превышение — `ResourceExhausted` → HTTP 429 «too many requests, try again later». Сбой Redis пропускает вызов с предупреждением в логе: защита от спама не должна останавливать сайт. Новое действие, создающее контент для других, получает свой лимит.

Поиск людей — в `user`: каждое слово запроса ищется `LIKE '%слово%'` по выражению с триграммным индексом `pg_trgm`. Условия на слова — отдельные `AND ... LIKE $n`: с `LIKE ALL (массив)` GIN-индекс не используется (проверено `EXPLAIN`). Фильтры анкеты тоже с индексами: `lower(hometown)` и `lower(city)` — B-дерево вместе с `id` (совпадение целиком и keyset-страницы), `lower(fav_films)`, `lower(fav_shows)`, `lower(fav_books)` — триграммные GIN; выражения в запросе и в миграции обязаны совпадать — это проверяет `TestSearchFilters_Indexed` по `EXPLAIN`.

Структура `gateway/` другая — в нём нет бизнес-логики:

```
gateway/
├── api/openapi.yaml         # публичный контракт для фронтенда
└── internal/
    ├── model/               # «домен» gateway: то, о чём говорит API, без JSON и proto
    ├── failure/             # виды ошибок для клиента (Kind) с безопасными сообщениями
    ├── backend/             # адаптеры к gRPC-сервисам: proto ↔ model, статус → failure
    ├── rest/                # HTTP: маршруты, DTO (camelCase JSON), middleware, порты Auth/Users
    ├── config/
    └── app/
```

`rest` зависит от портов (`rest.Auth`, `rest.Users`) и `model`, но не от gRPC; `backend` — единственное место, где gateway знает proto. Enum'ы в JSON — строчные имена значений домена (`"in_love"`, `""` = не задано), даты — `YYYY-MM-DD`.

## 2. Архитектура: чистая архитектура

### 2.1. Слои и правило зависимостей

Зависимости направлены **только внутрь**:

```
transport (grpc) ─┐
                  ├─►  service (use cases)  ─►  domain (entities, value objects)
infra (postgres,  ─┘          ▲
 redis, jwt, smtp)            │ реализуют интерфейсы, объявленные в service
```

| Слой | Пакет | Что содержит | Что импортировать МОЖНО | Что НЕЛЬЗЯ |
|---|---|---|---|---|
| Домен | `internal/<domain>` | сущности, value objects, инварианты, доменные ошибки | stdlib, `uuid` | proto, pgx, redis, grpc, slog, любой фреймворк, другие слои |
| Приложение | `internal/service` | use cases, DTO, **интерфейсы-порты** | домен, `pkg/errs` | proto-типы, `grpc/status`, SQL, redis-клиент, JWT-библиотеки |
| Транспорт | `internal/grpc` | хендлеры, маппинг proto↔домен, перевод ошибок в gRPC-коды | service, домен, proto | SQL, бизнес-правила |
| Инфраструктура | `postgres`, `redis`, `inmem`, `jwt`, `smtp`, `console` | реализации портов | домен, service (только для типов в сигнатурах), драйверы | бизнес-логика, импорт `grpc`-слоя |
| Composition root | `internal/app`, `cmd/` | сборка графа зависимостей | всё | — |

Жёсткие запреты:
- Домен не знает ни про что снаружи. Никаких тегов `db:`/`json:`, никаких proto-типов в доменных структурах.
- Сервисный слой **не импортирует сгенерированные proto-пакеты** (ни свои, ни чужих сервисов). Вызов другого сервиса — через порт (интерфейс в `service`), реализация-адаптер (gRPC-клиент) лежит в инфраструктуре, например `internal/userclient/`.
- Инфраструктура не вызывает use cases и не знает про транспорт.
- Циклические импорты между слоями недопустимы; если возникает — нарушена архитектура, а не «нужно вынести в utils».

### 2.2. Интерфейсы (порты)

- Интерфейс объявляется **на стороне потребителя** (там, где используется), а не рядом с реализацией: `service.UserRepository`, `grpc.UserService`.
- Интерфейсы маленькие: 1–4 метода, под конкретный use case. Не создавай «толстый» `Repository` на все случаи.
- Конструкторы принимают интерфейсы, возвращают **конкретные типы** (`NewUserService(repo UserRepository) *UserService`).
- Не создавай интерфейс «на будущее» без второго потребителя/реализации или потребности в моке.

### 2.3. Доменный слой

- Сущности — структуры с **неэкспортируемыми полями** и геттерами (`u.Email()`), создаются только через конструктор `New(...)`, который проверяет инварианты. Нельзя получить невалидную сущность.
- Для восстановления из хранилища — отдельный конструктор `Restore(...)` (без генерации ID и без побочных эффектов), а не публичные поля.
- Примитивы с правилами — **value objects** на базе `string`/`time.Time` в отдельных файлах: `Email`, `Nickname`, `Name`, `Birthday`, `Gender` и т. д. Шаблон:
  - тип `type Email string`;
  - конструктор `NewEmail(s string) (Email, error)`: нормализация (`TrimSpace`) → проверка → значение;
  - метод `String()`;
  - константы лимитов (`maxEmailLen`) и **доменные ошибки-sentinel** в `var (...)` рядом с типом.
- Перечисления — типизированные строковые константы + конструктор-валидатор (`NewGender`), а не «голые» строки. Значение «не задано» — осознанная константа (`GenderNone`).
- Длину строк считать в рунах (`utf8.RuneCountInString`), не в байтах.
- ID сущностей — `uuid.UUID`, генерация — **UUIDv7** (`uuid.NewV7()`).
- Время — `time.Time` в UTC. В доменном слое, где время влияет на логику, не вызывай `time.Now()` напрямую в неочевидных местах — передавай время параметром или используй интерфейс `Clock`, чтобы это можно было тестировать.
- Бизнес-правила живут в домене (методы сущностей), а не в хендлерах и не в SQL.

### 2.4. Сервисный слой (use cases)

- Один публичный метод = один use case. Принимает `context.Context` **первым** аргументом.
- Вход — DTO из `service/dto.go` (`CreateUserInput`) с **доменными типами** (value objects), а не сырые строки/proto. Выход — доменные сущности или DTO сервиса (`TokenPair`).
- Сервис оркестрирует: вызывает домен, репозитории, внешние порты. Не содержит SQL, не знает про gRPC-коды, не логирует «для галочки» (логирование ошибок — на границе, см. §5).
- Многошаговые операции, которые должны быть атомарными, выполняются в транзакции через порт (`TxManager`/`WithinTx`), а не склейкой из нескольких независимых вызовов. Реализация — `pgpool.TxManager`: транзакция едет в контексте, вложенный `WithinTx` присоединяется к внешней; для `inmem` — `inmem.TxManager`, который просто вызывает функцию. Так же атомарно с изменением записывается всё, что надо сообщить другому сервису (outbox, см. §1).
- Идемпотентность и гонки продумываются явно: «получить или создать» опирается на уникальный индекс в БД (`INSERT ... ON CONFLICT` или повторное чтение после `ErrAlreadyExists`, как в `user.GetOrCreateByEmail`), а не на `Get` + `Create` без защиты.

### 2.5. Транспортный слой (gRPC)

- Хендлер делает только: (1) достаёт данные из запроса, (2) собирает value objects (валидация формата), (3) вызывает use case, (4) мапит результат в proto, (5) переводит ошибки в gRPC-статусы.
- Маппинг proto↔домен — только в `mapper.go` пакета `grpc`. Именование: `toProtoX` (домен → proto), `fromProtoX` (proto → домен).
- Всегда используй геттеры (`req.GetEmail()`), а не прямой доступ к полям — они nil-безопасны.
- Метод, возвращающий `google.protobuf.Empty`, возвращает `&emptypb.Empty{}`, а **не** `nil, nil`.
- Трансляция ошибок (единое место, функция `toStatusError(err)`):

  | Ошибка | gRPC-код |
  |---|---|
  | ошибка валидации входа / value object | `InvalidArgument` |
  | сущность не найдена | `NotFound` |
  | уже существует / конфликт | `AlreadyExists` |
  | нет/невалидный токен или код | `Unauthenticated` |
  | нет прав | `PermissionDenied` |
  | лимит запросов | `ResourceExhausted` |
  | состояние не позволяет (страница не удалена, срок восстановления вышел) | `FailedPrecondition` (gateway — 409) |
  | всё остальное | `Internal` с **общим** текстом |

  Сопоставление — через `errors.Is`/`errors.As` по доменным ошибкам. Нельзя отдавать `err.Error()` внутренней ошибки клиенту (утечка деталей) и нельзя маппить всё подряд в `Internal` или всё в `InvalidArgument`.
- Сквозные вещи (логирование запросов, recover, метрики, трассировка, аутентификация по JWT) — через gRPC-интерсепторы, а не копипастой в хендлерах. ID запроса и метрики ставит сам `grpcserver.New` (снаружи интерсепторов сервиса), клиенты другим сервисам собираются с `reqid.DialOptions()`.
- Аутентификация — `jwtauth.UnaryServerInterceptor`: по умолчанию **каждый** RPC требует access-токен, публичные методы перечисляются явно (`jwtauth.Access{Public: grpc.PublicMethods()}`), методы, доступные токену удалённой страницы, — тоже (`Access.Deactivated`). ID текущего пользователя хендлер берёт из `jwtauth.IdentityFromContext`. Публичный метод работает и без токена, но присланный токен всё равно проверяется: так ответ может зависеть от зрителя («вы подписаны»), а истёкший токен даёт 401 для обновления.
- Внутренние RPC (вызываются только другими сервисами) перечисляются в `grpc.InternalMethods()` с разрешёнными идентичностями и закрываются `mtls.RestrictMethods`.
- Перевод ошибок — `grpcserver.ErrorInterceptor(log, toStatus)`: в сервисе остаётся только `toStatus(err) (*status.Status, bool)` с таблицей известных ошибок.
- Публичный контракт — только `.proto`. Меняя его, сохраняй обратную совместимость (см. §9).

### 2.6. Инфраструктурный слой

- Репозиторий реализует порт из `service`, принимает и возвращает **доменные** типы. Типы драйвера (`pgx.Row`, `redis.Nil`) наружу не выходят: `pgx.ErrNoRows` → доменная `ErrNotFound`, нарушение unique → `ErrAlreadyExists`, `redis.Nil` → `ErrNotFound`.
- Структура репозитория — `struct{ pool *pgxpool.Pool }` + `NewXRepository(pool)`. Репозиторий, который участвует в транзакциях, выполняет запросы на `r.conn(ctx)` (= `pgpool.Conn(ctx, r.pool)`): внутри `WithinTx` это транзакция, снаружи — пул.
- SQL — константами рядом с методом, именованными `<action><Entity>Query`; только параметризованные запросы (`$1, $2`), **никогда** конкатенация строк. Колонки в `INSERT`/`SELECT` перечисляются явно (никаких `SELECT *`), по одной на строку.
- Каждый запрос — с `ctx`. Для чтений из БД — таймауты через контекст.
- `inmem`-реализации — только для разработки и тестов; они должны вести себя как настоящие (TTL, уникальность, те же sentinel-ошибки). Не использовать их в production-сборке (`app.New` должен брать `postgres`/`redis` по конфигу).
- Redis: ключи с префиксом по назначению (`verification_code:<email>`), у каждого ключа обязательно TTL.

### 2.7. Composition root (`internal/app`, `cmd`)

- Единственное место, где создаются конкретные реализации и связываются зависимости (ручной DI, без DI-фреймворков и глобальных переменных).
- `main` минимален: `config.Load` → `logger.New` → `app.New` → `app.Run(ctx)`. Контекст должен отменяться по `SIGINT`/`SIGTERM` (`signal.NotifyContext`), а не быть `context.Background()`.
- `app.New` создаёт ресурсы и **не закрывает** те, что нужны во время работы (нельзя `defer conn.Close()` на gRPC-клиенте/пуле внутри конструктора — они понадобятся после возврата). Все ресурсы закрываются в `App.Close()`, который вызывается из `main` через `defer`/после `Run`.
- Graceful shutdown: health → `SERVING`/`NOT_SERVING`, `GracefulStop` с таймаутом и fallback на `Stop`, затем закрытие пулов и клиентов. `App.Run` запускает основной сервер и сервер метрик в `errgroup`: сбой одного (например, занят порт) останавливает другой.
- Адреса других сервисов, TTL, таймауты, порты — в конфиге, а не литералами в `app.go` (запрещено: `grpc.NewClient("localhost:7052", ...)`, `15*time.Minute` прямо в сборке).

### 2.8. Фронтенд (`web/`)

Сайт нарочно простой, в духе соцсетей конца 2000-х: никаких фреймворков, сборщиков и npm.

- **Образец интерфейса — openvk.org, и это обязательно.** Любая новая функциональность, которой нужен фронтенд, делается так, как она устроена в openvk: перед вёрсткой посмотри там тот же элемент — расположение, подписи, ссылки, поведение — и повтори его классами нашего `style.css`. Так, лайк — сердечко со счётчиком справа в подвале записи, комментарии — блок «Комментарии (N)» на странице записи. Отступать от openvk можно только осознанно, с причиной в описании коммита.

## 3. Чистый код (Go)

### 3.1. Общее
- Код должен проходить `gofmt`, `go vet`, `golangci-lint run`. Перед завершением задачи — `make check` в изменённом сервисе, перед коммитом — `make check-integration` из корня (то же, что CI).
- Простота важнее «умности». Не добавляй абстракции, пакеты, интерфейсы и параметры «на вырост». Правило трёх: дублируй до третьего повторения, потом выноси.
- Функция делает одну вещь на одном уровне абстракции. Ориентир: ≤ ~40 строк, ≤ 4 параметра (больше — структура-DTO), вложенность ≤ 3. Используй ранние возвраты (guard clauses), избегай `else` после `return`.
- Не используй `init()`, глобальное изменяемое состояние, `panic` для обычных ошибок (только в тестах и `Must*`-хелперах при старте).
- Не оставляй мёртвый код, закомментированный код, `TODO` без причины и автора/тикета.
- Комментарии объясняют **почему**, а не **что**. Экспортируемые идентификаторы с неочевидным поведением документируются в формате godoc (`// Name ...`). Язык комментариев в коде — английский; текст ошибок и логов — английский.

### 3.2. Нейминг
- Пакеты: короткие, строчные, одно слово, без `_` и без `util`/`common`/`helpers`/`base`. Имя пакета не повторяется в идентификаторе (`user.New`, не `user.NewUser`; `session.Session` допустимо как исключение для основной сущности).
- Конструкторы: `New`, `NewX`. Валидирующие конструкторы возвращают `(T, error)`.
- Интерфейсы: по роли (`Hasher`, `Mailer`, `TokenProvider`, `UserRepository`), без префикса `I` и суффикса `Impl`.
- Ресиверы — короткие (1–2 буквы), одинаковые у всех методов типа. Указатель для сущностей и сервисов, значение — для value objects.
- Ошибки-sentinel: `ErrXxx` (`ErrInvalidCode`, `ErrEmailEmpty`). Типы ошибок: `XxxError`.
- Аббревиатуры в верхнем регистре: `ID`, `URL`, `HTTP`, `JWT`, `SQL`.
- Булевы: `isX`, `hasX`, `canX`. Не называй переменные `data`, `info`, `tmp`, `obj`, `res` без необходимости.
- Файлы: по сущности/ответственности, `snake_case.go` (`political_views.go`). Тесты — `*_test.go` рядом с кодом.

### 3.3. Обработка ошибок
- Ошибки не игнорируются (`_ = f()` допустим только для `Close()` в cleanup и с комментарием/логом).
- Ошибки оборачиваются при **каждой** передаче вверх через `errs.Wrap("<что вызывали>", err)` — по шаблону проекта: `errs.Wrap("s.userRepo.Save", err)`, `errs.Wrap("uuid.Parse", err)`. Текст — это имя вызванной функции/метода, а не «failed to…». Если вызов называется иначе, чем строка (опечатка `s.userRepo.Create` для `Save`) — это баг, строка должна совпадать с реальным вызовом.
- Сравнение — только через `errors.Is` / `errors.As`, никогда по тексту ошибки.
- Не логируй и не возвращай одну и ту же ошибку одновременно: ошибка **либо** обрабатывается, **либо** возвращается. Логируется ошибка один раз — на границе (хендлер/интерсептор/`main`).
- Доменные ошибки — sentinel-переменные в пакете домена, инфраструктурные ошибки переводятся в доменные в репозитории (§2.6). Реализации (`inmem`, `redis`) не должны определять собственные «параллельные» ошибки, отличные от доменных.
- Сообщения ошибок — строчные, без точки в конце, без чувствительных данных.

### 3.4. Контекст, конкурентность, ресурсы
- `context.Context` — первый параметр каждой функции, делающей I/O; не хранится в структурах. Внешние вызовы (БД, Redis, gRPC, SMTP) всегда с таймаутом/дедлайном и реагируют на отмену `ctx`.
- Горутины не запускаются «вхолостую»: у каждой есть владелец, способ остановки и обработка ошибки. Общие данные защищены (`sync.Mutex`/`RWMutex`) или передаются каналами.
- Ресурсы закрываются сразу после успешного открытия через `defer`. Горутины и коннекты не утекают.
- Не делай пакетные глобали вроде `http.DefaultClient` с нулевым таймаутом.

### 3.5. Логирование
- Только `*slog.Logger`, внедряется зависимостью (не глобальный `slog.Default()`). Структурные поля: `log.Error("create user", "error", err, "user_id", id)`. Первый аргумент — **сообщение**, дальше пары ключ-значение (нельзя `log.Error("app.New", err)` — это ломает пары ключ-значение). Где есть контекст запроса — `...Context`-варианты (`log.WarnContext(ctx, ...)`): только так в строку попадает `request_id`.
- Уровни: `debug` — диагностика, `info` — значимые события жизненного цикла, `warn` — восстановимые аномалии, `error` — сбой операции.
- **Запрещено логировать**: пароли, JWT/refresh-токены, коды подтверждения, секреты, полные email/персональные данные в `info`/`error` продакшена. `console.Mailer` с логированием кода допустим только как dev-реализация и не должен подключаться в production.
- Ключи логов — `snake_case`, единообразные по проекту (`user_id`, `session_id`, `request_id`).

### 3.6. Конфигурация
- Все настройки — из переменных окружения, описанных структурой с тегами `env:"NAME,required,notEmpty"` (одного `required` мало: пустое `NAME=` его проходит). Необязательные — с `envDefault`. Каждая переменная добавляется в `.env.example` (без реальных значений, комментарии — отдельной строкой).
- `.env` необязателен: в контейнерах переменные приходят из окружения и имеют приоритет над `.env`.
- Реализации выбираются конфигом: `STORAGE=inmem|persistent` (по умолчанию `inmem` — для разработки ничего запускать не нужно), `MAILER=console|smtp|telegram` (по умолчанию `console`). Зависимости между переменными (например, `persistent` требует `DATABASE_URL`) проверяет `Config.validate()` при старте.
- Секреты (`HASH_SECRET`, ключи JWT, пароли БД, SMTP) никогда не коммитятся; `.env` в `.gitignore`.
- Загрузка и валидация конфига — при старте; приложение падает сразу, если конфиг неверен. Литералы вроде адресов и TTL выносятся в конфиг.

## 4. Данные и миграции

- Схема БД меняется **только** миграциями `goose` в `<service>/migrations` (`make migrate-create name=add_users_table`). Применённые миграции не редактируются — только новые.
- Миграции встроены в бинарник (`migrations/embed.go`) и применяются при старте в режиме `persistent` (`MIGRATE_ON_START`, по умолчанию `true`) под advisory lock PostgreSQL — несколько реплик стартуют безопасно. `make migrate-*` остаются для ручной работы.
- У каждого сервиса своя БД; **нельзя** делать запросы в таблицы другого сервиса или общие JOIN между сервисами — только через gRPC API владельца.
- Каждая миграция имеет рабочие `Up` и `Down`. Миграции обратимо-совместимы с предыдущей версией кода (expand → migrate → contract) для zero-downtime.
- Типы и ограничения: `uuid` для ID, `timestamptz` для времени, `NOT NULL` по умолчанию, `UNIQUE`/`CHECK`/`FOREIGN KEY` — в БД, а не только в коде (уникальность email/nickname гарантируется индексом). Индексы — под реальные запросы.
- Имена: таблицы — множественное число `snake_case` (`users`, `sessions`); колонки — `snake_case`; соответствие полей домена и колонок проверяется тестом/интеграционным прогоном.
- Пагинация в ленте и списках — **keyset (cursor)**, не `OFFSET` (Twitter-подобные ленты растут неограниченно). UUIDv7 удобен как курсор.

## 5. Безопасность

- Валидация **всех** входных данных на границе (value objects). Ничему извне не доверяй, включая данные от других сервисов.
- Аутентификация: access JWT короткоживущий (15 мин), refresh — долгоживущий, хранится в БД **только в виде хеша** (HMAC-SHA256 с секретом). Refresh-токен ротируется при обновлении; повторное предъявление уже ротированного токена завершает всю сессию; `Logout` удаляет сессию. Access-токен stateless и после `Logout` действует до истечения (≤ 15 мин) — это осознанный компромисс.
- Верификация подписи JWT — по **публичному** ключу и только ожидаемым алгоритмом (`WithValidMethods`), проверка `iss`, `exp`, типа токена (`access` ≠ `refresh`).
- Коды подтверждения: криптостойкая генерация (`crypto/rand`), хранятся хешем, имеют TTL, **одноразовые** (удаляются после успешной проверки), ограничено число попыток проверки, ограничена частота запроса нового кода (rate limit по email и IP). Сравнение — `hmac.Equal`/`subtle.ConstantTimeCompare`.
- Частота действий, создающих контент для других (записи, комментарии, лайки, сообщения, загрузки, подписки), ограничена на пользователя (`pkg/ratelimit`, см. §1); новое такое действие без лимита — дыра для спама.
- Ответы не должны позволять перебирать существование аккаунтов (`RequestCode` для любого email отвечает одинаково).
- Межсервисные вызовы — по mTLS (`pkg/mtls`, переменные `TLS_CA_PATH`, `TLS_CERT_PATH`, `TLS_KEY_PATH`): сервер принимает только клиентов с сертификатом внутреннего CA, CN сертификата — идентичность сервиса (`auth`, `user`, `post`, `media`, `notification`, `message`, `club`, `gateway`). Без этих переменных — plaintext, только для локальной разработки; сервис пишет об этом предупреждение при старте. Наружу публикуется только `gateway`.
- Адрес клиента для лимитов: `gateway` берёт его из соединения (или из `X-Forwarded-For`, только при `TRUST_FORWARDED_FOR=true` за своим прокси, крайнее правое значение) и передаёт в `auth` метаданными `authv1.ClientIPMetadata`; `auth` верит им только от mTLS-идентичности `gateway`.
- Ответы API не кешируются (`Cache-Control: no-store`), CORS разрешён только для `CORS_ALLOWED_ORIGINS`.
- Порт метрик (`METRICS_PORT`) наружу не публикуется: метрики раскрывают нагрузку и устройство системы. Метки метрик — только из ограниченных множеств (метод, шаблон маршрута, код), никогда ID, никнеймы или email.
- Секреты и ПДн не попадают в логи, ошибки, ответы API, URL.
- Чувствительные данные профиля (мировоззрение, политические взгляды, отношения, дата рождения — это **специальные категории ПДн**) отдаются другим пользователям только с учётом настроек приватности владельца; по умолчанию не раскрываются. Любой новый эндпоинт, возвращающий профиль, обязан это учитывать.
- Зависимости обновляются осознанно; не добавляй библиотеку, если задача решается стандартной библиотекой за пару десятков строк.

## 6. Тестирование

- Каждое изменение поведения — с тестами. Баг-фикс начинается с теста, воспроизводящего баг.
- Пирамида: много быстрых unit-тестов (домен, сервис), немного интеграционных (репозитории на реальном PostgreSQL/Redis через compose/testcontainers), единичные e2e на gRPC.
- Unit-тесты: табличные (`[]struct{ name string; ... }` + `t.Run`), `t.Parallel()` где безопасно, пакет `<pkg>_test` для проверки публичного API.
- Домен: тестируем конструкторы и граничные значения value objects (пусто, лимит длины, кириллица/эмодзи, пробелы).
- Сервис: зависимости — через порты; используем ручные fake-реализации (`inmem`) или сгенерированные моки; **не мокаем то, чем владеем в домене**.
- Не используем `time.Sleep` в тестах; время и случайность инъецируются.
- Тесты детерминированы и независимы; нет зависимости от порядка и внешней сети. Запуск: `make test` (`go test ./...`), перед PR — с `-race`.
- Интеграционные тесты репозиториев пропускаются без своих переменных: Postgres (`internal/postgres`) — `TEST_DATABASE_URL` (база с применёнными миграциями), Redis (`auth/internal/redis`, `pkg/ratelimit`) — `TEST_REDIS_ADDR`. Проще всего — `make check-integration`: скрипт поднимает временные Postgres 18 и Redis 7 в Docker, создаёт и мигрирует отдельную базу на сервис (общим пакетам, чьи тесты читают `TEST_DATABASE_URL`, — пустую: `pkg/pgpool`, `pkg/outbox` создают свои таблицы сами) и удаляет контейнеры после прогона. Вручную: `TEST_DATABASE_URL=postgres://... TEST_REDIS_ADDR=localhost:6379 go test ./internal/postgres ./internal/redis`.
- Покрытие — не самоцель, но весь бизнес-код (домен + сервис) должен иметь тесты на успешный путь и на каждую ветку ошибки.

## 7. Protobuf / gRPC-контракты

- Файлы — `<service>/api/<service>/v1/<service>.proto`, пакет `<service>.v1`, `go_package = "github.com/vexner67/freenet/<service>/api/<service>/v1;<service>v1"`.
- Сгенерированный код (`*.pb.go`, `*_grpc.pb.go`) **не правится руками** — только `make proto` в сервисе. Генерация закоммичена.
- Совместимость: не менять и не переиспользовать номера полей, удалённые поля — `reserved`; новые поля — только добавлять. Ломающие изменения — новая версия пакета (`v2`).
- Каждое сообщение имеет **свои** номера полей с 1 подряд, без пропусков. Запросы и ответы — отдельные сообщения на каждый RPC (`<Rpc>Request`/`<Rpc>Response`), не переиспользовать доменные сообщения в качестве запроса.
- Enum: нулевое значение — `*_UNSPECIFIED`/`*_NONE`, имена с префиксом типа (`GENDER_MALE`).
- Каждый RPC, объявленный в `.proto`, должен быть реализован хендлером; не оставляем объявленные, но не реализованные методы.
- Удаление RPC или сообщения — ломающее изменение: допустимо, только если у него нет потребителей (так был удалён неиспользуемый `user.Create`); иначе — новая версия пакета.
- Идентификаторы пользователя для бизнес-вызовов берутся из **проверенного JWT** (контекст/метаданные), а не из тела запроса.

## 8. Рабочий процесс

- Перед правкой — прочитай соседний код сервиса и следуй его стилю; новое решение должно выглядеть так, будто его написал автор остального кода.
- Изменения минимальны и сфокусированы: одна задача — один коммит/PR. Не смешивай рефакторинг с фичей.
- Порядок разработки новой фичи «изнутри наружу»: домен → use case (+порты) → инфраструктура (+миграция) → транспорт (`.proto`, хендлер, mapper) → сборка в `app` → тесты на каждом шаге.
- Команды (из каталога сервиса):
  ```bash
  make run         # запуск сервиса
  make build       # сборка
  make test        # тесты
  make fmt         # go fmt
  make lint        # golangci-lint
  make check       # fmt + lint + test (обязательно перед коммитом)
  make proto       # перегенерация protobuf
  make tidy        # go mod tidy
  make migrate-create name=<name> / migrate-up / migrate-down / migrate-status
  ```
  Из корня: `make dev` / `make dev-persistent` — весь бэкенд; `make check` / `make check-integration` — проверки всех модулей и сайта, как в CI; `make check-proto` — сгенерированный protobuf-код против `.proto`; `make stack` / `make smoke` — весь сайт в Docker и его сквозная проверка; `make up` / `make ps` / `make down` — docker compose (`down` останавливает и стек); `make certs` — dev-сертификаты для mTLS и JWT-ключи; `make web-test` — тесты сайта; `make ssh` — вход на прод-сервер (root по ключу `~/.ssh/freenet-prod_ed25519`, одно соединение на 10 минут; `PROD_HOST`, `PROD_KEY`).
- Локальный запуск всего бэкенда и сайта одной командой из корня: `make dev` (`scripts/dev.sh`) — собирает и запускает `notification`, `message`, `user`, `post`, `media`, `auth`, `gateway` с их `.env`, выводит логи с метками сервисов, Ctrl+C останавливает всё штатно; если один сервис упал, останавливаются и остальные. По умолчанию `STORAGE=inmem` и без mTLS — ничего, кроме Go, не нужно. `make dev-persistent` сначала поднимает Postgres и Redis (`docker compose up -d --wait`) и переключает сервисы на них. Новый сервис добавляется в массив `services` скрипта. Отдельный сервис по-прежнему можно запустить `make run` в его каталоге.
- Общий код между сервисами — только в `pkg/<name>` как отдельный модуль (с `go.mod`), добавленный в `go.work`. Это должны быть **маленькие технические** пакеты без бизнес-логики. Бизнес-логику между сервисами не шарим — общаемся по gRPC. Сервис не импортирует `internal/` другого сервиса; импорт чужого `api/` (proto-клиента) разрешён только из инфраструктурного адаптера.
- Коммиты — в стиле истории репозитория: Conventional Commits (`feat:`, `fix:`, `chore:`, `refactor:`, `test:`, `docs:`), краткое описание в повелительном наклонении, английский язык.
- Не коммить `.env`, ключи, бинарники, `.idea/`. Не меняй `go.work.sum`/`go.sum` вручную — только через `go mod tidy`/`go work sync`.
- Не используй `git push --force`, не переписывай историю общих веток.

### Definition of Done
- [ ] Соблюдено правило зависимостей слоёв (§2.1), нет proto/SQL/драйверов не в своём слое.
- [ ] Все ошибки обёрнуты `errs.Wrap`, нет проглоченных, в gRPC мапятся в корректные коды (§2.5).
- [ ] Входные данные валидируются value objects; секреты/ПДн не попадают в логи.
- [ ] Есть тесты (успех + ветки ошибок), `make check-integration` из корня проходит (как CI).
- [ ] Новый сервис или переменная окружения добавлены и в `compose.yaml` (профиль `app`), и стек проходит `make stack && make smoke`.
- [ ] Миграция (если нужна) с `Up`/`Down`; `.env.example` обновлён; `.proto` совместим и перегенерирован (`make check-proto`).
- [ ] Новый код собран в `app` и действительно используется (нет мёртвых реализаций и неподключённых RPC).
- [ ] Если фича видна на сайте — интерфейс сделан по образцу openvk.org (§2.8), страницы проверены в браузере.

## 9. Известные отклонения текущего кода (исправлять при касании)

Это не образец для подражания, а технический долг — не копируй эти паттерны:

1. Docker, CI и прод: образы в GHCR не подписаны, нет манифестов для оркестратора (Kubernetes) — прод один сервер с docker compose; нет резервных копий баз и `.data/media` (pg_dump по расписанию и копия на другой машине); деплой перезапускает изменившиеся сервисы — секунды простоя, без rolling update; Prometheus/Grafana на сервере видны только через SSH-туннель, алерты уходят только в Telegram (нет почты и дежурств), а Alertmanager на сервере один — без кластера; `make check-integration` требует на машине разработчика protoc и его плагины ровно тех версий, что в `scripts/check-proto.sh`, а флаги генерации записаны дважды — в `Makefile` сервисов и в этом скрипте; `make stack` собирает образы без кеша между запусками CI.
2. Сайт хранит токены в `localStorage`, защищаясь строгой CSP. Если на страницах появится сторонний код (счётчики, виджеты), перейти на httpOnly-cookie для refresh-токена.
3. Сертификаты из `make certs` — только для разработки: нет ротации, отзыва и управляемого PKI для продакшена.
4. Наблюдаемость: нет распределённой трассировки (OpenTelemetry) — путь запроса восстанавливается только по `request_id` в логах; нет сбора логов в одно место (Loki и т. п.); алерты доходят только до одного чата Telegram, и только с сервера (локальный стек никого не оповещает); шаблон сообщения — стандартный английский Alertmanager; у Postgres и Redis наблюдаются только доступность, соединения, размер и память — нет алертов на медленные запросы, блокировки, раздувание таблиц и место на диске (нет `node_exporter`: диск, память и CPU самого сервера не видны), у Redis нет предела памяти, а экспортёров семь контейнеров (по одному на базу); алерты баз не глушат ошибки сервиса, который без базы не работает, — придут оба; у Grafana пароль `admin` по умолчанию, хранилище — volume стека; метрики только серверные и outbox — нет метрик gRPC-клиентов, пулов БД и Redis; сайт не показывает ID запроса в тексте ошибки.
5. `pkg/pgpool.Migrate` проверен только сквозным прогоном, своего интеграционного теста нет.
6. Сайт: «о сайте», «правила» и «помощь» — статические страницы в `web/`: их тексты правятся в HTML, а не в базе знаний, как статьи openvk; правила — переложение правил openvk без наказаний, которых у нас нет (блокировок), их стоит перечитать владельцу; на «о сайте» нет «активных пользователей», списка администраторов, ссылок и популярных групп openvk, а счётчики читают таблицы целиком при каждом открытии; в подвале нет «блога», «разработчикам», «приватности» и выбора языка; «помощь» — вопросы и ответы, а не обращения в поддержку (`/support` openvk).
7. Записи: обрезанный текст кончается на 1000-м символе, даже посреди слова или обращения `[никнейм|Имя]` (в свёрнутом виде конец не виден), и поиск по стене находит запись по словам, которых в начале нет, а поле ввода растёт без предела высоты, как в openvk; история правок не хранится (видно только «ред.»), правка не обновляет записи, уже открытые у других, и не уведомляет тех, кто лайкнул или прокомментировал; поделиться можно на свою стену, в группу и в переписку; фото к своим словам прикладываются только к репосту записи, не к фото альбома; в выборе переписки — только последние диалоги, без «Избранного» openvk; «кто поделился» — наша подсказка над «Поделиться» (в openvk списка нет), она встаёт правым краем к ссылке и у левого края страницы заходит на меню, репосты удалённых страниц и архивные в ней пропущены, но посчитаны; удалённая запись забирает уведомления не больше чем о 1000 последних репостов, а стёртая вместе со страницей — не забирает; фото альбома в переписке получатель видит, даже если альбом от него скрыт, и каждое читается отдельным запросом; «Понравилось N людям» — подсказка над сердечком и окно со всеми, но без отдельной страницы `/wall…/likes` openvk, и лайкнувшие удалённые страницы в нём пропущены, но посчитаны; упоминания: назвать можно только человека и только по никнейму (`[никнейм|Имя]` и `@никнейм`; у openvk — ещё `@id1 (Имя)`, `*id1` и группы), не больше 10 в тексте; не уведомляют упоминания в предложенной записи (и в записи, опубликованной из неё) и личном сообщении, а ссылками они становятся только в записях, комментариях (и к фото), сообщениях тем и предложенных записях; правка, убравшая имя из записи, уведомление не забирает, а правка, назвавшая владельца чужой стены, его не уведомляет (он слышал о записи); есть ли страница у `@слова`, сайт узнаёт после отрисовки — ссылка на никого на мгновение видна, это ещё один запрос на страницу с упоминаниями, а в цитатах уведомлений `[никнейм|Имя]` читается «Имя», есть такой человек или нет; текст уведомления — наш («Анна упомянула вас в записи»), а не «Вас упомянул пользователь … в посте или в одной из веток его обсуждения» openvk; «в ответ» ведёт на комментарий, только если он уже загружен на странице; опросы: «Список проголосовавших» — окно, как у лайков, по одному варианту, а не страница с вкладками openvk, и проголосовавшие удалённые страницы в нём пропущены, но посчитаны; «Прикрепить опрос» — ссылка рядом с «Прикрепить фотографию», а не пункт меню «Прикрепить»; срок — галочка и число дней от 1 до 31; предел темы и варианта (128 символов) — наш; нет «Получить код» (встраивание опроса на другие сайты); опрос нельзя приложить к репосту, предложенной записи и при правке, а приложенный — изменить или убрать, не удалив запись; результаты до голосования сайт не показывает, но API отдаёт счётчики всем; процент считается от проголосовавших, поэтому при множественном выборе сумма больше 100; опрос открытой страницы не обновляется сам; в переписке вложенная запись показывает опрос и принимает голос, но в живом событии выбор зрителя не сказан (до перезагрузки там форма, и повторный голос молча отклоняется); голоса удалённой, но ещё не стёртой страницы остаются в счётчиках, а записи, отклонённые проверкой (пустая тема), всё равно тратят лимит записей; закрытие комментариев записи — наше (в openvk его нет): только по одной записи, без настройки на всю стену; в «Архиве записей» год записи считается по UTC (запись в первые часы 1 января по местному времени попадает в прошлый год), при «Всех годах» «Действия» относятся к самому новому году стены (openvk меняет год, пока архив листают), «Разархивировать все записи целиком» нет и в openvk (через API — `DELETE` без `year`), перед действием — наше окно подтверждения вместо `confirm` браузера, а после действия за год, в котором записей не было, открывается пустой архив этого года; «Поиск» по стене — подстрока текста без индекса (записи одной стены), подсвечена только подстрока запроса и только в тексте самой записи (не во вложенной записи репоста и не в упоминаниях), а в длинной записи, пока она свёрнута, найденное может быть не видно, и ищет только во «Всех записях» (через API — и в архиве); у страницы стены нет ссылки на RSS, а вкладка своих записей склоняет имя («Записи Анны», в openvk — «Записи Анна»); лента, в отличие от openvk, показывает и записи подписок на чужих стенах; чёрный список скрывает в ней записи человека, но не репосты его записей, не его комментарии под записями («Микроблог») и не записи тех, кто внёс в чёрный список самого читателя. Миграция `wall_id` в `post` сразу ставит `NOT NULL`: старая версия `post`, не пишущая `wall_id`, во время выкладки не сможет создавать записи (не expand → contract — выкладок ещё не было). Родительный падеж имён (`genitiveName`) — по окончаниям: редкие имена с беглой гласной вне таблицы исключений (Лев, Павел, Пётр) склоняются неверно.
8. Лента собирается при чтении (fan-out on read) и берёт не больше 1000 последних подписок; при росте — заранее собранные ленты. «Все новости»: нет настройки «не показывать мою страницу в глобальной ленте» (и «Не отображать публикации в глобальной ленте» у групп) — туда попадают записи всех страниц и групп, и страниц «только для пользователей» тоже (лента открыта лишь вошедшим), а с чужими записями на стенах, как в openvk по умолчанию, — и записи на стенах таких страниц; записи удалённых страниц gateway убирает уже из готовой страницы, так что она бывает короче; форма над лентой пишет только на свою стену, без выбора группы; «Показать предыдущие записи» вместо страниц. «Настройки ленты»: нет «Начинать со страницы» (у нас не страницы, а «Показать предыдущие записи») и выбора числа записей под лентой — оно только в окне; число записей и «Показывать посты на чужих стенах» хранит браузер (на другом устройстве — по умолчанию: 20 записей, как было, у openvk 10), а «Показывать игнорируемые источники» действует и в «Моих новостях» (у openvk — только во «Всех»); игнорируемый источник убирает стену, а не автора: записи игнорируемого человека на стене того, кого читатель читает, остаются, как в openvk; «Игнорировать» — только ссылкой на странице человека или группы, в меню записи в ленте её нет (у openvk есть), у встречи она подписана «Игнорировать встречу»; игнорировать можно и того, на кого не подписан (это действует во «Всех новостях»), а openvk не даёт игнорировать тех, кто скрыт из глобальной ленты, — у нас такой настройки нет; список — имена без «Онлайн» и без страниц, удалённая страница в нём подписана «(страница удалена)»; страница человека и группы — ещё один запрос за игнорируемыми, как и каждая страница ленты; новая запись из формы над лентой показывается и при настройках, которые её скрыли бы.
9. Фото: ориентация — только из EXIF в JPEG (PNG и WebP с меткой `Orientation` не поворачиваются; HEIC не принимается вовсе); `media` хранит файлы в каталоге `MEDIA_DIR` — это один узел, для нескольких реплик нужен S3 за теми же портами `AvatarStore`/`PhotoStore`; чистка неопубликованных обходит `uploads` и `retired` целиком (на S3 — правило жизненного цикла бакета); пока outbox `post` → `media` стоит дольше `UNPUBLISHED_PHOTO_TTL`, фото уже опубликованной записи — битая картинка (оно отложено и вернётся с доставкой), а простоявший дольше `RETIRED_PHOTO_TTL` теряет его совсем; брошенные загрузки занимают диск 30 дней вместо суток; одно фото можно приложить к двум записям через API (сайт так не делает) — удаление одной заберёт его и у другой; запись, отклонённая после проверки фото (например, лимитом частоты), фото не публикует — оно ждёт повторной попытки сутки; фото, загруженные до разделения на `uploads`/`photos`, считаются опубликованными; одно фото через API можно положить и в запись, и в альбом — удаление одного заберёт файл у другого; очистка страницы удаляет чужие комментарии к её записям без блокировки записей (`DeleteOnPostsOf`), так что комментарий, написанный в ту же секунду, может уйти каскадом без своих фото; откат миграции фото сообщений пишет в сообщения из одних фото текст «Фотография».
10. Уведомления: старые уведомления не удаляются со временем. Outbox: доставляет один relay на поток по одной записи — пропускная способность ограничена задержкой `Notify` (достаточно, пока `notification` отвечает за миллисекунды); запись, которую `notification` упорно отвергает «временной» ошибкой, держит все следующие (видно по `outbox_lag_seconds`, алерты `OutboxLagging`/`OutboxStuck`); порядок — по `id`, выданному при вставке: две транзакции, закоммиченные не в том порядке, в каком вставляли, доставятся в порядке вставки (для одного лайка и его отмены это не важно — их делает один пользователь последовательно); доставленные записи удаляются, истории нет; в `inmem` запись не откатывается вместе с изменением.
11. Сообщения: живые события несут сообщения целиком, до 60 000 символов и с пересланными; найденное поиском сообщение несёт отрывок вокруг первого совпадения (1000 символов), не говоря, что начало обрезано; «Показать больше» в диалоге открывает сразу все тексты сообщения, свой и пересланные; отредактированное сообщение собеседник видит без истории правок; правка заменяет фото списком целиком, и два окна, правящие одно сообщение, затрут друг друга; начав правку, человек теряет фото, которые прикрепил к ещё не отправленному сообщению; порядок фото при правке меняется, только если убрать фото и приложить заново; удаление пачкой — не больше 100 сообщений за запрос (сайт режет выделенное на такие части), и одно уже исчезнувшее сообщение отменяет всю пачку — сайт тогда удаляет по одному; пересылка: не больше 20 сообщений за раз, считая те, что они несут сами, и без вложенности (пересланное пересланного разворачивается в один ряд — у ВКонтакте вложено), пересылающее сообщение — только слова и пересланные (фото к нему приложить можно лишь правкой или через API), в окне человека без диалога находят по имени (первая страница поиска людей), а можно ли ему писать, скажет только отправка, копия фото появляется через outbox — первые мгновения картинка может быть битой, а когда страницу автора пересланного стёрли или удалили, его сообщение из пересланных пропадает («Пересланное сообщение недоступно.»); поиск в пересланных — перебор `jsonb` без индекса, находит и по пересланному, автора которого уже не показывают (строка поиска тогда говорит собственные слова сообщения), а в строке — только первое пересланное со словами запроса; найденное сообщение открывает диалог вокруг себя и раскрытым целиком, слова подсвечены только подстрокой запроса, а отправка из такого диалога, пока он не долистан до конца, перезагружает его с конца; поиск — подстрока без морфологии, и по всем диалогам читает сообщения человека перебором по двум индексам; `read` у найденных сообщений и в событии `edit` не говорится; кто удалил у себя все входящие от человека, теряет право ответить ему при настройке «никто»; забранное сообщение остаётся «Сообщение удалено» у обоих, и у отправителя тоже (ВКонтакте убирает его совсем — у нас так сделано нарочно, чтобы собеседник видел, что что-то было), не говорит, что в нём было, считается непрочитанным, пока его не откроют, и выделяется вместе с остальными, хотя переслать его нельзя; откат миграции удаляет забранные и состоящие из одних пересланных сообщения; из вложений — только фото; лайки и репосты чёрный список не закрывает; при отказе в подписке через API клиент получает общее «permission denied» (gateway не пропускает тексты `PermissionDenied`).
12. Защита от спама: только ограничение частоты на пользователя — нет фильтров содержимого (ссылки, повторы одного текста), жалоб, модерации и бана; новый аккаунт ограничен так же, как старый; фиксированные окна пропускают до двойного лимита на стыке окон.
13. Живые события: каждое событие получает каждая реплика (один канал Redis на сервис) — при большом числе реплик и событий нужны каналы по пользователю или брокер с маршрутизацией; публикация в Redis синхронная, в запросе (до 2 с при недоступном Redis); при недоступном Redis страница каждые несколько секунд переподключается и снова получает 1013; события не хранятся и не переигрываются — после разрыва страница догоняет обычными запросами; удаление записи (`ForgetPost`) не обновляет счётчик ответов сразу; WebSocket не проверялся за обратным прокси (нужны заголовки `Upgrade`/`Connection` и долгий таймаут).
14. Анкета: семейное положение партнёр не подтверждает и не видит у себя (как в openvk); имя после предлога не склоняется («замужем за Пётр Петров» — так и в openvk), а родительный падеж (`genitiveName`) склоняет «они/их» как мужское имя; ссылки поиска — только у родного города, города, фильмов, ТВ-шоу и книг (в openvk музыка ведёт в поиск аудиозаписей, а у нас их нет); фильтр по фильму, ТВ-шоу или книге короче трёх символов триграммный индекс не обслуживает — перебор; нет «Телефона» (у openvk — с подтверждением по SMS) и «Транслировать музыку в статус»; «Аватар» в настройках — то же окно, что на странице, а не форма «Обзор» openvk.
15. Удаление страницы: нет «Рассказать друзьям» openvk (запись с причиной на стене) — записи удалённой страницы скрыты, её никто бы не увидел; лайки удалённой, но ещё не стёртой страницы остаются в счётчиках; при очистке пропадают и чужие записи на стене стёртого пользователя (с их фото); сессии стёртого пользователя лежат в `auth`, пока их не обновят или не истечёт refresh-токен (в них только ID); причину удаления хранят до очистки, но нигде не показывают; очистка `user` — одна транзакция на пачку из 100 страниц, `ForgetPost` (и `DeletePublishedPhotos` для чужих записей с фото) пишется по записи на каждую удалённую запись.
16. Сообщества: нет сообщений группы и «Местоположения»; должность и «Скрыт» уходят одним запросом, так что двое руководителей, правящие одного человека одновременно, затрут друг друга, а пустую должность задают пустым полем, без отдельного «удалить комментарий»; скрытый руководитель не виден и в «Создателе» (openvk создателя показывает всегда), а когда скрыты все, «Список админов» сам на «Ничего не отображать» не переключается; скрытого руководителя всё ещё выдаёт «Подпись автора» под его записью от имени группы; уведомление о назначении называет группу, а не того, кто назначил, и остаётся, если администратор сам вышел из группы; `club` стал вести outbox — его поток не покрыт сквозной проверкой `make smoke`. Встречи: адрес встречи — тот же `/club/<адрес>`, а не `/event<id>` openvk; ответ «Я приду»/«Возможно приду» меняется второй кнопкой (в openvk — только выйдя), а повторное «вступить» без `maybe` от старого клиента делает «возможно» точным; в списках встреч ссылки — наши («Просмотр встречи», «Я не приду»; у openvk своих нет), из чужого списка на встречу записываются только точно, а поиск групп находит и встречи — отдельного «Поиска встреч» нет; блок «Встречи» на странице человека показывает только предстоящие (у openvk — все), и человек, у которого остались одни прошедшие, блока не имеет (они — по «Все» и «Прошедшие»); закрытых встреч и приглашений нет (в openvk тип есть, включить его негде); напоминание о встрече — одно, за сутки, и не больше чем 1000 участникам: вступивший после него не услышит ничего, вышедший из встречи сохраняет своё, а встреча, созданная меньше чем за сутки до начала, напоминает о себе сразу; других уведомлений участникам нет; «Прошедшие» — наша вкладка (в openvk её нет), а во вкладке «Управляемые» прошедшие и предстоящие вместе; встреча без окончания считается прошедшей с начала, как в openvk; владелец всегда «придёт точно»; время встречи вводится и показывается в часовом поясе браузера, пояс самой встречи не хранится; откат миграции встреч удаляет их. Уведомление о новой предложенной записи приходит на каждое предложение (в openvk одно «новые записи в предложке» на группу) и не больше чем 100 руководителям; предложенные записи открываются отдельной страницей, а не подгружаются над стеной по щелчку, при публикации можно поправить только текст, не фото, а ссылка «N предложенных записей» — ещё один запрос на странице группы; передача группы не спрашивает пароль, как openvk, — паролей у нас нет, вход по коду на почту, только окно подтверждения; в чужом списке групп «Вступить в группу»/«Выйти из группы» — ссылки, а не кнопки openvk, и ещё один запрос на страницу списка, как и роли для ленты; окно загрузки фото выбирает только квадрат (у openvk область любой формы — у нас аватарки квадратные), поворот сбрасывает выбранный квадрат, нет снимка с веб-камеры, а повороты — кнопки под картинкой, а не значки на ней; новая запись о фото появляется на стене после перезагрузки, как в openvk; группу нельзя удалить (как и в openvk); группу стёртого владельца наследует старший администратор, а без администраторов — старший участник, который об этом не просил и уведомления не получает; группа, где больше никого не было, остаётся без владельца навсегда; адрес группы — отдельное пространство (`/club/<адрес>`), а не общее с никнеймами, как короткие адреса openvk; записи участников на стене группы никого не уведомляют; фото записи «От имени сообщества» лежат под ID автора, и их адрес его выдаёт; такие записи уходят вместе со стёртым автором (его фото media стирает всё равно); лента берёт не больше 1000 последних групп читателя. Фон (групп и людей): схема в настройках нарисована нашими блоками, а не картинкой openvk; изменения видны сразу, без «через 5 минут». Закрытых групп с заявками нет и в openvk: флаг `closed` у него есть, но включить его негде. Обсуждения: нет «Создать тему в чате»; о новом сообщении слышит только начавший тему — «Ответить» подставляет обращение без ссылки на сообщение — тот, кому ответили, слышит об этом как об упоминании, а на тему нельзя подписаться; уведомление (о сообщении, сердечке и упоминании) цитирует сообщение, но ведёт к теме, а не к сообщению; тему уведомления gateway читает отдельным запросом на каждую; вместо значка закреплённой темы — «— закреплена»; тема с удалённым сообщением остаётся там, куда её подняло это сообщение; темы и сообщения удалённых страниц скрыты, но посчитаны; отказы `post` (закрепить, ограничить, писать в ограниченную тему) сайт видит общим «Недостаточно прав» — форма их и не предлагает; поиск — подстрока заголовка без индекса (темы одной группы); блок на странице группы — ещё один запрос. ## 10. Состояние работы и что дальше (для следующего агента)

Раздел обновляет агент, заканчивающий сессию. Последнее обновление — 2026-10-11.

### 10.1. Как работать с владельцем проекта

- Отвечай по-русски. Код, комментарии, тексты ошибок и коммиты — по-английски (§3).
- **Коммит и пуш — только по команде «коммит + пуш».** До неё изменения остаются в рабочем дереве: доделай, проверь и отчитайся.
- Коммиты делятся по слоям, по одному на сервис или слой, обычно в порядке «домен и сервис → `media`/другие сервисы → `gateway` → `web` → `docs: …` (AGENTS.md)». Ломающее изменение proto (удалён RPC, поле, сменился тип) идёт в одном коммите с gateway, который его использует. **Каждый коммит обязан собираться и проходить тесты сам по себе**: проверь цепочку перед пушем, например так:
  ```bash
  base=<последний запушенный коммит>; w=$(mktemp -d)/wt; git worktree add -q --detach "$w" HEAD
  for c in $(git rev-list --reverse "$base"..HEAD); do git -C "$w" checkout -q "$c"
    for m in $(sed -n 's|^\t\./||p' "$w/go.work"); do (cd "$w/$m" && go build ./... && go vet ./... && go test ./... >/dev/null) || echo "FAIL $c $m"; done
  done; git worktree remove --force "$w"
  ```
- Перед пушем — `make check-integration` из корня (то же, что CI). После пуша дождись CI (`gh run watch <id> --exit-status`) и скажи, прошёл ли деплой.
- Conventional Commits без scope (`feat: …`, `fix: …`, `docs: …`), повелительное наклонение, тело — что и почему. Отличия интерфейса от openvk перечисляются в теле коммита сайта («Deviations from openvk: …»). В конце — строка `Co-Authored-By:` агента.
- Пушим прямо в `main`, без force push и переписывания истории.
- Сайт повторяет openvk.org (§2.8): прежде чем верстать, посмотри тот же элемент в исходниках openvk — `gh api repos/OpenVK/openvk/contents/<путь> --jq .content | base64 -d`. Нужное: `Web/Presenters/templates/**.latte` (страницы), `locales/ru.strings` (подписи), `Web/static/js/al_wall.js` (лайки, «Поделиться», окна), `Web/static/css/main.css`.
- **Жалоб, модерации и бана владелец не хочет** — не предлагай и не делай.
- Безопасность: пароли от серверов не используются, вход только по SSH-ключам. Токены и секреты (Telegram, SMTP) владелец кладёт на сервер сам — не проси присылать их в чат.

### 10.2. Прод

- Сервер `31.57.28.32`, сайт https://freenet19.fun. Каждый пуш в `main`, прошедший CI, сам выкатывается (§1, «Деплой»).
- `make ssh` — root по ключу `~/.ssh/freenet-prod_ed25519`. Деплой ходит под пользователем `freenet` с ключом `~/.ssh/freenet-deploy_ed25519`; ufw ограничивает частоту SSH-соединений, держи одно переиспользуемое.
- Письма не отправляются: с `MAILER=console` коды входа видны только в `docker compose logs auth` на сервере, с `MAILER=telegram` приходят владельцу в чат алертов (переменная — в `/opt/freenet/.env`, применить — `docker compose up -d auth`). Новый человек получает код от владельца — см. 10.4.

### 10.3. Как проверять локально

- `make dev` поднимает весь стек в памяти (`STORAGE=inmem`), сайт — на http://localhost:8080. Логи — в выводе команды, коды входа — в строках `auth` вида `email=… code=123456`.
- Сквозные проверки удобно писать скриптом на Python (`urllib`): регистрация по коду из лога (`POST /api/v1/auth/code`, затем `/auth/verify`), заполнение профиля (`PUT /api/v1/me/profile`), дальше — запросы фичи. Лимит на запрос кода быстро даёт 429: делай паузу или используй уже выданные токены.
- Войти в браузере без кода: обнови токены (`POST /api/v1/auth/refresh` с refresh-токеном), положи их в `localStorage` под ключом `freenet.tokens` (JSON `{"accessToken","refreshToken"}`) и перезагрузи страницу.
- Страницы проверяй в браузере при ширине 900–1400 px. Подсказки по наведению эмулятор браузера срывает: вызывай `mouseenter` из JavaScript.
