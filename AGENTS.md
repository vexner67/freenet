# AGENTS.md — правила разработки бэкенда Freenet

Freenet — социальная сеть наподобие Twitter. Бэкенд: набор Go-микросервисов в монорепозитории (`go.work`). Снаружи доступен только `gateway` (REST/JSON, контракт — `gateway/api/openapi.yaml`); внутренние сервисы общаются по gRPC поверх mTLS.

Этот файл — источник правил для людей и AI-агентов. Перед изменением кода прочитай его целиком. Если правило конфликтует с существующим кодом — прав правило, код нужно привести к нему (но не рефакторь чужой код «заодно», см. раздел «Рабочий процесс»).

---

## 1. Стек и структура репозитория

- Язык: Go (версия — из `go.work`). Транспорт: gRPC + protobuf. БД: PostgreSQL (`pgx/v5`, `pgxpool`), Redis (`go-redis/v9`) для эфемерных данных (коды, счётчики лимитов) и живых событий между репликами (pub/sub).
- Конфиг: `caarlos0/env` + `godotenv`. Логи: стандартный `log/slog`. Миграции: `goose`. JWT: `golang-jwt/jwt/v5` (RS256).
- Модуль каждого сервиса: `github.com/vexner67/freenet/<service>`, общие модули: `github.com/vexner67/freenet/pkg/<name>`.

```
freenet/
├── go.work                  # workspace: все сервисы и pkg/*
├── compose.yaml             # postgres на каждый сервис, redis; сервисы и Prometheus — в профиле app
├── monitoring/             # наблюдаемость стека: prometheus.yml (что собирать), alerts.yml (+ alerts_test.yml),
│                            # alertmanager.yml (кого оповещать), grafana/ (источники данных и дашборд)
├── Dockerfile               # образ любого сервиса: --build-arg SERVICE=<имя>
├── Makefile                 # dev, check, stack, smoke, certs, docker compose up/ps/down
├── .github/workflows/ci.yml # CI: make check-integration, make stack + make smoke; на main — образы в GHCR и деплой
├── deploy/                  # прод: compose.prod.yaml (поверх compose.yaml), Caddyfile, bootstrap.sh (сервер), deploy.sh
├── scripts/
│   ├── dev.sh               # весь бэкенд локально (make dev)
│   ├── check.sh             # проверки всех модулей, как в CI (make check)
│   ├── smoke.sh             # сквозная проверка запущенного стека (make smoke)
│   └── gen-certs.sh         # dev CA, mTLS-сертификаты и JWT-ключи → certs/ (в .gitignore)
├── pkg/                     # ОБЩИЕ модули (каждый — отдельный go.mod)
│   ├── errs/                #   errs.Wrap
│   ├── logger/              #   slog-логгер из конфига
│   ├── hmac/                #   HMAC-хешер
│   ├── envconfig/           #   загрузка конфига: необязательный .env + env + Validate()
│   ├── pgpool/              #   пул PostgreSQL, goose-миграции при старте, транзакции в контексте (TxManager, Conn)
│   ├── pubsub/              #   события подписчикам по ключу (пользователю): в процессе (Hub) и между репликами (Redis)
│   ├── outbox/              #   надёжная доставка другому сервису: запись в транзакции изменения, relay с повторами
│   ├── reqid/               #   ID запроса: контекст, X-Request-ID, gRPC-метаданные, request_id в логах
│   ├── metrics/             #   реестр Prometheus и отдельный порт /metrics
│   ├── ratelimit/           #   счётчики событий в фиксированных окнах: в памяти или в Redis
│   ├── grpcserver/          #   gRPC-сервер: health и Probe, reflection, request ID, метрики, graceful stop, ErrorInterceptor
│   ├── mtls/                #   mTLS между сервисами, идентичность вызывающего, RestrictMethods
│   └── jwtauth/             #   формат JWT, проверка токенов, gRPC-интерсептор аутентификации
├── web/                     # сайт в стиле old web: HTML + CSS + JS-модули без сборки
├── gateway/                 # публичный REST/JSON API (BFF) и раздача web/, единственная точка входа снаружи
├── auth/                    # сервис аутентификации (коды по email, JWT, сессии)
├── user/                    # сервис пользователей (профиль, приватность, подписки, поиск)
├── post/                    # сервис записей: стена, лайки, комментарии
├── media/                   # сервис фото: аватарки и фото записей — проверка, обрезка, хранение, выдача
├── notification/            # уведомления («Мои Ответы»): лайки, комментарии, подписки
├── message/                 # личные сообщения («Мои Сообщения»): диалоги, прочитанное
└── club/                    # сообщества («Мои Группы»): группы, участники, руководство
```

Поток запроса: браузер → `gateway` (страницы из `web/` и HTTP/JSON API на одном origin) → `auth`/`user`/`post`/`media`/`notification`/`message`/`club` (gRPC + mTLS); `auth` → `user`, `post` и `user` → `notification`, `post` и `message` → `media` (фото опубликованных и удалённых записей, комментариев и сообщений), `post` → `club` (кто модерирует стену группы и кому сообщать о предложенных записях), `user` → `post`/`media`/`message`/`club` (очистка удалённых страниц) (gRPC + mTLS, внутренние RPC). Порты по умолчанию: `auth` 7051, `user` 7052, `post` 7053, `media` 7054, `notification` 7055, `message` 7056, `club` 7057, `gateway` 8080; метрики — на «девятке» с теми же последними цифрами (`METRICS_PORT`: 9051–9057, у `gateway` 9080). Порты сервисов — только ниже 32768: выше начинаются диапазоны, из которых ОС раздаёт порты исходящим соединениям (macOS — 49152–65535, Linux — 32768–60999), и любой процесс может случайно занять такой порт — сервис тогда не стартует с `address already in use` (так было с привычными для gRPC 50051–50056).

Структура одного сервиса (эталон — `user/` и `auth/`):

```
<service>/
├── api/<service>/v1/        # .proto + сгенерированный код (*.pb.go, *_grpc.pb.go)
├── cmd/<service>/main.go    # только точка входа
├── internal/
│   ├── <domain>/            # доменный слой: сущности, value objects, доменные ошибки
│   ├── service/             # прикладной слой (use cases) + DTO + порты (интерфейсы)
│   ├── grpc/                # транспорт: хендлеры + mapper.go (proto <-> домен)
│   ├── postgres/            # реализации репозиториев на PostgreSQL
│   ├── redis/               # реализации на Redis
│   ├── inmem/               # in-memory реализации (dev/тесты)
│   ├── config/              # конфигурация из окружения
│   └── app/                 # composition root: сборка зависимостей, Run/Close
├── migrations/              # goose SQL-миграции + embed.go (встраиваются в бинарник)
├── .env.example
└── Makefile                 # run build test fmt lint tidy proto check migrate-*
```

Новый сервис создаётся копированием этой структуры, добавляется в `go.work` и `compose.yaml` (своя БД на сервис и сам сервис в профиле `app`), в `scripts/dev.sh`, получает сертификат в `scripts/gen-certs.sh`, порт метрик и цель в `monitoring/prometheus.yml` (и в список `services` `scripts/smoke.sh`) и строится на `pkg/grpcserver`, `pkg/envconfig`, `pkg/mtls`.

Docker: один `Dockerfile` на все сервисы (контекст — корень репозитория из-за `go.work` и `pkg/*`): статический бинарник (`CGO_ENABLED=0`, `-trimpath`; Go собирает на платформе сборщика под целевую — `--platform linux/amd64` на Mac с arm64 не эмулирует компилятор) в distroless `static:nonroot`, модули и кеш сборки — в cache mount BuildKit; у `gateway` своя цель `--target gateway` с сайтом в `/web`. `make stack` поднимает весь сайт в Docker на тех же базах, что `make dev-persistent`, с mTLS между сервисами и JWT-ключами из `certs/` (`make certs`), `HASH_SECRET` — в корневом `.env`. Контейнеры работают от имени пользователя, запустившего `make stack` (`FREENET_UID`/`FREENET_GID`): так они читают ключи с правами 600 и пишут фото в `.data/media`. `make smoke` (`scripts/smoke.sh`) регистрирует пользователя и проходит через все сервисы (код входа — из `docker compose logs auth`), затем проверяет наблюдаемость: все контейнеры здоровы, ID запроса из ответа gateway — в строке лога `auth`, Prometheus собирает метрики всех сервисов, правила алертов загружены и работают, Alertmanager готов, в Grafana есть дашборд и его источник данных отвечает. В образе нет оболочки и curl, поэтому healthcheck — сам бинарник: `HEALTHCHECK` в `Dockerfile` запускает `/service -healthcheck`, который берёт тот же конфиг и спрашивает работающий сервис — gRPC health `Check` по mTLS (`grpcserver.Probe`; сертификат сервиса годится и как клиентский, в нём есть `localhost`) или `GET /healthz` у `gateway`. Поэтому в `compose.yaml` сервисы ждут тех, кого вызывают, `service_healthy`, а `make stack` (`up --wait`) возвращается, когда весь сайт готов.

CI (GitHub Actions, `.github/workflows/ci.yml`) делает то же, что локальные команды: `make check-integration` (gofmt, vet, golangci-lint, `go test -race` во всех модулях `go.work` с интеграционными тестами на временных Postgres и Redis, тесты сайта) и `make stack` + `make smoke`. Версии инструментов — Go из `go.work`, golangci-lint и goose — закреплены в workflow и `scripts/check.sh`; меняя их, меняй в обоих местах.

Деплой. Пуш в `main`, прошедший проверки, сразу уходит на сервер: задание `images` собирает образы всех сервисов (у `gateway` — с сайтом) и кладёт их в GHCR (`ghcr.io/vexner67/freenet-<сервис>:<коммит>` и `:latest`, кеш сборки — в кеше GitHub Actions), задание `deploy` (по одному, в порядке пушей — запуски на `main` не отменяют друг друга) копирует `compose.yaml`, `deploy/` и `monitoring/` в `/opt/freenet` на сервере по SSH (пользователь `freenet`, ключ — секрет `DEPLOY_SSH_KEY`, ключ сервера — `DEPLOY_KNOWN_HOSTS`, адрес — `DEPLOY_HOST`) и запускает `deploy/deploy.sh <коммит>`: он записывает коммит в `FREENET_TAG`, тянет образы (токен GHCR — `GITHUB_TOKEN` задания, через stdin, только на этот запуск), проверяет `deploy/Caddyfile` с `.env` сервера (Caddy, который не может его прочитать, уронил бы сайт — так деплой падает раньше, чем что-то перезапустится), делает `docker compose up --wait` (миграции сервисы применяют при старте) и чистит образы старше трёх дней; в конце CI проверяет `SITE_URL/healthz` (переменная репозитория). Откат — тот же `deploy.sh` с прежним коммитом. На сервере `.env` задаёт `COMPOSE_FILE=compose.yaml:deploy/compose.prod.yaml` и `COMPOSE_PROFILES=app`, так что там просто `docker compose ps|logs|...`. `deploy/compose.prod.yaml` поверх `compose.yaml`: образы из GHCR вместо сборки, наружу опубликован только Caddy (80/443 и 443/udp) — Docker пишет свои правила iptables в обход ufw, поэтому базы, Redis и gateway не публикуются вовсе (`!reset`), а Prometheus, Alertmanager и Grafana — только на 127.0.0.1 (смотреть через `ssh -L 3001:localhost:3001`). Caddy (`deploy/Caddyfile`) — TLS и прокси на gateway: `SITE_ADDRESS` — домен (сертификат Let's Encrypt Caddy получает и продлевает сам) или `:80`, пока домена нет, а `REDIRECT_ADDRESS` (`www.<домен>`) постоянно перенаправляет на него — у сайта один адрес, и вход действует, откуда бы ни пришли; каждому запросу Caddy даёт свой `X-Request-ID`, gateway ему верит (`TRUST_FORWARDED_FOR=true`). Коды входа, пока нет SMTP, — в `docker compose logs auth` (`MAILER=console`; для писем — `MAILER=smtp` и `SMTP_*` в `.env` сервера). Сервер готовит один раз `deploy/bootstrap.sh` (Ubuntu 24.04, от root, повторный запуск безопасен): вход по SSH только по ключу (`PasswordAuthentication no`, root — только по ключу), fail2ban, ufw (22 с ограничением частоты — не больше 6 соединений за 30 с с одного адреса, поэтому для работы с сервером удобно одно переиспользуемое соединение `ControlMaster`; 80, 443), автоматические обновления безопасности, swap на маленькой машине, Docker из его репозитория с ротацией логов, пользователь `freenet` для деплоя, `/opt/freenet/.env` со случайными паролями баз и секретами и `certs/` (`scripts/gen-certs.sh`) — секреты живут только на сервере.

`gateway` может собирать ответ из нескольких сервисов (стена = профиль из `user` + записи из `post` + профили авторов; лента = подписки из `user` → записи этих авторов из `post` → профили авторов и владельцев стен одним `GetProfiles`), но правил предметной области не придумывает. Исключение — проверка «писать на стену и подписываться можно после заполнения профиля»: без никнейма у человека нет адреса и имени в списках.

Подписки живут в `user`: это связь между пользователями, и только там внешний ключ гарантирует, что подписываются на существующего человека.

Фото: `media` хранит файлы, `user` — только `avatar_id` текущего фото. Загрузку собирает gateway: `media.UploadAvatar` → `user.SetAvatar` → `media.DeleteAvatars` с сохранением нового (старое удаляется лишь после того, как профиль указывает на новое). Путь к фото содержит ID пользователя, поэтому чужой `avatar_id` в своём профиле даёт лишь битую картинку. URL фото меняется с каждым новым фото — ответы кешируются навсегда (`immutable`). Изображения из загрузки всегда перекодируются (EXIF с геолокацией не сохраняется); размеры проверяются по заголовку до распаковки (защита от «пиксельных бомб»). Телефон хранит снимок так, как его видела матрица, и лишь помечает в EXIF, как его повернуть (`Orientation`) — `imaging.Picture` читает эту метку из JPEG (свой разбор APP1 на несколько десятков строк, каждое смещение проверяется) и отдаёт картинку стоящей прямо: масштабируются исходные пиксели, а поворачивается уже маленький результат, иначе поворот 50-мегапиксельной загрузки стоил бы сотни мегабайт.

Фото в записях: до 10 на запись, запись может состоять из одних фото (`post.Content` — текст, фото или оба, но не пусто; то же правило — `CHECK` в БД). Фото загружается в `media` до публикации (`POST /api/v1/me/photos`), запись хранит только ID. `post` не знает, чьи это фото, поэтому перед `CreatePost` gateway спрашивает у `media` `ListOwnPhotos` и отказывает при чужом/несуществующем ID; путь к файлу содержит ID автора, так что даже без проверки чужое фото дало бы лишь битую картинку. Загрузка ждёт своей записи в `<MEDIA_DIR>/uploads`: опубликованную запись `post` в той же транзакции записывает в outbox (поток `media`, `mediaclient`) — внутренний `PublishPhotos` (только для mTLS-идентичностей `post` и `message`) переносит фото в `<MEDIA_DIR>/photos` одним `rename`; удалённую — `DeletePublishedPhotos` с автором записи, кто бы её ни удалил (автор, владелец стены, очистка страницы). Так же устроены фото комментариев (`post`) и сообщений (`message`, свой outbox и своя копия `mediaclient` — сервисы не делят код, кроме `pkg/*`): до 10, текст, фото или оба, но не пусто (`CHECK` в БД), gateway проверяет их у `media` перед `CreateComment`/`SendMessage`. Комментарий уносит свои фото, удаляясь сам, с записью (`DeleteByPost` сначала берёт запись `FOR UPDATE`: комментарий, написанный в это время, ждёт и падает, а не исчезает каскадом незамеченным с фото) и при очистке страницы; сообщения удаляются только очисткой — она стирает и фото собеседников из диалогов стёртого. Сайт показывает фото комментария и сообщения той же сеткой, что у записи, только меньше; в списке диалогов и в «Ответах» вместо пустого текста — «Фотография», как во ВКонтакте. Фото, которое за `UNPUBLISHED_PHOTO_TTL` (по умолчанию сутки) не попало в запись, `media` удаляет сам (раз в `PHOTO_CLEANUP_INTERVAL`, возраст — из UUIDv7 фото); такой ID gateway уже не примет (`photo not found`). Публикация и удаление идут одним потоком — по порядку. Без `MEDIA_SERVICE_ADDR` у `post` фото записей считаются неопубликованными и удаляются — предупреждение при старте. В отличие от аватарки фото не обрезается: оно уменьшается целиком с сохранением пропорций (до 1280 и 640 по длинной стороне) и никогда не увеличивается. Чтение загрузки (сначала заголовок — защита от «пиксельных бомб») и запись JPEG без метаданных — общий пакет `media/internal/imaging`.

Записи на чужой стене: у записи есть автор (`author_id`) и стена (`wall_id`, ID владельца); на своей стене они совпадают. Стена (`ListPosts`, «N записей») — по `wall_id`, лента — по `author_id`: в ленте видно, что человек написал и у себя, и у других. Кто может писать на стену, решает её владелец — настройка приватности `wall_write` в `user` («Кто может писать у меня на стене», как в openvk): `everyone`, `following` (те, на кого владелец подписан; по умолчанию — так незнакомцы не пишут на новую стену) и `only_me`. Друзей у нас нет: «Друзья» openvk — это подписки владельца. Правило — `user.CanPostOnWall` в домене `user`, там же подписки; `post` пользователей не знает, поэтому перед `CreatePost` с `wall_id` gateway спрашивает `user.CanPostOnWall` (как с фото у `media`) и отказывает `403 you cannot post on this wall`. Запись удаляет её автор или владелец стены; комментарий — его автор, автор записи или владелец стены. Владельцу стены о чужой записи приходит уведомление `wall_post`. Сайт показывает форму, если первая страница стены пришла с `canPost`; в ленте у записи на чужой стене — «написал на стене Петра Петрова» (имя в родительном падеже склоняет `genitiveName` из `labels.js`), на странице записи — «Владелец » Стена » Запись», как в openvk.

Репосты («Поделиться», как в openvk): репост — обычная запись на стене того, кто делится, с `repost_of` (ID записи, которой поделились) и необязательным комментарием; `post.Content` — текст, фото, репост или их сочетание, но не пусто (то же правило — `CHECK` в БД). Отдельный RPC `RepostPost`, всегда на свою стену; лимит частоты — тот же `RATE_LIMIT_POSTS`, счётчик свой. Счётчик `repost_count` меняется тем же SQL-запросом, что вставляет или удаляет репост (CTE); репост записи, которой уже нет, не создаётся (`NotFound`). Внешнего ключа нет: репост переживает исходную запись и показывает «Запись удалена.». Репост без своих слов не делится сам — делятся его исходной записью (`post.Shared`), чтобы не плодить пустые вложенные цепочки; репост со своим комментарием делится сам, а сайт показывает в нём ссылку «Открыть запись» вместо второго уровня вложенности. Автору исходной записи приходит уведомление `repost`, его `post_id` — сам репост, поэтому удалённый репост забирает уведомление через `ForgetPost`. Вложенные записи gateway подтягивает одним `GetPosts`, а профили всех людей страницы — `GetProfiles` пачками по 100.

Редактирование и закрепление записей — как в openvk. Свою запись автор правит неделю после публикации (`post.Edited`: только автор и до `EditableUntil`, иначе `ErrCannotEdit` → 403 и `ErrEditExpired` → `FailedPrecondition`/409): `EditPost` заменяет текст и фото целиком, как при публикации (gateway так же проверяет фото у `media`), репост меняет только свои слова и остаётся репостом той же записи. Запись не изменяется на месте — `Edited` возвращает новую, потому что читатели (`inmem`) держат указатели. Фото, которые правка добавила, `post` публикует, а убранные удаляет — в той же транзакции через outbox `media`. Запись хранит `edited_at`, сайт пишет после даты «(ред.)», а правит запись на месте (`postedit.js`): текст и фото уступают место форме с «Сохранить»/«Отмена». Лимит частоты — `RATE_LIMIT_POST_EDITS`. Закрепляет запись владелец стены, чья бы она ни была (`CanBePinnedBy`); на стене закреплена одна запись — таблица `pinned_posts` с ключом по стене, так что закрепить другую — один `INSERT ... ON CONFLICT` без гонки, а удалённая запись уносит закрепление каскадом. `ListPosts` отдаёт закреплённую первой на первой странице, сверх `limit`, и пропускает её дальше; запись показывает «, закреплено» после даты. Ссылки «Редактировать», «Удалить», «Закрепить»/«Открепить» — в подвале записи, в порядке openvk.

Сообщества («группы» openvk) — сервис `club`: группа (`club.Club`: название до 64 символов, описание, необязательный адрес, «Сайт» — ссылка http/https, `https://` дописывается, если схему не указали, как в openvk, — стена `open`/`suggest`/`closed` («Открытая», «Предложка», «Закрытая» openvk) и «Список админов» `creator`/`all`/`none`), её участники (`club_members`, счётчик `member_count` меняется тем же SQL-запросом, что добавляет или убирает участника) и роли: создатель — владелец (`owner`, один на группу — частичный уникальный индекс; выйти не может), им назначенные администраторы (`admin`) и участники (`member`). Правила — в домене: правят группу и пишут «От имени сообщества» администраторы и владелец (`Role.Manages`), назначает их только владелец (`CheckAppoint`), он же передаёт группу одному из администраторов и сам остаётся администратором (`TransferClub`, «Назначить владельцем» openvk, `CheckTransfer`; роли меняются в одной транзакции — сначала владелец становится администратором, потом администратор владельцем, иначе частичный уникальный индекс увидел бы двух владельцев; второй одновременный перенос ждёт строку владельца и не находит его), на открытой стене пишет любой (как «Открытая» в openvk, даже не участник), на остальных — только администраторы и только от имени группы (`CanPostOnWall`; gateway сам ставит `from_wall`, как openvk), а на «Предложке» остальные предлагают записи (`CanSuggest`, ответ `suggest` у `CanPostOnWall`). Предложенные записи («Предложка» openvk) живут в `post` отдельной таблицей `suggestions` (`post.Suggestion`: текст, фото или оба, не репост), поэтому стена, лента и счётчик их не видят: видят только автор («Предложенные вами записи», `ListSuggestions` с `mine`) и администраторы («Предложенные записи», `post` спрашивает `club.CanModerateWall`). Фото публикуются в `media` сразу при предложении — запись может ждать дольше, чем `media` хранит неопубликованные. «Опубликовать запись» (`PublishSuggestion`, администратор правит текст и ставит «Подпись автора») в одной транзакции удаляет предложение (уже опубликованное или отклонённое — `NotFound`, дважды не опубликуется) и создаёт новую запись от имени группы с новым ID и датой — она встаёт наверх стены; это запись группы (`post.suggested`): автор её не правит и не удаляет, как «Вы не можете удалить ваш принятый пост» openvk, `mine` ему не говорят. Автору приходит уведомление `post_accepted` от имени группы (актор — ID группы; «Сообщество Кошки опубликовало вашу предложенную запись»). Администраторам о каждом новом предложении приходит `suggested_post` от имени группы («В сообществе Кошки новые записи в предложке» openvk, ссылка — на «Предложенные записи»): кому, `post` спрашивает у внутреннего `club.ListWallModerators` (владелец и администраторы, до 100), а `post_id` уведомления — ID предложения, поэтому gateway не ищет его среди записей; опубликованное, отклонённое, удалённое автором и стёртое с его страницей предложение забирает эти уведомления (`ForgetPost` с ID предложения). «Отклонить» и удаление своего предложения (`DeleteSuggestion`) уносят его фото. Очистка страницы удаляет и её предложения. Страница группы — `/club/<адрес>`, без адреса — `/club/<id>`, как `/club123` openvk; адрес — как никнейм (латиница, цифры, `_`, буква первой, поэтому ID с адресом не спутать), уникален без учёта регистра (индекс по `lower(address)`). Общего пространства адресов с никнеймами нет: уникальность пришлось бы держать в двух базах. Стена группы живёт в `post`: `wall_id` — ID группы, `post` не знает, чья это стена. Запись «От имени сообщества» хранит `from_wall`: автор (`author_id`) правит её неделю, как свою, но читателям gateway показывает автором группу (`author.club`), а `post` говорит только самому автору `mine`; такие записи не уведомляют автора (`post.Notified` — никто), не попадают в ленту по автору (только по стене) и не проверяют чёрный список автора при комментарии — иначе отказ выдал бы, кто писал. Так же администраторы комментируют записи на стене группы «От имени сообщества» (галочка под формой комментария, как в openvk): комментарий хранит `from_wall` (`Comment.ForWall`), gateway проверяет право у `club.CanPostOnWall` с `from_club` и показывает автором группу (фото остаются под автором), `post` говорит автору `mine`; уведомления о таком комментарии приходят от группы (актор — ID группы, «Сообщество Кошки оставило комментарий»), а ответы на него и его лайки никого не уведомляют (`Comment.Notified` — никто). Кто может писать, gateway спрашивает у `club.CanPostOnWall` (как у `user` для стен людей) и передаёт в `CreatePost` `club_wall` (владельца стены не уведомлять) и `from_wall`; удалять и закреплять чужие записи и комментарии на стене группы `post` разрешает сам, если запрос не прошёл его собственные правила, спросив внутренний `club.CanModerateWall` (`clubclient`, только для mTLS-идентичности `post`; для стены человека — «нет»). Лента («Мои Новости») — записи подписок и все записи на стенах групп, где состоит читатель (`ListMyClubIDs`, до 1000 последних, `ListFeed` с `wall_ids`). Авторов и стены страницы gateway ищет сначала среди людей (`GetProfiles`), остальные ID — среди групп (`GetClubs`, пачками по 100). Фото группы хранит `media` под ID группы и отдаёт как аватарку (`/media/avatars/<club>/...`): загрузку собирает gateway — проверяет у `club`, что вызывающий администратор, вызывает внутренние `media.UploadClubAvatar`/`DeleteClubAvatars` (только для mTLS-идентичности `gateway`, токен идёт с ними — по нему лимит), затем `club.SetClubAvatar` (правило — `Club.WithAvatar`), и лишь потом удаляет старое фото, как у людей. Поиск групп (`SearchClubs`, `/search?section=groups`) — как поиск людей: каждое слово `LIKE '%слово%'` по названию и адресу с триграммным индексом. От назначения администратором человек получает то же, что в openvk: группа появляется во вкладке «Управляемые» «Моих Групп» (`ListMyClubs` с `managed`), её можно «Добавить в левое меню» (`PinClub`, флаг `pinned` у членства, не больше `club.MaxPinned` = 10 — проверка тем же `UPDATE`; показываются только группы, которыми человек ещё управляет), и он правит группу, ставит фото, пишет от её имени и следит за стеной. Запись «От имени сообщества» может нести «Подпись автора» (`signed`, только вместе с `from_wall` — `CHECK` в БД): тогда gateway отдаёт автора в `signer`, и сайт пишет под текстом «Автор: Иван Иванов» со ссылкой, как openvk; на закрытой стене и «Предложке» администраторы, как в openvk, пишут только от имени группы (gateway ставит `from_wall` сам). Чьи группы видно: блок «Группы» на странице человека и его список (`/groups?u=<никнейм>`) отдаёт `club.ListUserClubs` (публичный, только группы — без ролей и меню), а можно ли их видеть, gateway спрашивает у `user.CanSeeClubs` — настройка `clubs_read` («Кому видно мои группы» openvk: `everyone` по умолчанию, как там, `following`, `only_me`, правило — `User.ClubsVisibleTo`; чёрный список её не закрывает, у удалённой страницы групп не видно). Сами группы показывают участников при любой настройке, как в openvk. Лимиты частоты: создание групп, правка настроек и фото, передача группы, вступление; предложение и публикация записи — `RATE_LIMIT_POSTS`, у каждого свой счётчик. При очистке страницы `club` (поток `club` outbox `user`) убирает человека из всех групп; группа, которой он владел, остаётся без владельца. На сайте — «Мои Группы» (`/groups`: вкладки «Группы» и «Управляемые» (`?act=managed`), серая полоса с «Поиском по группам» и «Создать группу» → `/groups/create`, «Вы состоите в N группах», группы списком openvk — фото, «Название», «Размер», описание и справа «Просмотр группы», «Добавить в левое меню»/«Удалить из левого меню», «Выйти из группы»; общий `clubs.js`), закреплённые группы — в левом меню под чертой (`showPinnedClubs`), страница группы (`club.js`, раскладка openvk, зеркальная странице человека: слева «Информация» с «Сайтом», «Участники» и стена с «От имени сообщества» и «Подпись автора» для администраторов, справа фото с «Загрузить фотографию» для них, «Вступить в группу»/«Выйти из группы», «Редактировать группу», «Тип группы» и, как велит «Список админов», «Создатель», «Администраторы» (сколько, «Все» и первые пять, владелец первым) или ничего), настройки (`/club/<адрес>/edit`: название, описание, адрес страницы, сайт, стена, список админов) и участники (`/club/<адрес>/members`, вкладка «Руководство», у владельца «Назначить администратором»/«Снять полномочия администратора» и у администраторов «Назначить владельцем» с окном openvk «Передача прав владельца»), над стеной — ссылка openvk «N предложенных записей» администраторам и «N предложенных вами записей» автору, форма «Предложить новость» на «Предложке» (после неё — свои предложенные записи, как в openvk), страница предложенных записей (`club-suggested.js`: «Опубликовать запись» с окном «Публикация предложенной записи» и «Отклонить» у администраторов, «Удалить» у автора); на странице человека — блок «Группы» openvk (сколько, «Все», названия через «•»); вместо аватарки — камера, как в openvk. Запись группы подписана «Кошки опубликовали» (openvk «post_writes_g»), запись участника на её стене — «Пётр написал в Кошки» (openvk «в $1»).

Лайки и комментарии живут в `post` рядом с записями: внешние ключи `ON DELETE CASCADE` удаляют их вместе с записью. Счётчики (`like_count`, `comment_count`) хранятся в строке записи и меняются **тем же SQL-запросом** (CTE), что вставляет или удаляет лайк/комментарий, — счётчик не расходится с данными даже при одновременных лайках, а стена читается без подсчёта. Лайк идемпотентен (первичный ключ `(post_id, user_id)`). «Нравится ли мне» — поле `liked` у записи: публичные методы заполняют его, если пришёл токен. Комментарий удаляет его автор, автор записи или владелец стены. In-memory реализация (`inmem.Store`) ведёт себя так же: репозитории записей, лайков и комментариев работают над общим состоянием. У комментария — свои лайки (`comment_likes`, счётчик `like_count` тем же SQL-запросом, `LikeComment`/`UnlikeComment`, тот же лимит частоты, что у лайков записей) и ответы, как в openvk: «Ответить» подставляет в поле имя автора («Катя, ») и отправляет `reply_to` — комментарий той же записи (`post.NewReply` отказывает в чужом: иначе ответ обошёл бы проверку чёрного списка по записи из URL); удалённый комментарий оставляет ответы, которые больше ни на что не отвечают (`ON DELETE SET NULL`). Сайт показывает у ответа ссылку «в ответ» на тот комментарий, сердечко — справа в подвале, как у записи (общий `likeButton`). Лента ответов плоская, по времени: веток нет и в openvk.

Уведомления — сервис `notification`. О событиях сообщают их владельцы: `post` (лайк, комментарий, запись на чужой стене, репост, ответ на комментарий — `comment_reply`, лайк комментария — `comment_like`, опубликованная предложенная запись — `post_accepted`, новая предложенная — `suggested_post` администраторам группы) и `user` (подписка) вызывают внутренние `Notify`/`Retract` по mTLS; отмена действия (лайк снят, отписка, блокировка) забирает уведомление `Retract`, удалённая запись — все свои `ForgetPost`, удалённый комментарий — все свои `ForgetComment` (о нём, об ответе, которым он был, и о его лайках). Ответ слышит автор комментария, на который ответили, а автор записи — о новом комментарии, если это не он же. Доставка надёжная, через outbox (`pkg/outbox`): `service.Notifier` не звонит, а записывает запрос (proto `NotifyRequest`/`RetractRequest`/`ForgetPostRequest`) в таблицу `outbox` своей БД **в той же транзакции**, что и лайк (`service.TxManager`), — уведомление записано тогда и только тогда, когда записано действие. Таблица делится на потоки (`stream`, по одному на получателя: у `user` это `notification`, `post`, `media`, `message`, `club`, у `post` — `notification` и `media`, у `message` — `media`) — у каждого свой порядок и свой relay, так что недоступный получатель задерживает только своё. Relay того же процесса доставляет записи потока по одной в порядке записи (`id` — identity из БД, не часы реплик) и повторяет с нарастающей паузой (1 с … 5 мин), пока `notification` недоступен: неудачная запись задерживает следующие, поэтому «снял лайк» не обгонит «поставил». Ошибки, которые повтор не исправит (`InvalidArgument`, `NotFound` и т. п. — `notifyclient.Deliverer`), запись отбрасывают с `ERROR` в логе. Доставляет один relay на поток — тот, кто держит advisory lock потока на своём соединении; новые записи будят его `LISTEN/NOTIFY` (NOTIFY приходит только после коммита), раз в 5 с он смотрит и сам. Доставка «хотя бы раз»: `Notify`/`Retract`/`ForgetPost` идемпотентны. Записи несут `request_id` запроса, а relay доставляет с ним — в логах доставка видна рядом с лайком. Метрики — `outbox_messages_total{result}` и `outbox_lag_seconds` (возраст самой старой недоставленной) с меткой `stream`. В `STORAGE=inmem` outbox в памяти (`outbox.Memory`) и без транзакций. Без `NOTIFICATION_SERVICE_ADDR` сервисы работают без уведомлений (предупреждение при старте). «Сам себе» уведомление не отправляется — это решает сервис-источник, домен `notification` такое отвергает. Один лайк/комментарий/подписка/запись на стене/репост — одно уведомление (частичные уникальные индексы), повтор не дублирует. Прочитанное — одна отметка на пользователя: `read_up_to`, ID самого нового прочитанного (UUIDv7 растут со временем); новее — «Непрочитанное», остальное — «Архив», как в openvk. Отметка только движется вперёд и принимает лишь собственное уведомление пользователя, иначе выдуманный ID «из будущего» спрятал бы все будущие уведомления. Ленту уведомлений собирает gateway: авторы из `user`, даты и тексты записей и тексты комментариев из `post` (`GetPosts`/`GetComments` пачкой); уведомления об исчезнувшем пропускаются, а `newestId` страницы отдаётся всегда, чтобы пропущенное не висело непрочитанным.

Личные сообщения — сервис `message`. Сообщение — строка `messages` с парой (`user_lo`, `user_hi`) = (меньший, больший) ID собеседников: история диалога — один диапазон индекса в обе стороны. Диалог — по строке `dialogs` на каждого участника: последнее сообщение, последнее входящее и отметка «прочитано до» (ID самого нового прочитанного входящего). Отправка — один SQL-запрос: сообщение и обе строки диалога; строки диалога пишутся в порядке `user_id`, иначе двое, пишущие друг другу одновременно, захватывают их в разном порядке и ловят взаимную блокировку (была найдена тестом). «Прочитано» вычисляется по отметкам обеих сторон (`message.ReadMarks`): видно и что не прочитал я, и что не прочитал собеседник. Отметка двигается только вперёд и только на сообщение собеседника пользователю. Своё сообщение отправитель удаляет у обоих в течение суток (`message.CheckDelete`, как «Удалить для всех» во ВКонтакте; позже — `ErrDeleteExpired` → `FailedPrecondition`/409, чужое — `ErrCannotDelete` → 403, сообщение из чужого диалога — `NotFound`), вместе с фото (outbox `media`). `DeleteMessage` — один SQL-запрос: удаляет сообщение и возвращает каждую строку диалога к последнему оставшемуся сообщению, только если удалённое было её последним (сообщение, отправленное в это время, уже сдвинуло строку — её не трогаем); строки блокируются в том же порядке `user_id`, что при отправке. Удалено всё — строка остаётся с нулевым `last_message_id` (и отметкой «прочитано») и выпадает из списка диалогов; удалённое входящее больше не даёт права ответить. Сайт показывает «Удалить» под датой своего сообщения при наведении и спрашивает подтверждение окном openvk. `message` не знает пользователей: получателя по никнейму находит и проверяет gateway, он же требует заполненную анкету отправителя и спрашивает право писать (см. ниже).

Приватность сообщений и чёрный список — в `user`, рядом с подписками. «Кто может писать мне сообщения» (`messages_write`, как в openvk): `everyone` (по умолчанию — как было до настройки), `following` (те, на кого подписан получатель) и `nobody`; тот, кому вы написали первыми, может ответить при любой настройке («Вам смогут ответить, если вы напишете первыми»). Писал ли получатель отправителю, знает только `message` (`HasMessagesFrom`, по строке `dialogs`): gateway берёт этот факт у `message` и передаёт в `user.CanMessage`, а решает правило домена `user.CanBeMessagedBy`. Чёрный список (`blocks`, «Чёрный список» openvk) действует в обе стороны: если один внёс другого, между ними нет сообщений (и ответов), записей на стене, подписок и комментариев к записям друг друга; блокировка удаляет подписки в обе стороны тем же SQL-запросом (CTE), их уведомления забираются. Правила («связи» `user.Ties`: подписан ли владелец, есть ли блокировка, писал ли первым) — в домене `user`, сбор связей — `service.PermissionService` (`CanPostOnWall`, `CanMessage`), подписка проверяет блокировку сама. Комментарии живут в `post`, который пользователей не знает, поэтому перед `CreateComment` gateway спрашивает `user.GetRelation` с автором записи и владельцем стены. Профиль для вошедшего отдаёт `blockedByMe`/`blockedMe`, и сайт показывает вместо него ограниченную страницу openvk («Анна ограничила доступ к своей странице», «… — в вашем чёрном списке»). Профиль и стена при этом остаются публичными (аноним видит их всё равно): чёрный список закрывает контакт, а не данные. Новые сообщения и отметки «прочитано» приходят на страницу сразу (см. «Живые события»); пока поток событий недоступен, страница диалога опрашивает раз в 5 секунд (`?after=`), только пока вкладка видна, и после переподключения один раз догоняет пропущенное; прочитанными отмечает только видимая вкладка.

Удаление страницы («Удаление страницы» openvk) — в `user`: `DeactivateAccount` с необязательной причиной (сайт предлагает причины openvk) скрывает страницу сразу, а восстановить её (`ReactivateAccount`) можно до `purge_at` — через `ACCOUNT_RETENTION` (по умолчанию 7 месяцев, как в openvk). Пока страница удалена, другие видят только имя и фото (`deactivated` в профиле): на неё нельзя подписаться, писать на её стену и ей, её нет в поиске, а написанное её владельцем gateway скрывает (записи, комментарии, уведомления — `authors` пропускает удалённых; в диалогах собеседник остаётся с пометкой). Правила — в домене (`User.Deactivate`/`Reactivate`, `PublicProfile`, `CanPostOnWall`, `CanBeMessagedBy`). Сам владелец удалённой страницы не может ничего, кроме как увидеть и восстановить её: `auth` при входе и при каждом refresh спрашивает `user` (`GetOrCreateByEmail`, внутренний `GetAccountState`) и ставит в access-токен `deactivated`; `jwtauth.UnaryServerInterceptor` во всех сервисах пускает такой токен только в методы `jwtauth.Access.Deactivated` (`GetMe`, `ReactivateAccount`), публичные видят его владельца анонимом, остальные отвечают `PermissionDenied` («your page is deleted»), потоков он не получает. После удаления и восстановления сайт сразу обновляет токены; уже выданный полный токен действует до истечения (≤ 15 мин), как после `Logout`. На сайте — ссылка «Вы также можете удалить свою страницу» под настройками (`deactivate.js`, окно openvk), у владельца удалённой страницы нет меню и в шапке только «выход», с любой страницы его переносит на свою, где «Ваша страница удалена… восстановить свою страницу до …»; другие видят «Страница удалена. Информация недоступна.». По истечении срока `user` каждые `ACCOUNT_PURGE_INTERVAL` (`service.PurgeService`) удаляет строки пользователей (подписки и блокировки — каскадом; `FOR UPDATE SKIP LOCKED`, реплики не мешают друг другу) и **в той же транзакции** записывает `purge_user` в outbox каждого сервиса, хранящего данные пользователей (`purgeclient`): их внутренний `PurgeUser` (только для mTLS-идентичности `user`, идемпотентный) стирает в `post` записи пользователя и записи на его стене с лайками и комментариями, его лайки и комментарии к чужим записям (счётчики — тем же SQL-запросом) и `ForgetPost` удалённых записей через свой outbox; в `media` — все аватарки и фото; в `message` — его диалоги с обеих сторон со всеми сообщениями (собеседнику остался бы диалог ни с кем); в `club` — его членство во всех группах; в `notification` — уведомления, которые он получил или вызвал, и отметку «прочитано» (через поток `notification`, чтобы старое уведомление о подписке не пришло после очистки). Сессии стёртого пользователя в `auth` кончаются при следующем refresh (`GetAccountState` → `NotFound`), почта освобождается — с ней можно зарегистрироваться заново, новым пользователем.

Живые события. Источники — сервисы, владеющие данными: `message` (новое сообщение — обоим участникам, сдвинутая отметка «прочитано» — обоим, удалённое сообщение — обоим) и `notification` (новое, отозванное, прочитанное). Каждый держит концентратор подписчиков (`pkg/pubsub`) и отдаёт события потоковым RPC `Subscribe` (server streaming): поток живёт не дольше access-токена — `jwtauth.StreamServerInterceptor` ставит дедлайн на его срок, и поток кончается `Unauthenticated`; отставший подписчик (буфер 64) отключается `ResourceExhausted` и догоняет из хранилища — события не теряются молча. При заданном `REDIS_ADDR` концентратор общий для реплик (`pubsub.Redis`): событие публикуется в канал Redis (`message:events`, `notification:events`, JSON — `internal/redis`), и каждая реплика раздаёт пришедшее своим подписчикам — поток получает события, опубликованные на любой реплике. Redis pub/sub ничего не хранит, поэтому реплика, потерявшая подписку на канал (переподключение, Redis недоступен), сбрасывает своих подписчиков и, пока не подписана снова, сразу закрывает новые потоки: страница получает 1013, догоняет обычными запросами (диалог — опросом) и подключается позже. go-redis не прерывает `Receive` по отмене контекста — `Run` закрывает подписку сам. Без `REDIS_ADDR` события остаются в реплике (`pubsub.Hub`, предупреждение при старте). `pkg/grpcserver` при остановке сначала отменяет все потоки, иначе `GracefulStop` ждал бы их до таймаута. `gateway` открывает на страницу один WebSocket `/api/v1/events` (`coder/websocket`): токен — первым сообщением, а не в URL (попал бы в логи); собирает оба потока, добавляет профили собеседников и пересчитывает счётчики у сервисов (события лишь говорят, когда), отдаёт JSON-события (`ready`, `counters`, `message`, `read`, `delete`, `notification`, контракт — `openapi.yaml`). Коды закрытия говорят странице, что делать: 4001 — обновить токен и подключиться заново, 1013 — подождать, 1001 — сервер останавливается. Таймаут запросов к потоку не применяется, дедлайны `http.Server` с перехваченного соединения снимаются, а при остановке gateway закрывает потоки сам (`Shutdown` их не ждёт). На сайте `events.js` (подключает `renderChrome`) держит соединение и переподключается с нарастающей паузой; счётчики меню, диалог, список диалогов (удалённое последнее сообщение — загрузкой первой страницы заново: что теперь последнее, знает только сервер) и вкладка «Непрочитанное» ответов обновляются без перезагрузки.

Наблюдаемость. **ID запроса** (`pkg/reqid`): `gateway` даёт каждому HTTP-запросу ID (или берёт `X-Request-ID` от своего прокси — только при `TRUST_FORWARDED_FOR=true` и только допустимого вида: до 64 символов из букв, цифр и `-_.:`, иначе ID подделал бы строки лога) и возвращает его в заголовке `X-Request-ID`. ID идёт в контексте и gRPC-метаданных `x-request-id` через все вызовы — gateway → сервис → сервис (клиенты собираются с `reqid.DialOptions()`; уведомления доставляет relay позже — ID хранится в записи outbox и идёт с доставкой), — и `pkg/logger` дописывает `request_id` в каждую строку, залогированную с этим контекстом. Сервер, к которому ID не пришёл, заводит свой. Поэтому логируем с контекстом (`InfoContext`, `ErrorContext`), когда он есть. Каждый gRPC-вызов пишется на уровне `debug` (`grpc call`: метод, код, время) — с `LOG_LEVEL=debug` весь путь запроса виден по одному `request_id`. **Метрики** Prometheus (`pkg/metrics`) — на отдельном порту `METRICS_PORT`, наружу не публикуется (без переменной не отдаются). `pkg/grpcserver` считает каждый вызов с кодом, который получил клиент (его интерсепторы стоят снаружи интерсепторов сервиса): `grpc_server_handled_total`, `grpc_server_handling_seconds` (только unary), `grpc_server_streams_open`; `gateway` — `http_requests_total` и `http_request_duration_seconds` по шаблону маршрута (`/api/v1/users/{nickname}`, никогда по самому пути — никнейм и ID в метке раздули бы её до бесконечности, поэтому middleware обёрнут прямо вокруг mux, который знает шаблон), `gateway_event_streams_open`; плюс метрики Go и процесса. `make stack` поднимает Prometheus (`monitoring/prometheus.yml`, http://localhost:9090), `make dev` даёт сервисам порты метрик сам. **Алерты** — правила Prometheus в `monitoring/alerts.yml`: сервис недоступен (`ServiceDown`), доля ошибок сервера выше 5% (`GRPCServerErrors` — коды `Internal`/`Unknown`/`DataLoss`, `HTTPServerErrors` — 5xx), 95-й перцентиль дольше 1 с у HTTP и 0,5 с у gRPC (`HTTPSlow`, `GRPCSlow`), поток outbox стоит дольше 5 минут (`OutboxLagging`) и часа (`OutboxStuck`, критично: через сутки `media` удаляет фото как неопубликованные), outbox отбросил запись (`OutboxDropped`). У каждого правила есть тест `promtool` в `monitoring/alerts_test.yml`; `make check-integration` гоняет их и проверяет конфиги `promtool`/`amtool` из тех же образов, что в `compose.yaml`. Новая метрика, о сбое которой надо знать, получает правило и тест. Prometheus отдаёт алерты Alertmanager (http://localhost:9093, `monitoring/alertmanager.yml`: группировка по сервису, `ServiceDown` глушит ошибки и задержки того же сервиса); оповещать пока некого — получатель без каналов, см. долг. **Grafana** (http://localhost:3001, `GRAFANA_PORT`) открыта для просмотра без входа (`admin` — с `GRAFANA_ADMIN_PASSWORD`); источники данных (Prometheus, Alertmanager) и дашборд «Freenet» берутся из `monitoring/grafana` при старте, правка — только в git (`freenet.json`), не мышью в Grafana: доступность сервисов и алерты, gRPC (вызовы, доля ошибок, задержки, отказы по кодам, открытые потоки), HTTP gateway по маршрутам, outbox по потокам, память, CPU и горутины; переменная `service` выбирает сервисы. **Healthcheck** — `<service> -healthcheck` (см. Docker выше); gRPC health `Check` открыт без токена (`jwtauth`), он говорит только, работает ли сервис.

Защита от спама — ограничение частоты действий на пользователя: записи, репосты, правки записей, комментарии, лайки (`post`), сообщения (`message`), загрузка фото и аватарок (`media`), подписки (`user`), создание и правка групп и вступление в них (`club`). Это сквозная задача, поэтому она сделана gRPC-интерсептором `pkg/ratelimit.UnaryServerInterceptor`: он стоит **после** `jwtauth` и считает по ID пользователя из проверенного токена, ключ — метод + окно + пользователь. Правила — в конфиге сервиса (`RATE_LIMIT_*`, формат `5/1m,100/24h`: короткое окно против всплесков, длинное против медленного спама; неверный формат роняет старт), сопоставление метод → правило — в `app` (`rateLimits`). Счётчики — фиксированные окна в Redis при заданном `REDIS_ADDR` (общие для реплик; `make dev-persistent` берёт Redis из compose) или в памяти (на реплику, с предупреждением при старте). Превышение — `ResourceExhausted` → HTTP 429 «too many requests, try again later». Сбой Redis пропускает вызов с предупреждением в логе: защита от спама не должна останавливать сайт. Новое действие, создающее контент для других, получает свой лимит.

Поиск людей — в `user`: каждое слово запроса ищется `LIKE '%слово%'` по выражению с триграммным индексом `pg_trgm`. Условия на слова — отдельные `AND ... LIKE $n`: с `LIKE ALL (массив)` GIN-индекс не используется (проверено `EXPLAIN`).

Структура `gateway/` другая — в нём нет бизнес-логики:

```
gateway/
├── api/openapi.yaml         # публичный контракт для фронтенда
└── internal/
    ├── model/               # «домен» gateway: то, о чём говорит API, без JSON и proto
    ├── failure/             # виды ошибок для клиента (Kind) с безопасными сообщениями
    ├── backend/             # адаптеры к gRPC-сервисам: proto ↔ model, статус → failure
    ├── rest/                # HTTP: маршруты, DTO (camelCase JSON), middleware, порты Auth/Users
    ├── config/
    └── app/
```

`rest` зависит от портов (`rest.Auth`, `rest.Users`) и `model`, но не от gRPC; `backend` — единственное место, где gateway знает proto. Enum'ы в JSON — строчные имена значений домена (`"in_love"`, `""` = не задано), даты — `YYYY-MM-DD`.

## 2. Архитектура: чистая архитектура

### 2.1. Слои и правило зависимостей

Зависимости направлены **только внутрь**:

```
transport (grpc) ─┐
                  ├─►  service (use cases)  ─►  domain (entities, value objects)
infra (postgres,  ─┘          ▲
 redis, jwt, smtp)            │ реализуют интерфейсы, объявленные в service
```

| Слой | Пакет | Что содержит | Что импортировать МОЖНО | Что НЕЛЬЗЯ |
|---|---|---|---|---|
| Домен | `internal/<domain>` | сущности, value objects, инварианты, доменные ошибки | stdlib, `uuid` | proto, pgx, redis, grpc, slog, любой фреймворк, другие слои |
| Приложение | `internal/service` | use cases, DTO, **интерфейсы-порты** | домен, `pkg/errs` | proto-типы, `grpc/status`, SQL, redis-клиент, JWT-библиотеки |
| Транспорт | `internal/grpc` | хендлеры, маппинг proto↔домен, перевод ошибок в gRPC-коды | service, домен, proto | SQL, бизнес-правила |
| Инфраструктура | `postgres`, `redis`, `inmem`, `jwt`, `smtp`, `console` | реализации портов | домен, service (только для типов в сигнатурах), драйверы | бизнес-логика, импорт `grpc`-слоя |
| Composition root | `internal/app`, `cmd/` | сборка графа зависимостей | всё | — |

Жёсткие запреты:
- Домен не знает ни про что снаружи. Никаких тегов `db:`/`json:`, никаких proto-типов в доменных структурах.
- Сервисный слой **не импортирует сгенерированные proto-пакеты** (ни свои, ни чужих сервисов). Вызов другого сервиса — через порт (интерфейс в `service`), реализация-адаптер (gRPC-клиент) лежит в инфраструктуре, например `internal/userclient/`.
- Инфраструктура не вызывает use cases и не знает про транспорт.
- Циклические импорты между слоями недопустимы; если возникает — нарушена архитектура, а не «нужно вынести в utils».

### 2.2. Интерфейсы (порты)

- Интерфейс объявляется **на стороне потребителя** (там, где используется), а не рядом с реализацией: `service.UserRepository`, `grpc.UserService`.
- Интерфейсы маленькие: 1–4 метода, под конкретный use case. Не создавай «толстый» `Repository` на все случаи.
- Конструкторы принимают интерфейсы, возвращают **конкретные типы** (`NewUserService(repo UserRepository) *UserService`).
- Не создавай интерфейс «на будущее» без второго потребителя/реализации или потребности в моке.

### 2.3. Доменный слой

- Сущности — структуры с **неэкспортируемыми полями** и геттерами (`u.Email()`), создаются только через конструктор `New(...)`, который проверяет инварианты. Нельзя получить невалидную сущность.
- Для восстановления из хранилища — отдельный конструктор `Restore(...)` (без генерации ID и без побочных эффектов), а не публичные поля.
- Примитивы с правилами — **value objects** на базе `string`/`time.Time` в отдельных файлах: `Email`, `Nickname`, `Name`, `Birthday`, `Gender` и т. д. Шаблон:
  - тип `type Email string`;
  - конструктор `NewEmail(s string) (Email, error)`: нормализация (`TrimSpace`) → проверка → значение;
  - метод `String()`;
  - константы лимитов (`maxEmailLen`) и **доменные ошибки-sentinel** в `var (...)` рядом с типом.
- Перечисления — типизированные строковые константы + конструктор-валидатор (`NewGender`), а не «голые» строки. Значение «не задано» — осознанная константа (`GenderNone`).
- Длину строк считать в рунах (`utf8.RuneCountInString`), не в байтах.
- ID сущностей — `uuid.UUID`, генерация — **UUIDv7** (`uuid.NewV7()`).
- Время — `time.Time` в UTC. В доменном слое, где время влияет на логику, не вызывай `time.Now()` напрямую в неочевидных местах — передавай время параметром или используй интерфейс `Clock`, чтобы это можно было тестировать.
- Бизнес-правила живут в домене (методы сущностей), а не в хендлерах и не в SQL.

### 2.4. Сервисный слой (use cases)

- Один публичный метод = один use case. Принимает `context.Context` **первым** аргументом.
- Вход — DTO из `service/dto.go` (`CreateUserInput`) с **доменными типами** (value objects), а не сырые строки/proto. Выход — доменные сущности или DTO сервиса (`TokenPair`).
- Сервис оркестрирует: вызывает домен, репозитории, внешние порты. Не содержит SQL, не знает про gRPC-коды, не логирует «для галочки» (логирование ошибок — на границе, см. §5).
- Многошаговые операции, которые должны быть атомарными, выполняются в транзакции через порт (`TxManager`/`WithinTx`), а не склейкой из нескольких независимых вызовов. Реализация — `pgpool.TxManager`: транзакция едет в контексте, вложенный `WithinTx` присоединяется к внешней; для `inmem` — `inmem.TxManager`, который просто вызывает функцию. Так же атомарно с изменением записывается всё, что надо сообщить другому сервису (outbox, см. §1).
- Идемпотентность и гонки продумываются явно: «получить или создать» опирается на уникальный индекс в БД (`INSERT ... ON CONFLICT` или повторное чтение после `ErrAlreadyExists`, как в `user.GetOrCreateByEmail`), а не на `Get` + `Create` без защиты.

### 2.5. Транспортный слой (gRPC)

- Хендлер делает только: (1) достаёт данные из запроса, (2) собирает value objects (валидация формата), (3) вызывает use case, (4) мапит результат в proto, (5) переводит ошибки в gRPC-статусы.
- Маппинг proto↔домен — только в `mapper.go` пакета `grpc`. Именование: `toProtoX` (домен → proto), `fromProtoX` (proto → домен).
- Всегда используй геттеры (`req.GetEmail()`), а не прямой доступ к полям — они nil-безопасны.
- Метод, возвращающий `google.protobuf.Empty`, возвращает `&emptypb.Empty{}`, а **не** `nil, nil`.
- Трансляция ошибок (единое место, функция `toStatusError(err)`):

  | Ошибка | gRPC-код |
  |---|---|
  | ошибка валидации входа / value object | `InvalidArgument` |
  | сущность не найдена | `NotFound` |
  | уже существует / конфликт | `AlreadyExists` |
  | нет/невалидный токен или код | `Unauthenticated` |
  | нет прав | `PermissionDenied` |
  | лимит запросов | `ResourceExhausted` |
  | состояние не позволяет (страница не удалена, срок восстановления вышел) | `FailedPrecondition` (gateway — 409) |
  | всё остальное | `Internal` с **общим** текстом |

  Сопоставление — через `errors.Is`/`errors.As` по доменным ошибкам. Нельзя отдавать `err.Error()` внутренней ошибки клиенту (утечка деталей) и нельзя маппить всё подряд в `Internal` или всё в `InvalidArgument`.
- Сквозные вещи (логирование запросов, recover, метрики, трассировка, аутентификация по JWT) — через gRPC-интерсепторы, а не копипастой в хендлерах. ID запроса и метрики ставит сам `grpcserver.New` (снаружи интерсепторов сервиса), клиенты другим сервисам собираются с `reqid.DialOptions()`.
- Аутентификация — `jwtauth.UnaryServerInterceptor`: по умолчанию **каждый** RPC требует access-токен, публичные методы перечисляются явно (`jwtauth.Access{Public: grpc.PublicMethods()}`), методы, доступные токену удалённой страницы, — тоже (`Access.Deactivated`). ID текущего пользователя хендлер берёт из `jwtauth.IdentityFromContext`. Публичный метод работает и без токена, но присланный токен всё равно проверяется: так ответ может зависеть от зрителя («вы подписаны»), а истёкший токен даёт 401 для обновления.
- Внутренние RPC (вызываются только другими сервисами) перечисляются в `grpc.InternalMethods()` с разрешёнными идентичностями и закрываются `mtls.RestrictMethods`.
- Перевод ошибок — `grpcserver.ErrorInterceptor(log, toStatus)`: в сервисе остаётся только `toStatus(err) (*status.Status, bool)` с таблицей известных ошибок.
- Публичный контракт — только `.proto`. Меняя его, сохраняй обратную совместимость (см. §9).

### 2.6. Инфраструктурный слой

- Репозиторий реализует порт из `service`, принимает и возвращает **доменные** типы. Типы драйвера (`pgx.Row`, `redis.Nil`) наружу не выходят: `pgx.ErrNoRows` → доменная `ErrNotFound`, нарушение unique → `ErrAlreadyExists`, `redis.Nil` → `ErrNotFound`.
- Структура репозитория — `struct{ pool *pgxpool.Pool }` + `NewXRepository(pool)`. Репозиторий, который участвует в транзакциях, выполняет запросы на `r.conn(ctx)` (= `pgpool.Conn(ctx, r.pool)`): внутри `WithinTx` это транзакция, снаружи — пул.
- SQL — константами рядом с методом, именованными `<action><Entity>Query`; только параметризованные запросы (`$1, $2`), **никогда** конкатенация строк. Колонки в `INSERT`/`SELECT` перечисляются явно (никаких `SELECT *`), по одной на строку.
- Каждый запрос — с `ctx`. Для чтений из БД — таймауты через контекст.
- `inmem`-реализации — только для разработки и тестов; они должны вести себя как настоящие (TTL, уникальность, те же sentinel-ошибки). Не использовать их в production-сборке (`app.New` должен брать `postgres`/`redis` по конфигу).
- Redis: ключи с префиксом по назначению (`verification_code:<email>`), у каждого ключа обязательно TTL.

### 2.7. Composition root (`internal/app`, `cmd`)

- Единственное место, где создаются конкретные реализации и связываются зависимости (ручной DI, без DI-фреймворков и глобальных переменных).
- `main` минимален: `config.Load` → `logger.New` → `app.New` → `app.Run(ctx)`. Контекст должен отменяться по `SIGINT`/`SIGTERM` (`signal.NotifyContext`), а не быть `context.Background()`.
- `app.New` создаёт ресурсы и **не закрывает** те, что нужны во время работы (нельзя `defer conn.Close()` на gRPC-клиенте/пуле внутри конструктора — они понадобятся после возврата). Все ресурсы закрываются в `App.Close()`, который вызывается из `main` через `defer`/после `Run`.
- Graceful shutdown: health → `SERVING`/`NOT_SERVING`, `GracefulStop` с таймаутом и fallback на `Stop`, затем закрытие пулов и клиентов. `App.Run` запускает основной сервер и сервер метрик в `errgroup`: сбой одного (например, занят порт) останавливает другой.
- Адреса других сервисов, TTL, таймауты, порты — в конфиге, а не литералами в `app.go` (запрещено: `grpc.NewClient("localhost:7052", ...)`, `15*time.Minute` прямо в сборке).

### 2.8. Фронтенд (`web/`)

Сайт нарочно простой, в духе соцсетей конца 2000-х: никаких фреймворков, сборщиков и npm.

- **Образец интерфейса — openvk.org, и это обязательно.** Любая новая функциональность, которой нужен фронтенд, делается так, как она устроена в openvk: перед вёрсткой посмотри там тот же элемент — расположение, подписи, ссылки, поведение — и повтори его классами нашего `style.css`. Так, лайк — сердечко со счётчиком справа в подвале записи, комментарии — блок «Комментарии (N)» на странице записи. Отступать от openvk можно только осознанно, с причиной в описании коммита.
- Структура: страницы `index.html` (вход/регистрация), `edit.html` (анкета и приватность), `blacklist.html` (чёрный список, вкладка настроек), `profile.html` (профиль со стеной и подписками), `feed.html` («Мои Новости»), `post.html` (запись с комментариями, `/post/<id>`), `notifications.html` («Мои Ответы»: вкладки «Непрочитанное»/«Архив», `?box=archive`), `im.html` («Мои Сообщения»: список диалогов), `dialog.html` (диалог, `/im/<nickname>`), `groups.html` («Мои Группы», с `?u=<nickname>` — группы другого человека), `club-create.html` («Создать группу»), `club.html` (страница группы, `/club/<адрес или id>`), `club-edit.html` (настройки группы), `club-members.html` (участники и руководство), `club-suggested.html` (предложенные записи: все — администраторам, `?type=my` — свои), `follows.html` (подписчики/подписки с вкладками, `?u=<nickname>&type=followers|following`), `search.html` (поиск: «Люди» и «Группы» (`?section=groups`), обычная GET-форма `?q=`); в `static/` — `style.css`, `api.js` (клиент API), `labels.js` (русские подписи, даты, склонения, тексты ошибок), `layout.js` (шапка, меню, хелперы), `events.js` (живые события: WebSocket, переподключение), `posts.js` (отрисовка записи с лайком, фото и вложенной записью репоста; в ленте — «на стене …»), `modal.js` (окно сообщения openvk: заголовок, тело, кнопки), `deactivate.js` (окно «Удаление страницы»), `share.js` (окно «Поделиться»), `postedit.js` (правка записи на месте), `blacklist.js` и `blacklist-page.js` (чёрный список на профиле и в настройках), `attach.js` (прикрепление фото к записи), `viewer.js` (просмотр фото поверх страницы), `comments.js` (отрисовка комментария), `notifications.js` (страница ответов), `im.js` и `dialog.js` (сообщения), `people.js` (человек в списках), `wall.js` (блок «Стена»: записи владельца и чужие, форма для тех, кому можно писать), `follow.js` (кнопка подписки и блоки людей), `photo.js` (загрузка и удаление фото) и по скрипту на страницу. ## 3. Чистый код (Go)

### 3.1. Общее
- Код должен проходить `gofmt`, `go vet`, `golangci-lint run`. Перед завершением задачи — `make check` в изменённом сервисе, перед коммитом — `make check-integration` из корня (то же, что CI).
- Простота важнее «умности». Не добавляй абстракции, пакеты, интерфейсы и параметры «на вырост». Правило трёх: дублируй до третьего повторения, потом выноси.
- Функция делает одну вещь на одном уровне абстракции. Ориентир: ≤ ~40 строк, ≤ 4 параметра (больше — структура-DTO), вложенность ≤ 3. Используй ранние возвраты (guard clauses), избегай `else` после `return`.
- Не используй `init()`, глобальное изменяемое состояние, `panic` для обычных ошибок (только в тестах и `Must*`-хелперах при старте).
- Не оставляй мёртвый код, закомментированный код, `TODO` без причины и автора/тикета.
- Комментарии объясняют **почему**, а не **что**. Экспортируемые идентификаторы с неочевидным поведением документируются в формате godoc (`// Name ...`). Язык комментариев в коде — английский; текст ошибок и логов — английский.

### 3.2. Нейминг
- Пакеты: короткие, строчные, одно слово, без `_` и без `util`/`common`/`helpers`/`base`. Имя пакета не повторяется в идентификаторе (`user.New`, не `user.NewUser`; `session.Session` допустимо как исключение для основной сущности).
- Конструкторы: `New`, `NewX`. Валидирующие конструкторы возвращают `(T, error)`.
- Интерфейсы: по роли (`Hasher`, `Mailer`, `TokenProvider`, `UserRepository`), без префикса `I` и суффикса `Impl`.
- Ресиверы — короткие (1–2 буквы), одинаковые у всех методов типа. Указатель для сущностей и сервисов, значение — для value objects.
- Ошибки-sentinel: `ErrXxx` (`ErrInvalidCode`, `ErrEmailEmpty`). Типы ошибок: `XxxError`.
- Аббревиатуры в верхнем регистре: `ID`, `URL`, `HTTP`, `JWT`, `SQL`.
- Булевы: `isX`, `hasX`, `canX`. Не называй переменные `data`, `info`, `tmp`, `obj`, `res` без необходимости.
- Файлы: по сущности/ответственности, `snake_case.go` (`political_views.go`). Тесты — `*_test.go` рядом с кодом.

### 3.3. Обработка ошибок
- Ошибки не игнорируются (`_ = f()` допустим только для `Close()` в cleanup и с комментарием/логом).
- Ошибки оборачиваются при **каждой** передаче вверх через `errs.Wrap("<что вызывали>", err)` — по шаблону проекта: `errs.Wrap("s.userRepo.Save", err)`, `errs.Wrap("uuid.Parse", err)`. Текст — это имя вызванной функции/метода, а не «failed to…». Если вызов называется иначе, чем строка (опечатка `s.userRepo.Create` для `Save`) — это баг, строка должна совпадать с реальным вызовом.
- Сравнение — только через `errors.Is` / `errors.As`, никогда по тексту ошибки.
- Не логируй и не возвращай одну и ту же ошибку одновременно: ошибка **либо** обрабатывается, **либо** возвращается. Логируется ошибка один раз — на границе (хендлер/интерсептор/`main`).
- Доменные ошибки — sentinel-переменные в пакете домена, инфраструктурные ошибки переводятся в доменные в репозитории (§2.6). Реализации (`inmem`, `redis`) не должны определять собственные «параллельные» ошибки, отличные от доменных.
- Сообщения ошибок — строчные, без точки в конце, без чувствительных данных.

### 3.4. Контекст, конкурентность, ресурсы
- `context.Context` — первый параметр каждой функции, делающей I/O; не хранится в структурах. Внешние вызовы (БД, Redis, gRPC, SMTP) всегда с таймаутом/дедлайном и реагируют на отмену `ctx`.
- Горутины не запускаются «вхолостую»: у каждой есть владелец, способ остановки и обработка ошибки. Общие данные защищены (`sync.Mutex`/`RWMutex`) или передаются каналами.
- Ресурсы закрываются сразу после успешного открытия через `defer`. Горутины и коннекты не утекают.
- Не делай пакетные глобали вроде `http.DefaultClient` с нулевым таймаутом.

### 3.5. Логирование
- Только `*slog.Logger`, внедряется зависимостью (не глобальный `slog.Default()`). Структурные поля: `log.Error("create user", "error", err, "user_id", id)`. Первый аргумент — **сообщение**, дальше пары ключ-значение (нельзя `log.Error("app.New", err)` — это ломает пары ключ-значение). Где есть контекст запроса — `...Context`-варианты (`log.WarnContext(ctx, ...)`): только так в строку попадает `request_id`.
- Уровни: `debug` — диагностика, `info` — значимые события жизненного цикла, `warn` — восстановимые аномалии, `error` — сбой операции.
- **Запрещено логировать**: пароли, JWT/refresh-токены, коды подтверждения, секреты, полные email/персональные данные в `info`/`error` продакшена. `console.Mailer` с логированием кода допустим только как dev-реализация и не должен подключаться в production.
- Ключи логов — `snake_case`, единообразные по проекту (`user_id`, `session_id`, `request_id`).

### 3.6. Конфигурация
- Все настройки — из переменных окружения, описанных структурой с тегами `env:"NAME,required,notEmpty"` (одного `required` мало: пустое `NAME=` его проходит). Необязательные — с `envDefault`. Каждая переменная добавляется в `.env.example` (без реальных значений, комментарии — отдельной строкой).
- `.env` необязателен: в контейнерах переменные приходят из окружения и имеют приоритет над `.env`.
- Реализации выбираются конфигом: `STORAGE=inmem|persistent` (по умолчанию `inmem` — для разработки ничего запускать не нужно), `MAILER=console|smtp` (по умолчанию `console`). Зависимости между переменными (например, `persistent` требует `DATABASE_URL`) проверяет `Config.validate()` при старте.
- Секреты (`HASH_SECRET`, ключи JWT, пароли БД, SMTP) никогда не коммитятся; `.env` в `.gitignore`.
- Загрузка и валидация конфига — при старте; приложение падает сразу, если конфиг неверен. Литералы вроде адресов и TTL выносятся в конфиг.

## 4. Данные и миграции

- Схема БД меняется **только** миграциями `goose` в `<service>/migrations` (`make migrate-create name=add_users_table`). Применённые миграции не редактируются — только новые.
- Миграции встроены в бинарник (`migrations/embed.go`) и применяются при старте в режиме `persistent` (`MIGRATE_ON_START`, по умолчанию `true`) под advisory lock PostgreSQL — несколько реплик стартуют безопасно. `make migrate-*` остаются для ручной работы.
- У каждого сервиса своя БД; **нельзя** делать запросы в таблицы другого сервиса или общие JOIN между сервисами — только через gRPC API владельца.
- Каждая миграция имеет рабочие `Up` и `Down`. Миграции обратимо-совместимы с предыдущей версией кода (expand → migrate → contract) для zero-downtime.
- Типы и ограничения: `uuid` для ID, `timestamptz` для времени, `NOT NULL` по умолчанию, `UNIQUE`/`CHECK`/`FOREIGN KEY` — в БД, а не только в коде (уникальность email/nickname гарантируется индексом). Индексы — под реальные запросы.
- Имена: таблицы — множественное число `snake_case` (`users`, `sessions`); колонки — `snake_case`; соответствие полей домена и колонок проверяется тестом/интеграционным прогоном.
- Пагинация в ленте и списках — **keyset (cursor)**, не `OFFSET` (Twitter-подобные ленты растут неограниченно). UUIDv7 удобен как курсор.

## 5. Безопасность

- Валидация **всех** входных данных на границе (value objects). Ничему извне не доверяй, включая данные от других сервисов.
- Аутентификация: access JWT короткоживущий (15 мин), refresh — долгоживущий, хранится в БД **только в виде хеша** (HMAC-SHA256 с секретом). Refresh-токен ротируется при обновлении; повторное предъявление уже ротированного токена завершает всю сессию; `Logout` удаляет сессию. Access-токен stateless и после `Logout` действует до истечения (≤ 15 мин) — это осознанный компромисс.
- Верификация подписи JWT — по **публичному** ключу и только ожидаемым алгоритмом (`WithValidMethods`), проверка `iss`, `exp`, типа токена (`access` ≠ `refresh`).
- Коды подтверждения: криптостойкая генерация (`crypto/rand`), хранятся хешем, имеют TTL, **одноразовые** (удаляются после успешной проверки), ограничено число попыток проверки, ограничена частота запроса нового кода (rate limit по email и IP). Сравнение — `hmac.Equal`/`subtle.ConstantTimeCompare`.
- Частота действий, создающих контент для других (записи, комментарии, лайки, сообщения, загрузки, подписки), ограничена на пользователя (`pkg/ratelimit`, см. §1); новое такое действие без лимита — дыра для спама.
- Ответы не должны позволять перебирать существование аккаунтов (`RequestCode` для любого email отвечает одинаково).
- Межсервисные вызовы — по mTLS (`pkg/mtls`, переменные `TLS_CA_PATH`, `TLS_CERT_PATH`, `TLS_KEY_PATH`): сервер принимает только клиентов с сертификатом внутреннего CA, CN сертификата — идентичность сервиса (`auth`, `user`, `post`, `media`, `notification`, `message`, `club`, `gateway`). Без этих переменных — plaintext, только для локальной разработки; сервис пишет об этом предупреждение при старте. Наружу публикуется только `gateway`.
- Адрес клиента для лимитов: `gateway` берёт его из соединения (или из `X-Forwarded-For`, только при `TRUST_FORWARDED_FOR=true` за своим прокси, крайнее правое значение) и передаёт в `auth` метаданными `authv1.ClientIPMetadata`; `auth` верит им только от mTLS-идентичности `gateway`.
- Ответы API не кешируются (`Cache-Control: no-store`), CORS разрешён только для `CORS_ALLOWED_ORIGINS`.
- Порт метрик (`METRICS_PORT`) наружу не публикуется: метрики раскрывают нагрузку и устройство системы. Метки метрик — только из ограниченных множеств (метод, шаблон маршрута, код), никогда ID, никнеймы или email.
- Секреты и ПДн не попадают в логи, ошибки, ответы API, URL.
- Чувствительные данные профиля (мировоззрение, политические взгляды, отношения, дата рождения — это **специальные категории ПДн**) отдаются другим пользователям только с учётом настроек приватности владельца; по умолчанию не раскрываются. Любой новый эндпоинт, возвращающий профиль, обязан это учитывать.
- Зависимости обновляются осознанно; не добавляй библиотеку, если задача решается стандартной библиотекой за пару десятков строк.

## 6. Тестирование

- Каждое изменение поведения — с тестами. Баг-фикс начинается с теста, воспроизводящего баг.
- Пирамида: много быстрых unit-тестов (домен, сервис), немного интеграционных (репозитории на реальном PostgreSQL/Redis через compose/testcontainers), единичные e2e на gRPC.
- Unit-тесты: табличные (`[]struct{ name string; ... }` + `t.Run`), `t.Parallel()` где безопасно, пакет `<pkg>_test` для проверки публичного API.
- Домен: тестируем конструкторы и граничные значения value objects (пусто, лимит длины, кириллица/эмодзи, пробелы).
- Сервис: зависимости — через порты; используем ручные fake-реализации (`inmem`) или сгенерированные моки; **не мокаем то, чем владеем в домене**.
- Не используем `time.Sleep` в тестах; время и случайность инъецируются.
- Тесты детерминированы и независимы; нет зависимости от порядка и внешней сети. Запуск: `make test` (`go test ./...`), перед PR — с `-race`.
- Интеграционные тесты репозиториев пропускаются без своих переменных: Postgres (`internal/postgres`) — `TEST_DATABASE_URL` (база с применёнными миграциями), Redis (`auth/internal/redis`, `pkg/ratelimit`) — `TEST_REDIS_ADDR`. Проще всего — `make check-integration`: скрипт поднимает временные Postgres 18 и Redis 7 в Docker, создаёт и мигрирует отдельную базу на сервис (общим пакетам, чьи тесты читают `TEST_DATABASE_URL`, — пустую: `pkg/pgpool`, `pkg/outbox` создают свои таблицы сами) и удаляет контейнеры после прогона. Вручную: `TEST_DATABASE_URL=postgres://... TEST_REDIS_ADDR=localhost:6379 go test ./internal/postgres ./internal/redis`.
- Покрытие — не самоцель, но весь бизнес-код (домен + сервис) должен иметь тесты на успешный путь и на каждую ветку ошибки.

## 7. Protobuf / gRPC-контракты

- Файлы — `<service>/api/<service>/v1/<service>.proto`, пакет `<service>.v1`, `go_package = "github.com/vexner67/freenet/<service>/api/<service>/v1;<service>v1"`.
- Сгенерированный код (`*.pb.go`, `*_grpc.pb.go`) **не правится руками** — только `make proto` в сервисе. Генерация закоммичена.
- Совместимость: не менять и не переиспользовать номера полей, удалённые поля — `reserved`; новые поля — только добавлять. Ломающие изменения — новая версия пакета (`v2`).
- Каждое сообщение имеет **свои** номера полей с 1 подряд, без пропусков. Запросы и ответы — отдельные сообщения на каждый RPC (`<Rpc>Request`/`<Rpc>Response`), не переиспользовать доменные сообщения в качестве запроса.
- Enum: нулевое значение — `*_UNSPECIFIED`/`*_NONE`, имена с префиксом типа (`GENDER_MALE`).
- Каждый RPC, объявленный в `.proto`, должен быть реализован хендлером; не оставляем объявленные, но не реализованные методы.
- Удаление RPC или сообщения — ломающее изменение: допустимо, только если у него нет потребителей (так был удалён неиспользуемый `user.Create`); иначе — новая версия пакета.
- Идентификаторы пользователя для бизнес-вызовов берутся из **проверенного JWT** (контекст/метаданные), а не из тела запроса.

## 8. Рабочий процесс

- Перед правкой — прочитай соседний код сервиса и следуй его стилю; новое решение должно выглядеть так, будто его написал автор остального кода.
- Изменения минимальны и сфокусированы: одна задача — один коммит/PR. Не смешивай рефакторинг с фичей.
- Порядок разработки новой фичи «изнутри наружу»: домен → use case (+порты) → инфраструктура (+миграция) → транспорт (`.proto`, хендлер, mapper) → сборка в `app` → тесты на каждом шаге.
- Команды (из каталога сервиса):
  ```bash
  make run         # запуск сервиса
  make build       # сборка
  make test        # тесты
  make fmt         # go fmt
  make lint        # golangci-lint
  make check       # fmt + lint + test (обязательно перед коммитом)
  make proto       # перегенерация protobuf
  make tidy        # go mod tidy
  make migrate-create name=<name> / migrate-up / migrate-down / migrate-status
  ```
  Из корня: `make dev` / `make dev-persistent` — весь бэкенд; `make check` / `make check-integration` — проверки всех модулей и сайта, как в CI; `make stack` / `make smoke` — весь сайт в Docker и его сквозная проверка; `make up` / `make ps` / `make down` — docker compose (`down` останавливает и стек); `make certs` — dev-сертификаты для mTLS и JWT-ключи; `make web-test` — тесты сайта; `make ssh` — вход на прод-сервер (root по ключу `~/.ssh/freenet-prod_ed25519`, одно соединение на 10 минут; `PROD_HOST`, `PROD_KEY`).
- Локальный запуск всего бэкенда и сайта одной командой из корня: `make dev` (`scripts/dev.sh`) — собирает и запускает `notification`, `message`, `user`, `post`, `media`, `auth`, `gateway` с их `.env`, выводит логи с метками сервисов, Ctrl+C останавливает всё штатно; если один сервис упал, останавливаются и остальные. По умолчанию `STORAGE=inmem` и без mTLS — ничего, кроме Go, не нужно. `make dev-persistent` сначала поднимает Postgres и Redis (`docker compose up -d --wait`) и переключает сервисы на них. Новый сервис добавляется в массив `services` скрипта. Отдельный сервис по-прежнему можно запустить `make run` в его каталоге.
- Общий код между сервисами — только в `pkg/<name>` как отдельный модуль (с `go.mod`), добавленный в `go.work`. Это должны быть **маленькие технические** пакеты без бизнес-логики. Бизнес-логику между сервисами не шарим — общаемся по gRPC. Сервис не импортирует `internal/` другого сервиса; импорт чужого `api/` (proto-клиента) разрешён только из инфраструктурного адаптера.
- Коммиты — в стиле истории репозитория: Conventional Commits (`feat:`, `fix:`, `chore:`, `refactor:`, `test:`, `docs:`), краткое описание в повелительном наклонении, английский язык.
- Не коммить `.env`, ключи, бинарники, `.idea/`. Не меняй `go.work.sum`/`go.sum` вручную — только через `go mod tidy`/`go work sync`.
- Не используй `git push --force`, не переписывай историю общих веток.

### Definition of Done
- [ ] Соблюдено правило зависимостей слоёв (§2.1), нет proto/SQL/драйверов не в своём слое.
- [ ] Все ошибки обёрнуты `errs.Wrap`, нет проглоченных, в gRPC мапятся в корректные коды (§2.5).
- [ ] Входные данные валидируются value objects; секреты/ПДн не попадают в логи.
- [ ] Есть тесты (успех + ветки ошибок), `make check-integration` из корня проходит (как CI).
- [ ] Новый сервис или переменная окружения добавлены и в `compose.yaml` (профиль `app`), и стек проходит `make stack && make smoke`.
- [ ] Миграция (если нужна) с `Up`/`Down`; `.env.example` обновлён; `.proto` совместим и перегенерирован.
- [ ] Новый код собран в `app` и действительно используется (нет мёртвых реализаций и неподключённых RPC).
- [ ] Если фича видна на сайте — интерфейс сделан по образцу openvk.org (§2.8), страницы проверены в браузере.

## 9. Известные отклонения текущего кода (исправлять при касании)

Это не образец для подражания, а технический долг — не копируй эти паттерны:

1. Docker, CI и прод: образы в GHCR не подписаны, нет манифестов для оркестратора (Kubernetes) — прод один сервер с docker compose; нет резервных копий баз и `.data/media` (pg_dump по расписанию и копия на другой машине); деплой перезапускает изменившиеся сервисы — секунды простоя, без rolling update; Prometheus/Grafana на сервере видны только через SSH-туннель, алерты никого не оповещают; CI не проверяет, что сгенерированный protobuf-код соответствует `.proto` (нужен `protoc` нужной версии); `make stack` собирает образы без кеша между запусками CI.
2. Сайт хранит токены в `localStorage`, защищаясь строгой CSP. Если на страницах появится сторонний код (счётчики, виджеты), перейти на httpOnly-cookie для refresh-токена.
3. Сертификаты из `make certs` — только для разработки: нет ротации, отзыва и управляемого PKI для продакшена.
4. Наблюдаемость: нет распределённой трассировки (OpenTelemetry) — путь запроса восстанавливается только по `request_id` в логах; нет сбора логов в одно место (Loki и т. п.); алерты никого не оповещают (у получателя в `alertmanager.yml` нет каналов — почты, Telegram), их видно только в Alertmanager и Grafana; Postgres и Redis не наблюдаются (нет экспортёров и алертов на них); у Grafana пароль `admin` по умолчанию, хранилище — volume стека; метрики только серверные и outbox — нет метрик gRPC-клиентов, пулов БД и Redis; сайт не показывает ID запроса в тексте ошибки.
5. `pkg/pgpool.Migrate` проверен только сквозным прогоном, своего интеграционного теста нет.
6. Сайт: ссылки в подвале («о сайте», «правила», «помощь») пока ведут на главную.
7. Записи: история правок не хранится (видно только «ред.»), правка не обновляет записи, уже открытые у других, и не уведомляет тех, кто лайкнул или прокомментировал; редактировать и закреплять можно на стене и на странице записи, в ленте ссылок нет (как и «Удалить»); поделиться можно только на свою стену (в openvk ещё в сообщество и в переписку) и только комментарием, без фото; нет списка «кто поделился»; уведомление о репосте остаётся, даже если исходную запись потом удалили; нет списка «кому понравилось»; обращение в ответе — простой текст, а не ссылка на человека (`[id|Имя]` openvk), и «в ответ» ведёт на комментарий, только если он уже загружен на странице; хозяин стены не может закрыть комментарии; на стене нет вкладок openvk «Записи владельца»/«Чужие записи»; лента не показывает чужие записи на стенах тех, на кого подписан (только записи самих этих людей). Миграция `wall_id` в `post` сразу ставит `NOT NULL`: старая версия `post`, не пишущая `wall_id`, во время выкладки не сможет создавать записи (не expand → contract — выкладок ещё не было). Родительный падеж имён (`genitiveName`) — по окончаниям: редкие имена с беглой гласной вне таблицы исключений (Лев, Павел, Пётр) склоняются неверно.
8. Лента собирается при чтении (fan-out on read) и берёт не больше 1000 последних подписок; при росте — заранее собранные ленты.
9. Фото: ориентация — только из EXIF в JPEG (PNG и WebP с меткой `Orientation` не поворачиваются; HEIC не принимается вовсе); `media` хранит файлы в каталоге `MEDIA_DIR` — это один узел, для нескольких реплик нужен S3 за теми же портами `AvatarStore`/`PhotoStore`; чистка неопубликованных обходит `uploads` целиком (на S3 — правило жизненного цикла бакета); если outbox `post` → `media` стоит дольше `UNPUBLISHED_PHOTO_TTL`, фото уже опубликованной записи может быть удалено как неопубликованное; одно фото можно приложить к двум записям через API (сайт так не делает) — удаление одной заберёт его и у другой; запись, отклонённая после проверки фото (например, лимитом частоты), фото не публикует — оно ждёт повторной попытки сутки; фото, загруженные до разделения на `uploads`/`photos`, считаются опубликованными; нет подписей к фото и альбомов; очистка страницы удаляет чужие комментарии к её записям без блокировки записей (`DeleteOnPostsOf`), так что комментарий, написанный в ту же секунду, может уйти каскадом без своих фото; откат миграции фото сообщений пишет в сообщения из одних фото текст «Фотография».
10. Уведомления: старые уведомления не удаляются со временем. Outbox: доставляет один relay на поток по одной записи — пропускная способность ограничена задержкой `Notify` (достаточно, пока `notification` отвечает за миллисекунды); запись, которую `notification` упорно отвергает «временной» ошибкой, держит все следующие (видно по `outbox_lag_seconds`, алерты `OutboxLagging`/`OutboxStuck`); порядок — по `id`, выданному при вставке: две транзакции, закоммиченные не в том порядке, в каком вставляли, доставятся в порядке вставки (для одного лайка и его отмены это не важно — их делает один пользователь последовательно); доставленные записи удаляются, истории нет; в `inmem` запись не откатывается вместе с изменением.
11. Сообщения: нет редактирования сообщений и поиска по ним, удалить можно только своё и только у обоих в течение суток — нет удаления «у себя» (в том числе чужих сообщений) и выбора нескольких сообщений, как во ВКонтакте; удалённое собеседником не помечается («сообщение удалено»), а просто исчезает; из вложений — только фото; лайки и репосты чёрный список не закрывает; при отказе в подписке через API клиент получает общее «permission denied» (gateway не пропускает тексты `PermissionDenied`).
12. Защита от спама: только ограничение частоты на пользователя — нет фильтров содержимого (ссылки, повторы одного текста), жалоб, модерации и бана; новый аккаунт ограничен так же, как старый; фиксированные окна пропускают до двойного лимита на стыке окон.
13. Живые события: каждое событие получает каждая реплика (один канал Redis на сервис) — при большом числе реплик и событий нужны каналы по пользователю или брокер с маршрутизацией; публикация в Redis синхронная, в запросе (до 2 с при недоступном Redis); при недоступном Redis страница каждые несколько секунд переподключается и снова получает 1013; события не хранятся и не переигрываются — после разрыва страница догоняет обычными запросами; удаление записи (`ForgetPost`) не обновляет счётчик ответов сразу; WebSocket не проверялся за обратным прокси (нужны заголовки `Upgrade`/`Connection` и долгий таймаут).
14. Удаление страницы: нет «Рассказать друзьям» openvk (запись с причиной на стене) — записи удалённой страницы скрыты, её никто бы не увидел; лайки удалённой, но ещё не стёртой страницы остаются в счётчиках; при очистке пропадают и чужие записи на стене стёртого пользователя (с их фото); сессии стёртого пользователя лежат в `auth`, пока их не обновят или не истечёт refresh-токен (в них только ID); причину удаления хранят до очистки, но нигде не показывают; очистка `user` — одна транзакция на пачку из 100 страниц, `ForgetPost` (и `DeletePublishedPhotos` для чужих записей с фото) пишется по записи на каждую удалённую запись.

Сообщества: нет фона, закрытых групп с заявками, встреч, обсуждений, сообщений группы, «Местоположения», должностей администраторов («Изменить комментарий» openvk) и их скрытия («Скрыт: Да»); уведомление о новой предложенной записи приходит на каждое предложение (в openvk одно «новые записи в предложке» на группу) и не больше чем 100 руководителям; предложенные записи открываются отдельной страницей, а не подгружаются над стеной по щелчку, при публикации можно поправить только текст, не фото, а ссылка «N предложенных записей» — ещё один запрос на странице группы; передача группы не спрашивает пароль, как openvk, — паролей у нас нет, вход по коду на почту, только окно подтверждения; в чужом списке групп нет «Вступить в группу»/«Выйти из группы» — только «Просмотр группы»; «Кому видно мои группы» не различает «Пользователям OpenVK» и «Всем желающим» (у нас группы видит и аноним, если открыто всем); фото группы не обрезается по выбору, как в openvk, и не становится записью «обновили фотографию»; закреплённые группы — лишний запрос на каждой странице, а не часть `/me`; группу нельзя удалить (как и в openvk); если страница владельца стёрта до передачи группы, группа остаётся без владельца, и новых администраторов назначить некому; адрес группы — отдельное пространство (`/club/<адрес>`), а не общее с никнеймами, как короткие адреса openvk; назначение администратором и записи участников на стене группы никого не уведомляют; фото записи «От имени сообщества» лежат под ID автора, и их адрес его выдаёт; такие записи уходят вместе со стёртым автором (его фото media стирает всё равно); лента берёт не больше 1000 последних групп читателя; в ленте у своих записей группы, как и у прочих, нет «Редактировать» и «Удалить».
